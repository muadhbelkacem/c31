\chapter{Evaluation and Manual Review Guidelines}

\section{Purpose of the evaluation appendix}
This appendix documents the rules used to evaluate whether a scraped role should be treated as a real internship, a non-internship, or an ambiguous case that requires manual review. The goal of the evaluation process is not only to keep internship records, but also to make each cleaning decision explainable and auditable.

The Internify pipeline evaluates each job posting using a combination of normalized text fields, rule-based internship evidence, negative professional-role patterns, optional local embedding similarity, and deterministic manual-review logic. The final output contains both a boolean decision, \texttt{is\_real\_internship}, and an \texttt{internship\_probability} score. The output also stores \texttt{cleaning\_metadata} so that every decision can be inspected later.

\section{Real internship definition}
A posting is treated as a real internship when it contains strong evidence that the role is intended for students, early-career candidates, or temporary work-term applicants. The strongest positive evidence usually appears in the title, because words such as ``Intern,'' ``Internship,'' ``Co-op,'' ``Student Intern,'' ``Stagiaire,'' or ``Stage'' directly describe the role type.

A role is more likely to be accepted as a real internship when one or more of the following signals are present:
\begin{itemize}
    \item The title contains an internship term, such as intern, internship, co-op, coop, student intern, software intern, engineering intern, data intern, research intern, summer intern, winter intern, fall intern, or stagiaire.
    \item The description says that the candidate must be currently enrolled, actively enrolled, a university student, a college student, an undergraduate student, a graduate student, or pursuing a degree.
    \item The description mentions a fixed internship duration, such as 3 months, 4 months, 8 months, 12 months, 16 months, work term, summer 2026, winter 2026, or fall 2026.
    \item The role is described as a student placement, co-op placement, internship program, work term, stage, programme de stage, or emploi etudiant.
    \item The posting uses education-related terms such as bachelor, master, diploma, degree, university, college, post-secondary, or student.
\end{itemize}

The internal classification threshold used by the ML cleaner is 0.55. A posting with \texttt{internship\_probability} greater than or equal to 0.55 is labelled as a real internship by the backend classifier. The public production frontend applies a stricter display threshold of 0.60, meaning that only accepted internships with \texttt{internship\_probability} greater than or equal to 0.60 are shown to users.

\section{Non-internship definition}
A posting is treated as not a real internship when it mainly describes a permanent, senior, licensed, professional, or experienced full-time role. These roles may still contain words such as ``stage'' or ``student'' in boilerplate text, but the main job requirements and title do not describe an internship.

A role is more likely to be rejected when one or more of the following signals are present:
\begin{itemize}
    \item The title contains senior professional terms, such as manager, director, senior, lead, principal, staff, architect, supervisor, administrator, consultant, head of, or licensee.
    \item The description contains permanent employment terms, such as full-time, full time, permanent, regular full-time, benefits package, signing bonus, or extended health care.
    \item The role requires a professional licence, such as pharmacy license, valid provincial pharmacy license, class A pharmacist, registered pharmacist, registered nurse, medical license, law society membership, CPA, P.Eng, or similar professional requirements.
    \item The role requires several years of experience, such as 5 years, 10 years, minimum 5 years, at least 5 years, or other high-experience requirements.
    \item The title is a high-confidence rejection title, such as Pharmacist, Staff Pharmacist, Relief Pharmacist, Pharmacy Manager, Medical Doctor, Physician, Dentist, Lawyer, or Senior Software Engineer.
\end{itemize}

\section{Ambiguous cases}
Some postings are not clearly positive or clearly negative. For example, a ``Graduate Program'' may be early-career but not necessarily an internship. A ``Trainee'' role may be a student placement in one company but a permanent training position in another. A ``Junior'' role may be suitable for new graduates but not be an internship. These records are treated carefully because automatic classification can be uncertain.

The following terms are considered manual-review signals when the rest of the posting is unclear:
\begin{itemize}
    \item graduate
    \item new graduate
    \item junior
    \item associate
    \item trainee
    \item resident
    \item fellowship
    \item apprentice
    \item entry level
    \item entry-level
    \item co-op eligible
    \item student preferred
    \item recent graduate
\end{itemize}

\section{Manual review rule}
The field \texttt{needs\_manual\_review} is set to true when the record is ambiguous. The pipeline uses deterministic logic instead of sending ambiguous cases to an LLM at runtime.

A posting is flagged for manual review when at least one of these conditions is true:
\begin{enumerate}
    \item The \texttt{internship\_probability} is in the borderline range between 0.45 and 0.60.
    \item The rule-based evidence and semantic evidence disagree.
    \item The title looks like an internship, but the final label is not real internship.
    \item The semantic margin is weak, meaning the classifier does not clearly separate the best internship interpretation from the strongest negative interpretation.
\end{enumerate}

This design makes manual review explainable. Instead of hiding uncertainty, the system exposes records where the automatic decision is less reliable.

\section{Implementation excerpt: final decision and manual review}
The following excerpt shows the core decision logic used by the cleaner. The label threshold is centralized in \texttt{final\_label\_from\_probability}, while \texttt{needs\_manual\_review\_flag} exposes uncertainty instead of hiding it.

\begin{lstlisting}[language=Python, caption=Core decision logic for internship classification]
# ml_pipeline/ml_cleaner/transformer_classifier.py
def final_label_from_probability(probability: float,
 min_probability: float = 0.55) -> str:
 """Single source of truth for final internship label."""
 return "real internship" if probability >= min_probability else "not real internship"

# ml_pipeline/ml_cleaner/pipeline.py
def needs_manual_review_flag(
 probability: float,
 rule_score: float,
 title_has_internship: bool,
 is_real: bool,
 semantic_margin: float | None,
 rule_semantic_disagreement: bool,
 min_review_probability: float,
 max_review_probability: float,
 weak_margin_threshold: float,
) -> bool:
 """Deterministically flag ambiguous records instead of using an LLM fallback."""
 uncertain_probability = min_review_probability <= probability <= max_review_probability
 title_conflict = title_has_internship and not is_real
 weak_semantic_margin = semantic_margin is not None and abs(semantic_margin) < weak_margin_threshold
 return bool(
 uncertain_probability
 or rule_semantic_disagreement
 or title_conflict
 or weak_semantic_margin
 )
\end{lstlisting}

\section{Metadata consistency checks}
The output schema includes several fields that allow the decision to be checked after processing:
\begin{itemize}
    \item \texttt{is\_real\_internship} stores the final boolean decision.
    \item \texttt{internship\_probability} stores the numerical confidence score.
    \item \texttt{needs\_manual\_review} stores whether the role should be checked manually.
    \item \texttt{cleaning\_metadata.internship\_label} stores the textual label, either ``real internship'' or ``not real internship.''
    \item \texttt{cleaning\_metadata.rule\_score} stores the rule-based internship score.
    \item \texttt{cleaning\_metadata.rule\_reasons} stores the positive and negative rule signals found in the posting.
    \item \texttt{cleaning\_metadata.classification\_method} explains whether the result came from rules, local prototype similarity, or deterministic override logic.
    \item \texttt{cleaning\_metadata.semantic\_label} stores the best semantic prototype when available.
    \item \texttt{cleaning\_metadata.semantic\_margin} stores how strongly the semantic model preferred the best label.
    \item \texttt{cleaning\_metadata.rule\_semantic\_disagreement} stores whether rule evidence and semantic evidence disagreed.
    \item \texttt{cleaning\_metadata.domain\_classification} stores the selected role category and confidence.
    \item \texttt{cleaning\_metadata.extracted\_skills} stores the skills found in the posting.
\end{itemize}

The most important consistency rule is that \texttt{is\_real\_internship} and \texttt{cleaning\_metadata.internship\_label} must agree. For example, if \texttt{is\_real\_internship} is true, then the \texttt{internship\_label} should be ``real internship.'' If \texttt{is\_real\_internship} is false, then the \texttt{internship\_label} should be ``not real internship.''

\chapter{Regex, Heuristic Rules, and Normalization Logic}

\section{Purpose of the cleaning rules}
This appendix documents the rule-based and normalization logic used to convert inconsistent scraped job postings into a cleaner internship dataset. The purpose of these rules is to reduce noise from different job boards, standardize fields, remove obvious non-internships, and support consistent frontend display.

\section{Field normalization}
Scraped job data can use different names for the same field. For example, one scraper may use title, another may use job\_title, and another may use position. The cleaner handles this by using field aliases and selecting the first non-empty value.

Examples of normalized field aliases include:
\begin{itemize}
    \item Title aliases: title, job\_title, position, role, name
    \item Company aliases: company, company\_name, employer, organization
    \item Location aliases: location, job\_location, city, place
    \item Description aliases: description, job\_description, details, summary, content
    \item Apply link aliases: original\_apply\_link, apply\_url, url, link, platform\_link
    \item Date aliases: date\_posted, posted\_at, scrape\_date, scraped\_date
\end{itemize}

This allows the pipeline to accept input from multiple scraping sources without requiring every scraper to use exactly the same field names.

\section{Implementation excerpt: field aliases and stable identifiers}
The following excerpt shows how inconsistent scraped field names are mapped into a canonical representation. It also shows the stable ID fallback used when no source identifier is available.

\begin{lstlisting}[language=Python, caption=Field aliases and stable ID generation]
# ml_pipeline/ml_cleaner/text_cleaning.py
FIELD_ALIASES = {
 "title": ("title", "job_title", "position", "role", "name"),
 "company": ("company", "employer", "organization", "company_name"),
 "description": ("description", "job_description", "summary", "details", "content"),
 "location": ("location", "city", "job_location", "place"),
 "link": ("original_apply_link", "apply_url", "link", "url", "platform_link"),
 "salary": ("salary", "compensation", "pay", "wage"),
 "job_age": ("job_age", "date_posted", "posted_date", "posted", "age",
 "scrape_date", "scraped_date"),
 "platform": ("platform", "source", "site"),
}

def first_value(record: dict[str, Any], aliases: tuple[str, ...]) -> str:
 """Return the first non-empty string-like value among candidate aliases."""
 for key in aliases:
     value = record.get(key)
     if value is None:
         continue
     if isinstance(value, (list, tuple)):
         value = ", ".join(str(v) for v in value if v is not None)
     value = str(value).strip()
     if value and value.lower() not in {"none", "null", "nan", "n/a"}:
         return value
 return ""

def stable_id(parts: list[str]) -> str:
 """Create a deterministic ID from important fields."""
 joined = "|".join(p.strip().lower() for p in parts if p)
 return sha1(joined.encode("utf-8")).hexdigest()[:16]
\end{lstlisting}

\section{Title cleaning}
The title normalization step removes extra whitespace, HTML entities, repeated separators, and noisy formatting. The goal is not to rewrite the title, but to keep a readable and consistent version of the original job title.

Examples:
\begin{itemize}
    \item Raw title: `` Software Intern '' $\rightarrow$ Cleaned title: ``Software Intern''
    \item Raw title: ``Data Analyst \& Reporting Intern'' $\rightarrow$ Cleaned title: ``Data Analyst \& Reporting Intern''
\end{itemize}

\section{Company and location cleaning}
Company and location fields are cleaned using the same conservative principle. Empty, null, none, n/a, or nan values are treated as missing values. If a location cannot be found, the frontend fallback is ``Location Not Specified.''

Examples:
\begin{itemize}
    \item Raw location: `` Montreal, Quebec, Canada '' $\rightarrow$ Cleaned location: ``Montreal, Quebec, Canada''
    \item Raw location: ``'' $\rightarrow$ Cleaned location: ``Location Not Specified''
\end{itemize}

\section{Salary cleaning}
Salary cleaning is designed to extract readable compensation information when available while avoiding invented salary values. If no salary is found, the system returns ``Salary not specified.''

Examples of accepted salary patterns include:
\begin{itemize}
    \item \$20 / hour
    \item \$20/hr
    \item \$20 - \$25 / hour
    \item \$50,000 - \$60,000
    \item \$70K
    \item \$70K - \$90K
\end{itemize}

Examples:
\begin{itemize}
    \item Raw salary: ``Compensation: \$20 - \$25 / hour depending on experience'' $\rightarrow$ Cleaned salary: ``\$20 - \$25 / hour''
    \item Raw salary: ``N/A'' $\rightarrow$ Cleaned salary: ``Salary not specified''
\end{itemize}

\section{Duplicate ID logic}
The pipeline uses stable identifiers so that the same role can be tracked consistently after cleaning. If the scraped data already contains a usable job ID, the system keeps it. If the role does not have a reliable ID, the system creates a stable ID from normalized job information such as title, company, location, and link.

The frontend also protects against repeated IDs. If two records produce the same base ID, the later record receives a suffix such as -1 or -2 so that every role still has a unique frontend identifier.

\section{Deduplication logic}
Duplicate removal is important because the same internship may appear on multiple job boards or may be scraped more than once. The deduplication step compares normalized job records using stable link information and similarity between title, company, location, and description.

The configured deduplication thresholds are:
\begin{itemize}
    \item \texttt{duplicate\_similarity\_threshold}: 0.88
    \item \texttt{duplicate\_title\_threshold}: 0.90
\end{itemize}

This means that records must be very similar before they are treated as duplicates. This reduces the risk of deleting different internships that happen to have similar titles.

\section{Implementation excerpt: domain classification}
The following excerpt shows that domain classification is not a black-box label. Keyword scores are computed first, and the optional embedding fallback is used only when keyword confidence is weak.

\begin{lstlisting}[language=Python, caption=Domain classification logic]
# ml_pipeline/ml_cleaner/domain_classifier.py
def _count_keyword(text: str, keyword: str) -> bool:
 if keyword.startswith(" ") or keyword.endswith(" "):
     return keyword in f" {text} "
 return re.search(
     rf"(?<![a-z0-9]){re.escape(keyword)}(?![a-z0-9])",
     text,
     flags=re.I,
 ) is not None

class DomainClassifier:
 """Classify job domains with keyword rules plus optional embedding fallback."""
 def _keyword_scores(self, text: str) -> Counter[str]:
     lower = f" {text.lower()} "
     scores: Counter[str] = Counter()
     for domain, keywords in self.domain_keywords.items():
         for keyword, weight in keywords.items():
             if _count_keyword(lower, keyword.lower()):
                 scores[domain] += weight
     return scores
\end{lstlisting}

\section{API behaviour}
The frontend API reads the production JSON file from \texttt{frontend/public/intern\_data.json}. Before returning roles to users, it normalizes the records and applies the production acceptance filter. This filter requires:
\begin{itemize}
    \item \texttt{is\_real\_internship} must be true.
    \item \texttt{internship\_probability} must be a number.
    \item \texttt{internship\_probability} must be greater than or equal to 0.60.
\end{itemize}

This means that the public API is intentionally stricter than the backend classifier. The backend can keep development and audit records, while the frontend only displays higher-confidence internships.

\section{Skill extraction method}
Skill extraction uses a conservative approach. The system first checks for exact skill names and synonyms in the title and description. These keyword and synonym matches are trusted because they are directly visible in the posting text.

The system can also use optional local embedding similarity for semantic skill matching. However, embedding-based skill extraction is intentionally conservative. A semantic match is accepted only when the best skill score is above the configured threshold and clearly above the second-best score. This reduces false positives, such as extracting programming skills from unrelated business or accounting postings.

The configured skill extraction values are:
\begin{itemize}
    \item \texttt{max\_skills\_per\_job}: 15
    \item \texttt{skill\_similarity\_threshold}: 0.68
    \item \texttt{skill\_similarity\_margin}: 0.06
\end{itemize}

\section{Implementation excerpt: conservative skill extraction}
The following code excerpt shows that skill extraction is not based only on free-form prediction. Exact names and synonyms are checked first. Optional embedding matches are accepted only when they pass both a threshold and a margin test.

\begin{lstlisting}[language=Python, caption=Conservative skill extraction logic]
# ml_pipeline/ml_cleaner/skill_extractor.py
class SkillExtractor:
 @staticmethod
 def _matches_term(text: str, term: str) -> bool:
     term_l = term.lower().strip()
     if not term_l:
         return False
     if len(term_l) <= 2 and term_l not in {"c#", "c++"}:
         return re.search(
             rf"(?<![A-Za-z0-9]){re.escape(term)}(?![A-Za-z0-9])",
             text,
         ) is not None
     return re.search(
         rf"(?<![a-z0-9]){re.escape(term_l)}(?![a-z0-9])",
         text.lower(),
     ) is not None

 def _keyword_hits(self, text: str) -> set[str]:
     found: set[str] = set()
     for skill, payload in self.skills.items():
         terms = [skill, *[str(s) for s in payload.get("synonyms", [])]]
         for term in terms:
             if self._matches_term(text, term):
                 found.add(skill)
                 break
     return found

 def _embedding_hits(self, text: str) -> set[str]:
     # A semantic hit is accepted only when the top score is high enough
     # and clearly separated from the second-best skill.
     if top_score >= self.threshold and (top_score - second_score) >= self.margin:
         found.add(self.skill_names[top_idx])
     return found

\section{Relationship between skill library and category classification}
The skill library and domain keyword library support different parts of the pipeline. The skill library extracts individual skills such as Python, React, Docker, SAP, SIEM, Accounting, or Communication. The domain keyword library assigns the overall category of the role, such as software\_engineering, data\_science, cybersecurity, business, healthcare, or engineering.

For example, a posting that mentions Python, APIs, React, Git, and software development may extract several software skills and also be classified as \texttt{software\_engineering}. A posting that mentions SIEM, threat hunting, and vulnerability research may extract cybersecurity skills and be classified as \texttt{cybersecurity}.

\section{Important implementation note}
The expanded skill library is grouped by category. This is useful for documentation and manual review. However, the inspected runtime code expects the skill library in a flat dictionary format, where each canonical skill is a top-level key. Therefore, unless the code is updated to flatten the grouped JSON format, the safest claim is that the expanded skill library is a curated reference resource for skill extraction and evaluation, not necessarily that every grouped entry is directly loaded by the deployed runtime pipeline.
