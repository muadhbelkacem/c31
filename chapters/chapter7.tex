\chapter{Semantic Schema and Label Space}
This chapter defines the internal data model and the controlled vocabularies used to transform raw internship listings into a structured format. We describe the transition from a "RawDocument" to a "StructuredDocument" and the mechanisms used to bridge the gap between diverse natural language expressions and standardized taxonomies.

This chapter is organized as follows:

    \item \textbf{Section 7.1: Target Schema} defines the structured fields used for extraction and search.

\section{Target Schema}
The target schema serves as the blueprint for the extraction process. It defines the specific fields that the enrichment pipeline (detailed in Chapter 8) aims to populate. Unlike the "RawDocument" schema, which preserves all original artifacts, the "StructuredDocument" schema is optimized for retrieval and analytical consistency.

\subsection{Field Definitions}
The core fields of the schema are categorized into three groups: identifying metadata, descriptive attributes, and semantic labels.

\begin{itemize}
    \item \textbf{Metadata:} Includes a unique \texttt{uuid}, the \texttt{source\_url} or \texttt{file\_origin}, and the \texttt{ingestion\_timestamp}.
    \item \textbf{Textual Attributes:} The \texttt{title\_raw} and \texttt{description\_clean} are preserved to allow for highlighting in search results and for manual verification of extracted data.
    \item \textbf{Semantic Fields:} These are the primary targets for normalization:
    \begin{itemize}
        \item \texttt{canonical\_job\_role}: A reference to a specific node in the occupation taxonomy.
        \item \texttt{skills\_list}: A collection of unique identifiers representing extracted competencies.
        \item \texttt{location\_structured}: A JSON object containing normalized city, region, and country codes.
        \item \texttt{experience\_level}: A categorical value (e.g., Junior, Intern, Lead).
    \end{itemize}
\end{itemize}

\subsection{Design Rationale}
The schema adopts a \textit{denormalized approach} for the "skills" and "tags" fields. While a relational database typically suggests a many-to-many junction table, our search-centric design stores these as arrays of identifiers within the document. This significantly reduces join overhead during complex filtering operations in the search index.

\section{Canonical Labels}
To prevent data fragmentation, the system maps raw strings to a fixed set of canonical labels. As discussed in Chapter 2, we rely on the \textbf{ESCO (European Skills, Competences, Qualifications and Occupations)} framework as our primary label space.

\subsection{Occupation Taxonomy}
Raw job titles vary significantly across companies (e.g., "Happiness Engineer" vs. "Customer Support"). We map these to the ESCO Occupation pillar, typically at the fourth level of hierarchy. This level provides sufficient granularity (e.g., "Web Developer" vs. "Mobile App Developer") without becoming overly specific to the point of sparsity.

\subsection{Skill Taxonomy}
The ESCO skills pillar contains over 13,000 concepts. We filter this space to focus on "Information and Communication Technologies" and "Business and Administration" to keep the label space manageable for our lightweight classifiers. Each canonical skill is associated with a URI, a preferred label, and a set of hidden labels.

\section{Synonyms and Alias Tables}
The "semantic gap" is bridged through a robust mapping layer consisting of manually curated and automatically expanded alias tables.

\subsection{Lexical Normalization}
Before semantic mapping, raw tokens undergo lexical normalization. This includes case folding, punctuation removal, and the resolution of common abbreviations. For example, "Sr." is normalized to "Senior", and "Int." is expanded to "Internship" or "International" depending on the field context.

\subsection{Dynamic Alias Generation}
While the core alias tables are static, we supplement them with a dynamic expansion module. This module uses the Word2Vec or FastText embeddings discussed in Chapter 3 to identify terms that are semantically identical but missing from the lookup table. If a term like "Golang" frequently appears in the same context as "Go (programming language)", the system flags it as a potential alias for review.
