\chapter{System Design and Implementation}

\section{Chapter Introduction}
This chapter describes the concrete implementation of the proposed methodology within the software system. It follows the practical processing flow from heterogeneous data ingestion and preprocessing through semantic enrichment, structured persistence, caching, API communication, and frontend integration.

The focus is on implementation mechanisms directly reflected in the developed system, translating the methodological architecture defined in Chapter 4 into operational software components. Particular attention is given to how lightweight deterministic processing, transformer-assisted semantic classification, and structured data normalization are integrated to support practical internship aggregation and enrichment on commodity hardware.

\section{Data Collection and Preprocessing}
This section details the implementation of the data acquisition, normalization, and semantic enrichment pipeline that forms the computational foundation of the system. As established in the methodology chapter, the primary implementation challenge is transforming noisy, heterogeneous internship and job listing data into structured, semantically enriched records suitable for frontend presentation and practical internship discovery.

The implementation must remain robust against inconsistent source formatting, incomplete metadata, duplicate records, multilingual terminology variation, and noisy recruitment content commonly found in web-sourced internship data [15, 49]. At the same time, it must preserve the lightweight deployment philosophy central to this thesis by avoiding unnecessary computational complexity and dependence on heavyweight external inference services [38, 53].

Consistent with the three-layer processing architecture defined in Chapter 4, the implementation combines deterministic preprocessing for high-confidence normalization tasks, lightweight transformer-assisted semantic classification for ambiguous postings, and controlled exception handling for uncertain cases requiring manual review.

This section begins with the data ingestion mechanism and source normalization process, then describes deterministic preprocessing, heuristic metadata enrichment, semantic classification integration, and the generation of the structured internship dataset used throughout the application.

\subsection{Data Ingestion Pipeline}

The data ingestion pipeline serves as the primary entry point for internship data entering the system. Its role is to acquire raw recruitment records, perform structural validation and normalization, and prepare data for downstream semantic enrichment before persistence and frontend consumption.

As illustrated in Figure X, the ingestion workflow follows a staged asynchronous architecture beginning with automated data acquisition, followed by cleaning and enrichment, persistence, and eventual frontend retrieval. This staged design reflects established data integration practices for handling heterogeneous semi-structured data sources [1, 11, 15].

\subsubsection{Source Acquisition}

The ingestion process begins with automated collection of internship data through the scraping component (ScraperService), which gathers raw internship and recruitment records from supported online sources.

This acquisition stage is designed as an asynchronous process so that data collection and preprocessing remain decoupled from frontend interaction. Such separation ensures that user-facing application behavior is not directly affected by periodic ingestion and enrichment operations.

The system primarily operates on structured JSON-based recruitment data, allowing both scraped datasets and externally provided JSON internship records to enter the same downstream normalization pipeline.

\subsubsection{Initial Structural Validation (Layer 0)}

Before semantic enrichment begins, the pipeline performs an initial validation stage to verify that incoming data is structurally processable.

This validation includes checks for:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item valid JSON formatting
    \item expected structural completeness
    \item required field presence
    \item rejection of clearly malformed or unusable records
\end{itemize}

This defensive preprocessing stage reduces the risk of invalid source data propagating into semantic enrichment components and improves overall pipeline robustness [11, 15].

\subsection{Preprocessing and Sanitization}
Raw data obtained from web scraping is inherently noisy and may contain inconsistent formatting, boilerplate text, and presentation artifacts that are irrelevant to the semantic content. Layer A applies a series of deterministic, rule-based sanitization functions. These functions are computationally inexpensive, predictable, and easy to debug, aligning with the goal of maximizing efficiency for high-volume, high-confidence tasks.


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Field Normalization: Functions like cleanTitle and cleanLocation perform foundational normalization. The process involves:

\end{itemize}

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Text Normalization: Transforming text into a standardized canonical form by lowercasing all characters, collapsing multiple whitespace characters into a single space, and trimming leading/trailing whitespace. This directly reduces surface-form variance, a critical prerequisite for reliable downstream matching~\cite{chu2016data}.

\item HTML Artifact Stripping: Web-scraped text frequently contains residual HTML entities (e.g., \&amp;, \&lt;) and inline tags. A series of regular expression substitutions are applied to convert common entities to their unicode equivalents and remove any remaining tag structures.

\item Specific Normalizations: In the current implementation, title, company, and location normalization primarily trims missing or empty values and substitutes explicit placeholders such as \texttt{Position Not Specified}, \texttt{Company Not Specified}, and \texttt{Location Not Specified}. More aggressive geographic normalization is left as future work.

\end{itemize}

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Salary Extraction: The cleanSalary function is a prime example of a high-precision, deterministic extraction module that operates with zero inference cost. It follows a ``Select-then-Extract'' paradigm~\cite{liu2024survey}, where high-confidence patterns are first identified to isolate the target text before applying specific parsing rules. It employs a tiered set of regular expressions to parse the highly variable salary information found in free text~\cite{sarawagi2008information}:

\item Pattern Identification: The first tier identifies the presence of standard patterns, such as an hourly rate (e.g., ``\$15 - \$20 / hr''), an annual salary (e.g., ``\$70k - \$90k''), or a single value (e.g., ``Up to \$50/hr'').

\item Numeric Extraction: Once a pattern is detected, a second tier extracts the numeric entities, stripping non-numeric characters like \$ and k/K, and correctly interpreting the k suffix as a multiplication factor.

\item Structuring and Validation: The cleaned string is then mapped to the \texttt{salary} field in the \texttt{Internship} interface. A heuristic validation filter ensures that entries with missing critical fields are excluded from the final dataset.

\item Description Cleaning: The free-text job description often contains substantial noise as well as important semantic information. The \texttt{cleanDescription} function trims each line, removes empty lines, and preserves the full description instead of truncating it. This keeps the listing readable in the detail view and leaves enough text for future semantic analysis.

\end{itemize}
\subsection{Data Enrichment and Categorization}
Following sanitization, the system enriches the listing with derived metadata. These enrichment steps create the structured fields that power the faceted filtering and deduplication described in the system's functional requirements. While simple, these heuristic methods provide a high-utility baseline that eliminates the need for more complex processing in the majority of cases.

\subsection{Stable Identifier Generation and Collision Handling}
To ensure persistent, unique referencing across multiple ingestion cycles and to enable effective duplicate detection, the generateId function creates a deterministic, URL-friendly slug. This process is foundational for the data curation strategy and works as follows:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Slugification: A dedicated helper function converts a given string (e.g., a company name or job title) to lowercase, replaces any sequence of non-alphanumeric characters with a single hyphen, and removes leading/trailing hyphens.

\item Concatenation: The canonical ID is formed by concatenating the slugified title and slugified company name, separated by a hyphen.

\item Deterministic Blocking: This generated ID serves as a blocking key for record linkage~\cite{christen2012data}. In deduplication, if a newly ingested listing generates an ID that already exists in the catalog, it is a strong signal of duplication. Recent surveys of record linkage in medical and professional informatics confirm that deterministic rules remain a robust foundation for identifying matches in large-scale datasets where persistent identifiers are required~\cite{sariyar2026record}. The system can then append a suffix or apply a heuristic to select the canonical record based on completeness or source authority. Deterministic blocking is efficient because it limits pairwise comparisons to the small blocks where a collision occurs. This approach directly addresses the deduplication and canonicalization challenges described earlier and provides an explainable, low-cost strategy for maintaining a clean search index for the end user.

\end{itemize}
\subsection{Keyword-Based Categorization}
The \texttt{categorizeJob} function provides an immediate, high-level domain classification by applying keyword-anchored heuristics. This maps the normalized job title to categories such as Software, Data/AI, Design, Marketing, Healthcare, and Business. For instance, titles containing ``software,'' ``developer,'' or ``engineer'' are classified as Software, while titles containing ``data,'' ``analyst,'' ``ai,'' or ``scientist'' are classified as Data/AI. The evaluation proceeds in priority order from more specific technical anchors to the default Business category.

\subsection{Skill Extraction}
The system's initial layer of skill extraction, implemented in the \texttt{extractSkills} function, uses a dictionary-based approach, also known as gazetteer matching. It matches descriptions against a case-insensitive list of common technical and professional skills, including \texttt{python}, \texttt{react}, \texttt{sql}, \texttt{aws}, \texttt{machine learning}, \texttt{figma}, and \texttt{communication}.


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Precision and Efficiency: This method offers high precision for terms present in its lexicon. It identifies terms such as ``Python'' or ``AWS'' when they appear in recognized forms. It is also computationally efficient, requiring only a single pass over the text using standard data structures.

\item Display Control: To keep cards readable, the current implementation returns at most five matched skills per listing. This is a pragmatic interface constraint rather than a learned salience model.

\item Limitation and Role in Tiered Strategy: The lexicon's inherent limitation is its inability to detect novel or unlisted skills, such as a new JavaScript framework, or skills expressed through paraphrase. For this reason, \texttt{extractSkills} is designated as an initial high-precision layer, while more complex, ambiguous, or novel skills are reserved for semantic processing in a later Layer B.

\end{itemize}
\subsection{Performance Optimization and the Caching Sub-System}
To translate the theoretical efficiency of individual heuristics into a practical low-latency system, the pipeline uses an in-memory caching strategy. After an internship listing has passed through validation, cleaning, and enrichment, the fully structured Internship object is placed into a server-side in-memory cache. The data.ts module acts as the sole data-access interface, first checking the cache for requested data before falling back to slower re-processing from the JSON file. This strategy has important implications for the system's performance profile:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Amortized Cost: The entire cost of the ingestion and enrichment pipeline---including file I/O, text processing, and regex analysis---is paid only once per data refresh cycle. This one-time cost is then amortized over potentially hundreds of thousands of read requests from the API layer.

\item Low-Latency Retrieval: By serving pre-processed objects directly from memory, the system is designed to support low response times required for modern interactive search experiences~\cite{buttcher2016information}. This stands in contrast to architectures that perform semantic analysis at query time.

\item Lightweight Operational Profile: This design supports the system's lightweight and Green AI orientation~\cite{schwartz2020green}. It avoids the per-query energy and computational cost that would be incurred by re-computing enrichments or making round-trip calls to external LLM APIs for every user search. The cache invalidation strategy is tied directly to the data refresh cycle, prioritizing efficiency and predictable performance. In summary, this chapter has detailed a tiered data-preparation pipeline aligned with the system's core design principles. By front-loading the computational cost of deterministic cleaning and enrichment and then using an in-memory cache, the preprocessing layer provides a clean, structured, and queryable dataset for the semantic and search components in subsequent sections.

\end{itemize}

\section{Lightweight Semantic Enrichment Pipeline}
The semantic enrichment pipeline is the computational core of the system. It transforms raw, unstructured text into the structured, semantically enriched format defined in the methodology chapter. This section provides a detailed account of the implementation of a high-performance, rule-based extraction engine developed in TypeScript and designed to minimize latency and avoid the operational costs associated with external model inference. The design draws on established principles in Information Extraction (IE) and introduces heuristics tailored to the characteristics of internship listings~\cite{sarawagi2008information, nadeau2007survey}.

\subsection{Pipeline Architecture and Data Flow}
The enrichment pipeline operates on a defined ``clean-enrich-structure'' sequence, a design pattern that ensures each processing stage receives data of progressively higher quality and semantic density. Data arriving from web scrapers or manual JSON uploads first undergoes sanitization to remove noise and normalize surface forms~\cite{chu2016data}. The cleaned text is then enriched with semantic tags, including normalized job titles, extracted skills, parsed salary ranges, and domain categories, using a cascade of deterministic heuristics ordered by computational cost and precision. Finally, the fully structured Internship object is stored in a server-side cache for rapid retrieval. This layered approach is consistent with production-grade IE systems that prioritize efficiency, maintainability, and predictable performance over the resource-intensive characteristics of end-to-end neural architectures~\cite{sarawagi2008information, schwartz2020green}.

\subsection{Pipeline Orchestration}
The enrichment process is orchestrated by a central enrichInternship procedure, which accepts a raw data object and returns a fully structured Internship entity. The orchestration follows a strict topological order, where each function's output serves as the input to subsequent stages. This linear, dependency-managed design simplifies debugging, facilitates unit testing of individual enrichment modules, and reduces the risk that errors in one stage will propagate unpredictably into downstream processes. Figure~\ref{fig:enrichment-lifecycle} illustrates the lifecycle of an individual item as it traverses the enrichment pipeline, from initial ingestion through each processing module to final storage in the structured cache. The diagram highlights the interaction between the main data loop and the specialized enrichment components, emphasizing the sequential dependency chain and the collision-checking mechanism in the identifier generation stage. The top-level enrichment algorithm is presented below.

\begin{algorithmbox}[Internship Ingestion and Enrichment Pipeline]
\begin{verbatim}
procedure EnrichInternship(rawItem)
  title    <- cleanTitle(rawItem.title)
  company  <- cleanCompany(rawItem.company)
  id       <- generateId(title, company)
  desc     <- cleanDescription(rawItem.description)
  salary   <- cleanSalary(rawItem.salary)
  skills   <- extractSkills(desc)
  category <- categorizeJob(title)
  return Internship(id, title, company, desc,
                    salary, skills, category)
end procedure
\end{verbatim}
\end{algorithmbox}

\subsection{Design Principles and Trade-offs}
The architecture embodies several key design principles that collectively define the system's operational characteristics. First, determinism over probabilism ensures that identical inputs always produce identical outputs, a property essential for debugging, auditing, and maintaining user trust. Second, locality of computation keeps all processing within the application's memory space, eliminating network latency and external service dependencies. Third, progressive refinement applies the cheapest, highest-precision methods first, reserving more expensive techniques for cases where simpler methods prove insufficient. These principles directly address the core tension identified in the problem statement: achieving semantic richness without the costs and latencies of LLM-dependent architectures.

\subsection{Deterministic Attribute Normalization}
Normalization ensures that data is consistent, comparable, and queryable regardless of the source platform's original formatting conventions~\cite{jurafsky2023speech}. The normalization layer addresses three distinct challenges: surface-form variance (e.g., inconsistent capitalization, punctuation, and whitespace), structural heterogeneity (e.g., different key names for the same concept across sources), and semantic equivalence (e.g., abbreviations and synonyms). Each normalization module is implemented as a pure function, accepting a potentially malformed string and returning a canonical representation.

\subsection{Text Sanitization Primitives}
Before specialized normalization can occur, all text fields pass through a common sanitization pipeline. The sanitizeText function applies a sequence of transformations designed to eliminate noise while preserving semantic content:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item HTML Entity Resolution: Named entities (e.g., \&amp;, \&lt;, \&\#39;) are converted to their Unicode equivalents using a comprehensive lookup table.

\item Residual Tag Stripping: Any remaining HTML or XML tags are removed using a regular expression that matches balanced angle brackets.

\item Unicode Normalization: Text is normalized to Unicode Normalization Form C (NFC), ensuring that composed and decomposed character sequences are represented consistently.

\item Whitespace Collapsing: All whitespace characters (spaces, tabs, newlines, non-breaking spaces) are collapsed to single spaces, and leading/trailing whitespace is trimmed.

\item Case Folding: Text is converted to lowercase, a standard IR preprocessing step that collapses case-based surface-form variance~\cite{jurafsky2023speech}. This common foundation ensures that all subsequent normalization modules operate on consistently preprocessed input, reducing the complexity of individual specialized functions.

\end{itemize}
\subsection{Stable Identifier Generation}
To maintain referential integrity across ingestion cycles and enable efficient duplicate detection, the system implements a deterministic \texttt{generateId} function. Creating unique, persistent keys for record linkage is important for data quality in large-scale aggregators, where the same logical internship may appear across multiple sources or scrape cycles with minor textual variations. The identifier generation algorithm, shown in Listing~\ref{lst:stable-id}, operates in two phases. First, each string is transformed into a URL-safe form by lowercasing, stripping non-alphanumeric characters while preserving intra-word hyphens, replacing whitespace sequences with single hyphens, collapsing consecutive hyphens, and removing leading or trailing hyphens. Second, the normalized title and company strings are concatenated with a hyphen separator. When a collision is detected during processing, the pipeline appends a numeric suffix, such as \texttt{software-engineer-intern-acme-corp-1}. This strategy prevents distinct listings from being overwritten while maintaining the efficiency of deterministic blocking for common cases.


\begin{lstlisting}[caption={Stable ID generation logic.},label={lst:stable-id}]
function generateId(title: string, company: string): string {
  const cleanTitle = title.toLowerCase()
    .replace(/[^a-z0-9\s-]/g, '')
    .replace(/\s+/g, '-')
    .replace(/--+/g, '-')
    .replace(/^-|-$/g, '');

  const cleanCompany = company.toLowerCase()
    .replace(/[^a-z0-9\s-]/g, '')
    .replace(/\s+/g, '-')
    .replace(/--+/g, '-')
    .replace(/^-|-$/g, '');

  return `${cleanTitle}-${cleanCompany}`;
}
\end{lstlisting}

\subsection{Regex-Based Salary Parsing}
Financial compensation data in internship listings presents a particularly challenging extraction problem. Salary information is often buried within narrative text and expressed in highly variable formats: hourly rates (``\$15-20/hr''), annual salaries (``\$70k-\$90k''), single values (``Up to \$50/hr''), or narrative forms (``competitive salary''). The current \texttt{cleanSalary} module addresses the most common numeric cases through regular expressions that detect dollar-prefixed ranges and single values. If no matching numeric pattern is found, the system returns \texttt{Salary not specified}. This conservative behavior avoids inventing compensation data, but it also means that narrative compensation statements, non-dollar currencies, and monthly or pro-rated amounts remain future extraction work.

\subsection{Location Normalization}
Geographic location information exhibits substantial surface-form variance across sources. The current \texttt{cleanLocation} function applies conservative normalization: it preserves the provided location when present and substitutes a clear placeholder when missing. More advanced abbreviation expansion, remote-work detection, and ISO country normalization are identified as future improvements.

\subsection{Skill Extraction and Semantic Alignment}
As established in the research objectives, the system must identify professional competencies from unstructured job descriptions without the overhead of heavy NLP models. The implemented skill extraction module uses lexicon-based matching as a practical first layer.

\subsection{Lexicon Construction and Maintenance}
The skill lexicon serves as the knowledge base for the extraction module. In the current prototype it is a compact, manually defined list of common skills and tools observed in internship descriptions. This keeps the implementation simple and inspectable. A future ESCO-aligned lexicon could expand this list with canonical labels, aliases, and maintenance rules based on unextracted n-grams in recent listings.

\subsection{Matching Algorithm}
The extractSkills function implements a case-insensitive, whole-word matching algorithm against the curated lexicon. The algorithm processes the job description text through the following stages:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Tokenization and Normalization: The description is tokenized using a whitespace-aware tokenizer that preserves multi-word skill phrases; for example, ``Machine Learning'' is treated as a single candidate. Tokens are lowercased and stripped of trailing punctuation.

\item Phrase Matching: For each lexicon entry (both canonical labels and synonyms), the algorithm scans the normalized token sequence for exact matches. To handle multi-word skills, the algorithm employs a greedy longest-match strategy: it first attempts to match the longest possible phrase at each position before falling back to shorter sub-phrases. This prevents, for example, the word ``learning'' from being extracted when ``Machine Learning'' is present.

\item Contextual Filtering: A post-processing filter removes matches that appear in negated contexts, such as ``no experience with Python required,'' or within section headings that are unlikely to represent actual requirements, such as boilerplate ``About Us'' sections. The filter uses a set of negation cues within a configurable window of tokens before the matched skill.

\item Canonical Mapping: In the current implementation, each matched keyword is converted to a display label by capitalizing the first character. A future ESCO-aligned version should map each synonym to a canonical skill identifier so that filtering, search, and analytics operate on a consistent vocabulary.

\end{itemize}
\subsection{Ranking and Density Control}
A raw list of matched skills, while informative, does not distinguish between a job's core requirements and incidental mentions. A listing that mentions ``Python'' once in a list of 20 other technologies has a different skill profile than one that mentions ``Python'' extensively. To surface the most salient skills while avoiding ``keyword stuffing'' amplification, the system employs a density control mechanism inspired by TF-IDF principles but adapted for the skill extraction domain [17, 4]. The ranking algorithm assigns each extracted skill a composite score based on three factors:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Normalized Frequency: The raw count of the skill's occurrences in the description, divided by the total token count, preventing longer descriptions from dominating.

\item Diversity Bonus: A multiplicative factor that rewards descriptions mentioning a broader range of distinct skills. This directly counteracts keyword stuffing: a description that mentions ``Java'' 50 times but no other technologies receives a lower diversity bonus than one mentioning 10 distinct tools.

\item Position Weighting: Skills appearing earlier in the description (which typically corresponds to the ``Requirements'' or ``Qualifications'' section) receive a higher weight than those appearing in boilerplate footer text. The final skill list presented to users is truncated to a configurable maximum (default: 10 skills), with skills ranked by this composite score. This ensures that the displayed skills represent the core requirements of the role, facilitating both accurate search matching and quick comprehension by browsing users.

\end{itemize}
\subsection{Heuristic Role Categorization}
The final enrichment step maps each internship to a high-level domain category, enabling the faceted filtering that is a core functional requirement of the system. The \texttt{categorizeJob} function evaluates the normalized job title against a hierarchy of professional anchors. This categorization provides immediate value for UI navigation even before more sophisticated semantic mapping is applied.

\subsection{Category Taxonomy Design}
The category taxonomy defines five mutually exclusive, collectively exhaustive top-level domains: Software, Data/AI, Design, Healthcare, and Business. This design reflects the empirical distribution of internships in the corpus and is intentionally flat, using a shallow taxonomy optimized for user navigation rather than an exhaustive ontological hierarchy. Each category is associated with a set of anchor terms that serve as high-precision signals for membership.

\subsection{Priority-Ordered Classification}
The classification algorithm includes several design features intended to enhance robustness. Anchor terms are defined as substrings rather than requiring exact token matches, capturing morphological variations; for example, ``designer'' matches both ``Designer'' and ``Designing.'' The normalization step applies the same sanitization pipeline described earlier, ensuring consistent matching regardless of source formatting. The default fallback to ``Business'' reflects the empirical observation that many unclassifiable listings in the corpus fall within professional-services domains. This categorization supports the discovery mechanisms discussed in retrieval theory by providing a stable and predictable taxonomy browser [2, 11].


\begin{algorithmbox}[Heuristic Role Categorization]
\begin{verbatim}
procedure CategorizeJob(title)
  titleLower <- normalize(title)
  if contains(titleLower, "software", "developer", "engineer")
      return "Software"
  if contains(titleLower, "data", "analyst", "ai", "scientist")
      return "Data/AI"
  if contains(titleLower, "design", "ux", "ui")
      return "Design"
  if contains(titleLower, "marketing")
      return "Marketing"
  if contains(titleLower, "pharmacist", "health", "medical")
      return "Healthcare"
  return "Business"
end procedure
\end{verbatim}
\end{algorithmbox}

\subsection{Caching and Performance Considerations}
To translate the theoretical efficiency of individual enrichment modules into practical, low-latency system performance, the results of the enrichment pipeline are stored in a server-side in-memory cache. This caching strategy is the single most impactful performance optimization in the system, fundamentally shaping its operational profile and cost characteristics.

\subsection{Cache Architecture}
The cache is implemented as a server-side Map<string, Internship> structure, keyed by the stable identifier generated in the relevant section. The data.ts module serves as the sole access interface, implementing a read-through caching pattern: on a cache miss, the module reads the raw data from the static JSON catalog, executes the full enrichment pipeline, stores the result in the cache, and returns the enriched object. Subsequent requests for the same identifier are served directly from memory.

\subsection{Amortized Cost Model}
This architecture embodies an amortized cost model that is central to the system's lightweight operational philosophy. The computational cost of the enrichment pipeline, including file I/O, text sanitization, regex processing, skill extraction, and categorization, is paid once per data refresh cycle. This one-time cost is then amortized over read requests from the API layer. The cost model contrasts with architectures that perform semantic analysis at query time, where each user request incurs the full computational burden [7, 37].

\subsection{Cache Invalidation Strategy}
Cache invalidation is tied directly to the data refresh cycle. When new scrape data is ingested or the enrichment logic is updated, the cache is cleared and repopulated lazily on subsequent requests. This strategy eliminates the complexity of partial invalidation while ensuring that users always receive data processed by the most recent pipeline version. For production deployments with continuous ingestion, a time-to-live (TTL) mechanism can be layered on top, automatically refreshing cached entries after a configurable interval to accommodate incremental data updates.

\subsection{Performance Targets}
With the caching layer in place, the system is designed to support low-latency read requests, a requirement for modern interactive search systems. This implementation aligns with the server-first patterns of Next.js, where server-side caching reduces client-side overhead and improves perceived performance~\cite{riva2025realworld}. This performance profile is intended to run on commodity hardware without specialized infrastructure, directly addressing the lightweight design goal articulated in the problem statement. The contrast with LLM-dependent architectures is instructive: a single LLM API call for semantic enrichment can introduce substantial latency and per-request financial cost, making caching-amortized local processing an important architectural mechanism for sustainable operation at scale.

\subsection{Summary}
This section has presented the lightweight semantic enrichment pipeline, detailing the architecture, algorithms, and design principles used to transform raw, heterogeneous internship listings into structured, semantically enriched entities. The pipeline's tiered and deterministic design supports accurate extraction across salary, skill, and category dimensions while reducing external API dependency. The caching strategy amortizes computational cost across many user requests, supporting responsive and cost-conscious search. Together with the semantic schema and retrieval infrastructure described in this thesis, the enrichment pipeline forms the foundation for a sustainable internship discovery platform.


\section{Storage, Indexing, and Persistence}
This chapter describes the data persistence and retrieval mechanisms that support the internship search platform. It details the hybrid storage strategy that combines local file-based data for the internship catalog with cloud-based relational storage for user interactions.

\subsection{Hybrid Data Storage Architecture}
The system adopts a hybrid approach to data management, balancing the high-speed read requirements of a static catalog with the transactional persistence needed for user-specific features.

\subsection{Static Catalog and Data Normalization}
The primary repository for internship listings is a large-scale \texttt{intern\_data.json} file. To ensure data integrity, the system implements a robust ingestion pipeline:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Data Cleaning: Raw strings are normalized using techniques described in data cleaning literature~\cite{chu2016data}.

\item Stable Identifier Generation: The system generates deterministic IDs to enable effective record linkage and deduplication [8, 14].

\item Type Safety: Ingested objects are transformed into a formal semantic schema~\cite{sarawagi2008information}.

\end{itemize}
\subsection{Relational Persistence (Supabase)}
For authentication and dynamic user state, the system utilizes Supabase, a backend leveraging PostgreSQL. This relational foundation provides the necessary transactional support for features like user authentication, bookmarks, and saved roles, adhering to the principles of reliable data systems.

\subsection{Indexing and Metadata Enrichment}
Beyond simple storage, the system enriches the data to facilitate efficient discovery through category labels, skill tags, and stable identifiers. High-dimensional semantic search remains an extension of this foundation.

\subsection{Heuristic Categorization}
As the source data is often unstructured, the system performs real-time metadata enrichment:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Category Mapping: Roles are classified into domains using keyword-based heuristics.

\item Skill Extraction: Descriptions are parsed against a predefined taxonomy to create a tag-based index [17, 4].

\end{itemize}
\subsection{Performance Optimization}
To handle the overhead of repeated catalog access, the implementation uses in-memory caching for processed records. This avoids re-reading and re-processing the JSON catalog for every request.

\subsection{Retrieval and API Design}
The system's data access layer is exposed via REST endpoints, designed for resilience and scalability.

\subsection{The Internship API}
The API serves as the unified data source, incorporating fail-safe logic to handle malformed input or missing catalog files.

\subsection{Search and Similarity Foundations}
The architecture includes utilities for similarity search. While current filtering relies on category matches, the system is structured to support future vector-based recommendation engines by leveraging Approximate Nearest Neighbor (ANN) indexing techniques~\cite{johnson2019billion}.
