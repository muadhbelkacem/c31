\chapter{System Design and Implementation}

\section{Chapter Introduction}
This chapter describes how the methodology is implemented in the software system. It follows the processing path from data ingestion and preprocessing to semantic enrichment, storage, indexing, caching, and API access. The chapter focuses on implementation mechanisms that are supported by the existing manuscript evidence and avoids introducing unverified components or deployment claims.

\section{Data Collection and Preprocessing}
This chapter details the implementation of the data acquisition, sanitization, and enrichment pipeline, which forms the first computational tier of the system. As established in the methodology chapter, the primary challenge addressed here is the ingestion of raw, heterogeneous internship listings and their transformation into a consistent, structured format. This processed output serves as the foundation on which the semantic enrichment and hybrid retrieval mechanisms are built. The pipeline must be robust against the data noise inherent in web-sourced content [9] and flexible enough to handle high-volume, multi-source inputs [28], while adhering to the lightweight and cost-effective design philosophy central to this thesis [46]. Recent studies highlight that while Large Language Models (LLMs) offer rapid prototyping for such tasks, rule-based systems maintain a superior profile for deterministic behavior and cost-efficiency in specialized domains~\cite{principe2025enhancing}. The chapter begins by detailing the initial ingestion mechanism, then proceeds through deterministic preprocessing, and finally describes the heuristic enrichment strategies that provide immediate, low-cost structure to the data.

\subsection{Data Ingestion Pipeline}
The ingestion pipeline is the system's entry point for all internship data, designed as an asynchronous, non-blocking process to ensure the main application loop remains responsive. Its core function is to safely acquire raw data from the local JSON repository, validate its structural integrity, and parse it into the system's canonical format. This process directly addresses the ``schema-on-read'' challenge common in integrating semi-structured web data, where different sources may use different keys for the same concept [13]. The diagram illustrates the flow from the asynchronous file read through structural validation to the final caching of parsed Internship objects.


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Source Acquisition: The primary static catalog is persisted in \texttt{public/intern\_data.json}. The \texttt{getInternships()} function uses the Node.js \texttt{fs.promises} API for asynchronous file reading. This non-blocking I/O model is necessary for a system that must serve user requests without stalling on file-system access, a fundamental principle in responsive server-side applications. This single-file approach for the core catalog supports simple version control and rapid deployment without the operational overhead of a database for static, read-heavy data.

\item Initial Validation (Layer 0): Before any parsing logic is applied, the system performs structural checks on the raw file content. This pre-validation Layer 0 is a defensive programming strategy in automated data pipelines [9]. It verifies that the file is not empty, confirms that the top-level structure is a JSON array, and checks that essential keys exist in a representative sample of objects. By failing early at this stage, the system prevents corrupted data from propagating into downstream processes such as enrichment and indexing. Records that fail preliminary schema validation are logged with error context and quarantined in a separate log file for administrative review, creating a feedback loop for data-quality monitoring.

\item Structural Parsing: Upon passing validation, the content is parsed into an array of TypeScript Internship interfaces. This parsing is not only a JSON decode; it is an enforced type assertion against the target schema defined in the methodology chapter. TypeScript's compile-time and runtime checks, implemented through custom type guards, ensure that each object conforms to the expected shape. This provides an initial pass at structural normalization and establishes a semantic contract between the raw data and the rest of the application [44]. This formalization ensures that every component, from the regex-based salary parser to the React search card, operates on a shared, unambiguous definition of an Internship.

\end{itemize}

\subsection{Preprocessing and Sanitization}
Raw data obtained from web scraping is inherently noisy and may contain inconsistent formatting, boilerplate text, and presentation artifacts that are irrelevant to the semantic content. Layer A applies a series of deterministic, rule-based sanitization functions. These functions are computationally inexpensive, predictable, and easy to debug, aligning with the goal of maximizing efficiency for high-volume, high-confidence tasks [8].


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Field Normalization: Functions like cleanTitle and cleanLocation perform foundational normalization. The process involves:

\end{itemize}

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Text Normalization: Transforming text into a standardized canonical form by lowercasing all characters, collapsing multiple whitespace characters into a single space, and trimming leading/trailing whitespace. This directly reduces surface-form variance, a critical prerequisite for reliable downstream matching [9].

\item HTML Artifact Stripping: Web-scraped text frequently contains residual HTML entities (e.g., \&amp;, \&lt;) and inline tags. A series of regular expression substitutions are applied to convert common entities to their unicode equivalents and remove any remaining tag structures.

\item Specific Normalizations: For locations, abbreviations are expanded (e.g., ``St.'' to ``Street''), and common variations are standardized (``NYC'' to ``New York''). For titles, irrelevant prefixes like ``Urgent:'' or ``Hot Job:'' are stripped to leave the core semantic title. This step ensures that the text is ready for the tokenization and NLP tasks that follow [36].

\end{itemize}

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Salary Extraction: The cleanSalary function is a prime example of a high-precision, deterministic extraction module that operates with zero inference cost. It follows a ``Select-then-Extract'' paradigm~\cite{liu2024survey}, where high-confidence patterns are first identified to isolate the target text before applying specific parsing rules. It employs a tiered set of regular expressions to parse the highly variable salary information found in free text [44]:

\item Pattern Identification: The first tier identifies the presence of standard patterns, such as an hourly rate (e.g., ``\$15 - \$20 / hr''), an annual salary (e.g., ``\$70k - \$90k''), or a single value (e.g., ``Up to \$50/hr'').

\item Numeric Extraction: Once a pattern is detected, a second tier extracts the numeric entities, stripping non-numeric characters like \$ and k/K, and correctly interpreting the k suffix as a multiplication factor.

\item Structuring and Validation: The cleaned string is then mapped to the \texttt{salary} field in the \texttt{Internship} interface. A heuristic validation filter ensures that entries with missing critical fields are excluded from the final dataset.

\item Description Cleaning: The free-text job description often contains substantial noise as well as important semantic information. The cleanDescription function performs stronger sanitization than basic field normalization. It removes long sequences of newlines or tabs and common boilerplate sentences, such as equal-opportunity-employer statements. The goal is to improve the signal-to-noise ratio for downstream lexical and semantic analysis so that tokenization and vectorization operate on a cleaner representation of job requirements [9, 36].

\end{itemize}
\subsection{Data Enrichment and Categorization}
Following sanitization, the system enriches the listing with derived metadata. These enrichment steps create the structured fields that power the faceted filtering and deduplication described in the system's functional requirements. While simple, these heuristic methods provide a highutility baseline that eliminates the need for more complex processing in the majority of cases [5].

\subsubsection{Stable Identifier Generation and Collision Handling}
To ensure persistent, unique referencing across multiple ingestion cycles and to enable effective duplicate detection, the generateId function creates a deterministic, URL-friendly slug. This process is foundational for the data curation strategy and works as follows:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Slugification: A dedicated helper function converts a given string (e.g., a company name or job title) to lowercase, replaces any sequence of non-alphanumeric characters with a single hyphen, and removes leading/trailing hyphens.

\item Concatenation: The canonical ID is formed by concatenating the slugified title and slugified company name, separated by a hyphen.

\item Deterministic Blocking: This generated ID serves as a blocking key for record linkage [8]. In deduplication, if a newly ingested listing generates an ID that already exists in the catalog, it is a strong signal of duplication. Recent surveys of record linkage in medical and professional informatics confirm that deterministic rules remain a robust foundation for identifying matches in large-scale datasets where persistent identifiers are required~\cite{sariyar2026record}. The system can then skip the record or apply a heuristic to select the canonical record based on completeness or source authority [14]. Deterministic blocking is efficient because it limits pairwise comparisons to the small blocks where a collision occurs. This approach directly addresses the deduplication and canonicalization challenges described earlier and provides an explainable, low-cost strategy for maintaining a clean search index for the end user.

\end{itemize}
\subsubsection{Keyword-Based Categorization}
The categorizeJob function provides an immediate, high-level domain classification by applying a set of keyword-anchored heuristics. This maps the normalized job title to a predefined set of top-level categories, such as Software, Data/AI, Design, Healthcare, and Business, as defined in the internal label space. The function evaluates the job title against a hierarchy of professional anchors. For instance, if the title contains ``Software,'' ``Frontend,'' ``Backend,'' or ``Full Stack,'' it is classified as Software. The evaluation proceeds in priority order from most specific to most general. This rule-based approach is effective for faceted filtering in the user interface [5], providing a stable and predictable taxonomy browser. It also serves as a fallback mechanism for cases where the subsequent Layer B semantic mapping may have low confidence, ensuring that every listing has at least one high-level category for filtering.

\subsubsection{Skill Extraction}
The system's initial layer of skill extraction, implemented in the extractSkills function, uses a dictionary-based approach, also known as gazetteer matching [18, 38]. It matches text against a carefully curated, case-insensitive lexicon of technical skills grounded in the ESCO framework and expanded with common industry synonyms.


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Precision and Efficiency: This method offers high precision for terms present in its lexicon. It identifies terms such as ``Python'' or ``AWS'' when they appear in recognized forms. It is also computationally efficient, requiring only a single pass over the text using standard data structures.

\item Density Control: To mitigate the risk of keyword stuffing and to surface the most relevant skills, the system implements a density-control mechanism. It ranks matched skills not only by presence but also by frequency and by the number of unique other skills mentioned. Recent advancements in granular information extraction from job advertisements suggest that identifying ``salient tokens'' through bi-directional attention can improve extraction quality, a concept this system approximates through frequency-based weighting~\cite{lsbillms2026}. A job description that mentions 20 technologies once each is treated as a broader skill profile than one that mentions ``Java'' repeatedly. This provides a more nuanced signal for subsequent matching and search ranking [44].

\item Limitation and Role in Tiered Strategy: The lexicon's inherent limitation is its inability to detect novel or unlisted skills, such as a new JavaScript framework, or skills expressed through paraphrase. This is a known constraint of dictionary-based NER rather than a problem solved at this layer [38]. For this reason, extractSkills is designated as an initial high-precision layer (Layer A), while more complex, ambiguous, or novel skills are reserved for semantic processing in Layer B.

\end{itemize}
\subsection{Performance Optimization and the Caching Sub-System}
To translate the theoretical efficiency of individual heuristics into a practical low-latency system, the pipeline uses an in-memory caching strategy. After an internship listing has passed through validation, cleaning, and enrichment, the fully structured Internship object is placed into a server-side in-memory cache. The data.ts module acts as the sole data-access interface, first checking the cache for requested data before falling back to slower re-processing from the JSON file. This strategy has important implications for the system's performance profile:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Amortized Cost: The entire cost of the ingestion and enrichment pipeline---including file I/O, text processing, and regex analysis---is paid only once per data refresh cycle. This one-time cost is then amortized over potentially hundreds of thousands of read requests from the API layer.

\item Low-Latency Retrieval: By serving pre-processed objects directly from memory, the system is designed to support low response times required for modern interactive search experiences [7]. This stands in contrast to architectures that perform semantic analysis at query time.

\item Lightweight Operational Profile: This design supports the system's lightweight and Green AI orientation [46]. It avoids the per-query energy and computational cost that would be incurred by re-computing enrichments or making round-trip calls to external LLM APIs for every user search. The cache invalidation strategy is tied directly to the data refresh cycle, prioritizing efficiency and predictable performance. In summary, this chapter has detailed a tiered data-preparation pipeline aligned with the system's core design principles. By front-loading the computational cost of deterministic cleaning and enrichment and then using an in-memory cache, the preprocessing layer provides a clean, structured, and queryable dataset for the semantic and search components in subsequent sections.

\section{Lightweight Semantic Enrichment Pipeline}
The semantic enrichment pipeline is the computational core of the system. It transforms raw, unstructured text into the structured, semantically enriched format defined in the methodology chapter. This section provides a detailed account of the implementation of a high-performance, rule-based extraction engine developed in TypeScript and designed to minimize latency and avoid the operational costs associated with external model inference. The design draws on established principles in Information Extraction (IE) and introduces heuristics tailored to the characteristics of internship listings [44, 18].

\subsection{Pipeline Architecture and Data Flow}
The enrichment pipeline operates on a defined ``clean-enrich-structure'' sequence, a design pattern that ensures each processing stage receives data of progressively higher quality and semantic density. Data arriving from web scrapers or manual JSON uploads first undergoes sanitization to remove noise and normalize surface forms [9]. The cleaned text is then enriched with semantic tags, including normalized job titles, extracted skills, parsed salary ranges, and domain categories, using a cascade of deterministic heuristics ordered by computational cost and precision. Finally, the fully structured Internship object is stored in a server-side cache for rapid retrieval. This layered approach is consistent with production-grade IE systems that prioritize efficiency, maintainability, and predictable performance over the resource-intensive characteristics of end-to-end neural architectures [5, 37].

\subsubsection{Pipeline Orchestration}
The enrichment process is orchestrated by a central enrichInternship procedure, which accepts a raw data object and returns a fully structured Internship entity. The orchestration follows a strict topological order, where each function's output serves as the input to subsequent stages. This linear, dependency-managed design simplifies debugging, facilitates unit testing of individual enrichment modules, and reduces the risk that errors in one stage will propagate unpredictably into downstream processes. Figure~\ref{fig:enrichment-lifecycle} illustrates the lifecycle of an individual item as it traverses the enrichment pipeline, from initial ingestion through each processing module to final storage in the structured cache. The diagram highlights the interaction between the main data loop and the specialized enrichment components, emphasizing the sequential dependency chain and the collision-checking mechanism in the identifier generation stage. \begin{algorithmbox}[Internship Ingestion and Enrichment Pipeline]
\begin{verbatim}
procedure EnrichInternship(rawItem)
  title    <- cleanTitle(rawItem.title)
  company  <- cleanCompany(rawItem.company)
  id       <- generateId(title, company)
  desc     <- cleanDescription(rawItem.description)
  salary   <- cleanSalary(rawItem.salary)
  skills   <- extractSkills(desc)
  category <- categorizeJob(title)
  return Internship(id, title, company, desc,
                    salary, skills, category)
end procedure
\end{verbatim}
\end{algorithmbox}

\subsubsection{Design Principles and Trade-offs}
The architecture embodies several key design principles that collectively define the system's operational characteristics. First, determinism over probabilism ensures that identical inputs always produce identical outputs, a property essential for debugging, auditing, and maintaining user trust. Second, locality of computation keeps all processing within the application's memory space, eliminating network latency and external service dependencies. Third, progressive refinement applies the cheapest, highest-precision methods first, reserving more expensive techniques for cases where simpler methods prove insufficient. These principles directly address the core tension identified in the problem statement: achieving semantic richness without the costs and latencies of LLM-dependent architectures.

\subsection{Deterministic Attribute Normalization}
Normalization ensures that data is consistent, comparable, and queryable regardless of the source platform's original formatting conventions [36]. The normalization layer addresses three distinct challenges: surface-form variance (e.g., inconsistent capitalization, punctuation, and whitespace), structural heterogeneity (e.g., different key names for the same concept across sources), and semantic equivalence (e.g., abbreviations and synonyms). Each normalization module is implemented as a pure function, accepting a potentially malformed string and returning a canonical representation.

\subsubsection{Text Sanitization Primitives}
Before specialized normalization can occur, all text fields pass through a common sanitization pipeline. The sanitizeText function applies a sequence of transformations designed to eliminate noise while preserving semantic content:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item HTML Entity Resolution: Named entities (e.g., \&amp;, \&lt;, \&\#39;) are converted to their Unicode equivalents using a comprehensive lookup table.

\item Residual Tag Stripping: Any remaining HTML or XML tags are removed using a regular expression that matches balanced angle brackets.

\item Unicode Normalization: Text is normalized to Unicode Normalization Form C (NFC), ensuring that composed and decomposed character sequences are represented consistently.

\item Whitespace Collapsing: All whitespace characters (spaces, tabs, newlines, non-breaking spaces) are collapsed to single spaces, and leading/trailing whitespace is trimmed.

\item Case Folding: Text is converted to lowercase, a standard IR preprocessing step that collapses case-based surface-form variance [36]. This common foundation ensures that all subsequent normalization modules operate on consistently preprocessed input, reducing the complexity of individual specialized functions.

\end{itemize}
\subsubsection{Stable Identifier Generation}
To maintain referential integrity across ingestion cycles and enable efficient duplicate detection, the system implements a deterministic generateId function. Creating unique, persistent keys for record linkage is important for data quality in large-scale aggregators, where the same logical internship may appear across multiple sources or scrape cycles with minor textual variations [8, 14]. The identifier generation algorithm, shown in Listing~\ref{lst:stable-id}, operates in two phases. First, a slugify helper transforms arbitrary strings into URL-safe, normalized forms by lowercasing, stripping non-alphanumeric characters while preserving intra-word hyphens, and replacing whitespace sequences with single hyphens. Second, the slugified title and company name are concatenated with a hyphen separator, forming a composite key that is both human-readable and machine-friendly. The slugify function trims input, collapses consecutive hyphens, and strips leading and trailing hyphens from the final result. The at infix separator between the title and company slugs disambiguates cases where the boundary might otherwise be ambiguous, such as distinguishing ``Data Analyst at Data Corp'' from ``Data at Analyst Data Corp.'' This generated ID serves multiple architectural roles. As a primary key, it uniquely identifies each internship within the system. As a blocking key for deduplication, it groups records that share identical normalized representations, limiting pairwise fuzzy comparison to small, manageable blocks [8]. When a collision is detected, the pipeline appends a disambiguating numeric suffix, such as software-engineer-intern-at-acme-corp-1. A metadata field, collisionResolved, is set to true on such records, flagging them for potential manual review. This strategy prevents distinct listings from being overwritten while maintaining the efficiency of deterministic blocking for common cases.


\begin{lstlisting}[caption={Stable ID generation logic.},label={lst:stable-id}]
function generateId(title: string, company: string): string {
  const cleanTitle = title.toLowerCase()
    .replace(/[^a-z0-9\s-]/g, '')
    .replace(/\s+/g, '-')
    .replace(/--+/g, '-')
    .replace(/^-|-$/g, '');

  const cleanCompany = company.toLowerCase()
    .replace(/[^a-z0-9\s-]/g, '')
    .replace(/\s+/g, '-')
    .replace(/--+/g, '-')
    .replace(/^-|-$/g, '');

  return `${cleanTitle}-${cleanCompany}`;
}
\end{lstlisting}

\subsubsection{Regex-Based Salary Parsing}
Financial compensation data in internship listings presents a particularly challenging extraction problem. Salary information is often buried within narrative text and expressed in highly variable formats: hourly rates (``\$15-20/hr''), annual salaries (``\$70k-\$90k''), single values (``Up to \$50/hr''), or narrative forms (``competitive salary''). The parseSalary module addresses this variability through a tiered regex strategy, employing a cascade of increasingly specific patterns that attempt to extract structured numeric ranges from free-text input [44]. Tier 1: Range Patterns. The first tier attempts to match the most information-rich format---explicit numeric ranges. Patterns are compiled for common currency prefixes (\$, USD, EUR), optional magnitude suffixes (k, K for thousands), and per-unit qualifiers (/hr, /hour, per hour, /yr, /year, per year, annually). The extraction logic handles both space-separated and hyphen-separated range delimiters, as well as the common ``k'' suffix convention where ``\$70k'' represents \$70,000. Tier 2: Single-Value Patterns. If no range is detected, the second tier matches single values, which may represent either a minimum (``From \$20/hr'') or a maximum (``Up to \$50/hr''). Contextual keywords (from, starting at, up to, maximum) are used to determine the salary range to be extracted. Tier 3: Narrative Fallback. The final tier applies lightweight heuristics to detect nonnumeric salary indicators. Phrases like ``competitive,'' ``commensurate with experience,'' ``unpaid,'' and ``stipend provided'' are mapped to structured boolean flags (salaryCompetitive, salaryUnpaid) that enable faceted filtering even in the absence of precise figures. Validation and Normalization. All extracted numeric values pass through a validation filter that enforces domain-specific plausibility constraints. Hourly rates must fall within \$0- \$500, annual salaries within \$0-\$1,000,000. Values outside these bounds are discarded and logged for review. Extracted ranges are normalized to a common unit (annual salary equivalent) to enable cross-listing comparison, using a standard conversion factor of 2,080 working hours per year for full-time positions and a configurable factor for part-time roles. This tiered approach achieves high precision on structured salary expressions while gracefully degrading to partial or boolean information for narrative forms. The modular design also facilitates incremental improvement: new patterns can be added to any tier without modifying the overall extraction logic.

\subsubsection{Location Normalization}
Geographic location information exhibits substantial surface-form variance across sources. The cleanLocation function normalizes location strings through a sequence of transformations: abbreviation expansion (e.g., ``St.'' to ``Street'', ``NYC'' to ``New York''), removal of redundant qualifiers (e.g., ``Remote --'' prefix when a separate remote boolean field captures this information), and standardization of country names to ISO 3166-1 codes where possible. The normalized location is stored alongside the raw source string, preserving provenance while enabling reliable geographic filtering.

\subsection{Skill Extraction and Semantic Alignment}
As established in the research objectives, the system must identify professional competencies from unstructured job descriptions without the overhead of heavy NLP models. The skill extraction module implements a hybrid approach that combines the precision and efficiency of lexicon-based matching with a novel density-ranking heuristic that surfaces the most salient skills for each listing.

\subsubsection{Lexicon Construction and Maintenance}
The skill lexicon serves as the knowledge base for the extraction module. Its construction follows a methodology designed to maximize coverage while maintaining precision. Canonical Skill Selection: The lexicon's canonical skill labels are grounded in the ESCO Skills and Competences pillar, ensuring interoperability with the broader European labor-market taxonomy framework. From the full ESCO skill hierarchy, approximately 800 skills relevant to the internship domain were selected, spanning technical competencies, methodological competencies, and transferable skills. Synonym Expansion: For each canonical skill, a set of recognized synonyms and aliases is curated through analysis of the 327-listing corpus. Common variations include abbreviations, version-specific references, vendor-specific terminology, and common shortened forms such as ML for Machine Learning. This synonym expansion is necessary for bridging the vocabulary gap between employer terminology and canonical skill labels [17]. Lexicon Maintenance: The technology landscape evolves rapidly, with new frameworks and tools emerging continuously. The lexicon is designed for periodic maintenance through a semi-automated pipeline: frequency analysis of unextracted n-grams in recent listings surfaces candidate new skills, which are then reviewed by a domain expert for inclusion. This approach balances the need for currency with the quality assurance of expert curation.

\subsubsection{Matching Algorithm}
The extractSkills function implements a case-insensitive, whole-word matching algorithm against the curated lexicon. The algorithm processes the job description text through the following stages:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Tokenization and Normalization: The description is tokenized using a whitespace-aware tokenizer that preserves multi-word skill phrases; for example, ``Machine Learning'' is treated as a single candidate. Tokens are lowercased and stripped of trailing punctuation.

\item Phrase Matching: For each lexicon entry (both canonical labels and synonyms), the algorithm scans the normalized token sequence for exact matches. To handle multi-word skills, the algorithm employs a greedy longest-match strategy: it first attempts to match the longest possible phrase at each position before falling back to shorter sub-phrases. This prevents, for example, the word ``learning'' from being extracted when ``Machine Learning'' is present.

\item Contextual Filtering: A post-processing filter removes matches that appear in negated contexts, such as ``no experience with Python required,'' or within section headings that are unlikely to represent actual requirements, such as boilerplate ``About Us'' sections. The filter uses a set of negation cues within a configurable window of tokens before the matched skill.

\item Canonical Mapping: Each matched synonym is mapped to its canonical ESCO-aligned label, ensuring that downstream processing (filtering, search, analytics) operates on a consistent vocabulary. Dictionary-based methods provide a high-precision baseline for entity recognition in specialized domains, where the vocabulary of relevant entities is relatively stable and well-documented [38]. The primary limitation---inability to detect novel or unlisted skills---is addressed through the periodic lexicon maintenance process and, in future work, through the integration of contextual embedding-based extraction as a secondary tier for low-confidence cases.

\end{itemize}
\subsubsection{Ranking and Density Control}
A raw list of matched skills, while informative, does not distinguish between a job's core requirements and incidental mentions. A listing that mentions ``Python'' once in a list of 20 other technologies has a different skill profile than one that mentions ``Python'' extensively. To surface the most salient skills while avoiding ``keyword stuffing'' amplification, the system employs a density control mechanism inspired by TF-IDF principles but adapted for the skill extraction domain [17, 4]. The ranking algorithm assigns each extracted skill a composite score based on three factors:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Normalized Frequency: The raw count of the skill's occurrences in the description, divided by the total token count, preventing longer descriptions from dominating.

\item Diversity Bonus: A multiplicative factor that rewards descriptions mentioning a broader range of distinct skills. This directly counteracts keyword stuffing: a description that mentions ``Java'' 50 times but no other technologies receives a lower diversity bonus than one mentioning 10 distinct tools.

\item Position Weighting: Skills appearing earlier in the description (which typically corresponds to the ``Requirements'' or ``Qualifications'' section) receive a higher weight than those appearing in boilerplate footer text. The final skill list presented to users is truncated to a configurable maximum (default: 10 skills), with skills ranked by this composite score. This ensures that the displayed skills represent the core requirements of the role, facilitating both accurate search matching and quick comprehension by browsing users.

\end{itemize}
\subsection{Heuristic Role Categorization}
The final enrichment step maps each internship to a high-level domain category, enabling the faceted filtering that is a core functional requirement of the system. The categorizeJob function evaluates the (now normalized) job title against a hierarchy of professional ``anchors'' [2, 11]. This categorization serves dual purposes: it provides immediate value for UI navigation even before more sophisticated semantic mapping is applied, and it serves as a fallback classification for cases where embedding-based mapping (Layer B) has low confidence.

\subsubsection{Category Taxonomy Design}
The category taxonomy defines five mutually exclusive, collectively exhaustive top-level domains: Software, Data/AI, Design, Healthcare, and Business. This design reflects the empirical distribution of internships in the corpus and is intentionally flat, using a shallow taxonomy optimized for user navigation rather than an exhaustive ontological hierarchy. Each category is associated with a set of anchor terms that serve as high-precision signals for membership.

\subsubsection{Priority-Ordered Classification}
The classification algorithm includes several design features intended to enhance robustness. Anchor terms are defined as substrings rather than requiring exact token matches, capturing morphological variations; for example, ``designer'' matches both ``Designer'' and ``Designing.'' The normalization step applies the same sanitization pipeline described earlier, ensuring consistent matching regardless of source formatting. The default fallback to ``Business'' reflects the empirical observation that many unclassifiable listings in the corpus fall within professional-services domains. This categorization supports the discovery mechanisms discussed in retrieval theory by providing a stable and predictable taxonomy browser [2, 11].


\begin{algorithmbox}[Heuristic Role Categorization]
\begin{verbatim}
procedure CategorizeJob(title)
  titleLower <- normalize(title)
  if contains(titleLower, "software", "developer", "engineer")
      return "Software"
  if contains(titleLower, "data", "analyst", "ai", "scientist")
      return "Data/AI"
  if contains(titleLower, "design", "ux", "ui")
      return "Design"
  if contains(titleLower, "marketing")
      return "Marketing"
  if contains(titleLower, "pharmacist", "health", "medical")
      return "Healthcare"
  return "Business"
end procedure
\end{verbatim}
\end{algorithmbox}

\subsection{Caching and Performance Considerations}
To translate the theoretical efficiency of individual enrichment modules into practical, low-latency system performance, the results of the enrichment pipeline are stored in a server-side in-memory cache. This caching strategy is the single most impactful performance optimization in the system, fundamentally shaping its operational profile and cost characteristics.

\subsubsection{Cache Architecture}
The cache is implemented as a server-side Map<string, Internship> structure, keyed by the stable identifier generated in the relevant section. The data.ts module serves as the sole access interface, implementing a read-through caching pattern: on a cache miss, the module reads the raw data from the static JSON catalog, executes the full enrichment pipeline, stores the result in the cache, and returns the enriched object. Subsequent requests for the same identifier are served directly from memory.

\subsubsection{Amortized Cost Model}
This architecture embodies an amortized cost model that is central to the system's lightweight operational philosophy. The computational cost of the enrichment pipeline, including file I/O, text sanitization, regex processing, skill extraction, and categorization, is paid once per data refresh cycle. This one-time cost is then amortized over read requests from the API layer. The cost model contrasts with architectures that perform semantic analysis at query time, where each user request incurs the full computational burden [7, 37].

\subsubsection{Cache Invalidation Strategy}
Cache invalidation is tied directly to the data refresh cycle. When new scrape data is ingested or the enrichment logic is updated, the cache is cleared and repopulated lazily on subsequent requests. This strategy eliminates the complexity of partial invalidation while ensuring that users always receive data processed by the most recent pipeline version. For production deployments with continuous ingestion, a time-to-live (TTL) mechanism can be layered on top, automatically refreshing cached entries after a configurable interval to accommodate incremental data updates.

\subsubsection{Performance Targets}
With the caching layer in place, the system is designed to support low-latency read requests, a requirement for modern interactive search systems [7]. This implementation aligns with the "server-first" patterns of Next.js 14/15, where server-side caching reduces client-side overhead and improves perceived performance [riva2025realworld]. This performance profile is intended to run on commodity hardware without specialized infrastructure, directly addressing the lightweight design goal articulated in the problem statement. The contrast with LLM-dependent architectures is instructive: a single LLM API call for semantic enrichment can introduce substantial latency and per-request financial cost, making caching-amortized local processing an important architectural mechanism for sustainable operation at scale.

\subsection{Summary}
This section has presented the lightweight semantic enrichment pipeline, detailing the architecture, algorithms, and design principles used to transform raw, heterogeneous internship listings into structured, semantically enriched entities. The pipeline's tiered and deterministic design supports accurate extraction across salary, skill, and category dimensions while reducing external API dependency. The caching strategy amortizes computational cost across many user requests, supporting responsive and cost-conscious search. Together with the semantic schema and retrieval infrastructure described in this thesis, the enrichment pipeline forms the foundation for a sustainable internship discovery platform.
