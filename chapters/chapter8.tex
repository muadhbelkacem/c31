\chapter{Lightweight Semantic Enrichment Pipeline}

The semantic enrichment pipeline constitutes the computational heart of the system, responsible for transforming raw, unstructured text into the structured, semantically rich format defined in Chapter~7. This chapter provides a comprehensive account of the implementation of a high-performance, rule-based extraction engine developed in TypeScript, specifically engineered to minimize latency and eliminate the operational costs associated with external model inference. The design draws upon and extends established principles in Information Extraction (IE), while introducing novel heuristics tailored to the unique characteristics of internship listings \cite{sarawagi2008information, grishman2015information}.

%===========================================
\section{Pipeline Architecture and Data Flow}
%===========================================

The enrichment pipeline operates on a rigorously defined ``clean-enrich-structure'' sequence, a design pattern that ensures each processing stage receives data of progressively higher quality and semantic density. Data arriving from web scrapers or manual JSON uploads first undergoes comprehensive sanitization to remove noise and normalize surface forms \cite{chu2016data}. The cleansed text is then enriched with semantic tags—including normalized job titles, extracted skills, parsed salary ranges, and domain categories—using a cascade of deterministic heuristics ordered by computational cost and precision. Finally, the fully structured \texttt{Internship} object is stored in a server-side cache for rapid retrieval. This layered approach is consistent with production-grade IE systems that prioritize efficiency, maintainability, and predictable performance over the opaque, resource-intensive characteristics of end-to-end neural architectures \cite{boselli2018classifying, menghani2023efficient}.

\subsection{Pipeline Orchestration}

The enrichment process is orchestrated by a central \texttt{enrichInternship} procedure, which accepts a raw data object and returns a fully structured \texttt{Internship} entity. The orchestration follows a strict topological order, where each function's output serves as the input to subsequent stages. This linear, dependency-managed design simplifies debugging, facilitates unit testing of individual enrichment modules, and ensures that errors in one stage do not cascade unpredictably into downstream processes.

\begin{algorithm}[H]

\label{alg:enrichment_pipeline}
\begin{algorithmic}[1]
\Procedure{EnrichInternship}{rawItem}
    \State $title \gets \text{cleanTitle}(rawItem.title)$
    \State $company \gets \text{cleanCompany}(rawItem.company)$

\EndProcedure
\end{algorithmic}

\subsection{Design Principles and Trade-offs}

The architecture embodies several key design principles that collectively define the system's operational characteristics. First, \textbf{determinism over probabilism} ensures that identical inputs always produce identical outputs, a property essential for debugging, auditing, and maintaining user trust. Second, \textbf{locality of computation} keeps all processing within the application's memory space, eliminating network latency and external service dependencies. Third, \textbf{progressive refinement} applies the cheapest, highest-precision methods first, reserving more expensive techniques for cases where simpler methods prove insufficient. These principles directly address the core tension identified in the problem statement: achieving semantic richness without the costs and latencies of LLM-dependent architectures.

%===========================================
\section{Deterministic Attribute Normalization}
%===========================================

Normalization ensures that data is consistent, comparable, and queryable regardless of the source platform's original formatting conventions \cite{manning2008introduction}. The normalization layer addresses three distinct challenges: surface-form variance (e.g., inconsistent capitalization, punctuation, and whitespace), structural heterogeneity (e.g., different key names for the same concept across sources), and semantic equivalence (e.g., abbreviations and synonyms). Each normalization module is implemented as a pure function, accepting a potentially malformed string and returning a canonical representation.

\subsection{Text Sanitization Primitives}

Before specialized normalization can occur, all text fields pass through a common sanitization pipeline. The \texttt{sanitizeText} function applies a sequence of transformations designed to eliminate noise while preserving semantic content:

\begin{enumerate}
    \item \textbf{HTML Entity Resolution}: Named entities (e.g., \texttt{\&amp;}, \texttt{\&lt;}, \texttt{\&\#39;}) are converted to their Unicode equivalents using a comprehensive lookup table.
    \item \textbf{Residual Tag Stripping}: Any remaining HTML or XML tags are removed using a regular expression that matches balanced angle brackets.
    \item \textbf{Unicode Normalization}: Text is normalized to Unicode Normalization Form C (NFC), ensuring that composed and decomposed character sequences are represented consistently.
    \item \textbf{Whitespace Collapsing}: All whitespace characters (spaces, tabs, newlines, non-breaking spaces) are collapsed to single spaces, and leading/trailing whitespace is trimmed.
    \item \textbf{Case Folding}: Text is converted to lowercase, a standard IR preprocessing step that collapses case-based surface-form variance \cite{manning2008introduction}.
\end{enumerate}

This common foundation ensures that all subsequent normalization modules operate on consistently preprocessed input, reducing the complexity of individual specialized functions.

\subsection{Stable Identifier Generation}

To maintain referential integrity across ingestion cycles and enable efficient duplicate detection, the system implements a deterministic \texttt{generateId} function. This process of creating unique, persistent keys for record linkage is critical for data quality in large-scale aggregators, where the same logical internship may appear across multiple sources or scrape cycles with minor textual variations \cite{christen2012data, elmagarmid2007duplicate}.

The identifier generation algorithm, shown in Listing~\ref{lst:stable_id}, operates in two phases. First, a \texttt{slugify} helper transforms arbitrary strings into URL-safe, normalized forms by lowercasing, stripping non-alphanumeric characters (preserving intra-word hyphens), and replacing whitespace sequences with single hyphens. Second, the slugified title and company name are concatenated with a hyphen separator, forming a composite key that is both human-readable and machine-friendly.

\begin{lstlisting}[language=TypeScript, caption=Stable ID Generation Logic, label=lst:stable_id]
function generateId(title: string, company: string): string {
    const slugify = (str: string): string => str
        .toLowerCase()
        .trim()
        .replace(/[^a-z0-9\s-]/g, '')
        .replace(/[\s-]+/g, '-')
        .replace(/^-+|-+$/g, '');

    const titleSlug = slugify(title);
    const companySlug = slugify(company);

    return `${titleSlug}-at-${companySlug}`;
}
\end{lstlisting}

The \texttt{slugify} function incorporates several defensive measures: it trims input to remove leading and trailing whitespace, collapses consecutive hyphens that may result from the replacement of special characters adjacent to spaces, and strips leading and trailing hyphens from the final result. The \texttt{at} infix separator between the title and company slugs disambiguates cases where the boundary might otherwise be ambiguous (e.g., distinguishing ``Data Analyst at Data Corp'' from ``Data at Analyst Data Corp'').

This generated ID serves multiple architectural roles. As a \textbf{primary key}, it uniquely identifies each internship within the system, enabling stable references from user bookmarks and external links. As a \textbf{blocking key} for deduplication, it groups records that share identical normalized representations, limiting the computationally expensive task of pairwise fuzzy comparison to small, manageable blocks \cite{christen2012data}. As a \textbf{human-readable slug}, it provides transparency to developers and power users who can decode the canonical identity of a listing directly from its URL.

\paragraph{Collision Handling:} While the deterministic ID dramatically reduces the search space for duplicates, collisions may still occur when two genuinely distinct internships normalize to the same slug (e.g., two different ``Software Engineer Intern'' positions at the same company in different departments). The system maintains a \texttt{seenIds} set during ingestion. When a collision is detected, the pipeline appends a disambiguating numeric suffix (e.g., \texttt{software-engineer-intern-at-acme-corp-2}). A metadata field \texttt{collisionResolved} is set to \texttt{true} on such records, flagging them for potential manual review. This graceful degradation strategy ensures that the pipeline never silently overwrites distinct listings while maintaining the efficiency of deterministic blocking for the common case.

\subsection{Regex-Based Salary Parsing}

Financial compensation data in internship listings presents a particularly challenging extraction problem. Salary information is often buried within narrative text and expressed in highly variable formats: hourly rates (``\$15-20/hr''), annual salaries (``\$70k-\$90k''), single values (``Up to \$50/hr''), or narrative forms (``competitive salary''). The \texttt{parseSalary} module addresses this variability through a tiered regex strategy, employing a cascade of increasingly specific patterns that attempt to extract structured numeric ranges from free-text input \cite{sarawagi2008information}.

\paragraph{Tier 1: Range Patterns.} The first tier attempts to match the most information-rich format—explicit numeric ranges. Patterns are compiled for common currency prefixes (\$, USD, EUR), optional magnitude suffixes (k, K for thousands), and per-unit qualifiers (/hr, /hour, per hour, /yr, /year, per year, annually). The extraction logic handles both space-separated and hyphen-separated range delimiters, as well as the common ``k'' suffix convention where ``\$70k'' represents \$70,000.

\paragraph{Tier 2: Single-Value Patterns.} If no range is detected, the second tier matches single values, which may represent either a minimum (``From \$20/hr'') or a maximum (``Up to \$50/hr''). Contextual keywords (from, starting at, up to, maximum) are used to determine whether the extracted value should populate \texttt{salaryMin}, \texttt{salaryMax}, or both (in the case of an exact figure).

\paragraph{Tier 3: Narrative Fallback.} The final tier applies lightweight heuristics to detect non-numeric salary indicators. Phrases like ``competitive,'' ``commensurate with experience,'' ``unpaid,'' and ``stipend provided'' are mapped to structured boolean flags (\texttt{salaryCompetitive}, \texttt{salaryUnpaid}) that enable faceted filtering even in the absence of precise figures.

\paragraph{Validation and Normalization.} All extracted numeric values pass through a validation filter that enforces domain-specific plausibility constraints. Hourly rates must fall within \$0-\$500, annual salaries within \$0-\$1,000,000. Values outside these bounds are discarded and logged for review. Extracted ranges are normalized to a common unit (annual salary equivalent) to enable cross-listing comparison, using a standard conversion factor of 2,080 working hours per year for full-time positions and a configurable factor for part-time roles.

This tiered approach achieves high precision on structured salary expressions while gracefully degrading to partial or boolean information for narrative forms. The modular design also facilitates incremental improvement: new patterns can be added to any tier without modifying the overall extraction logic.

\subsection{Location Normalization}

Geographic location information exhibits substantial surface-form variance across sources. The \texttt{cleanLocation} function normalizes location strings through a sequence of transformations: abbreviation expansion (e.g., ``St.'' to ``Street'', ``NYC'' to ``New York''), removal of redundant qualifiers (e.g., ``Remote --'' prefix when a separate \texttt{remote} boolean field captures this information), and standardization of country names to ISO 3166-1 codes where possible. The normalized location is stored alongside the raw source string, preserving provenance while enabling reliable geographic filtering.

\section{Skill Extraction and Semantic Alignment}
%===========================================

As established in the research objectives, the system must identify professional competencies from unstructured job descriptions without the overhead of heavy NLP models. The skill extraction module implements a hybrid approach that combines the precision and efficiency of lexicon-based matching with a novel density-ranking heuristic that surfaces the most salient skills for each listing.

\subsection{Lexicon Construction and Maintenance}

The skill lexicon serves as the knowledge base for the extraction module. Its construction follows a principled methodology designed to maximize coverage while maintaining precision:

\paragraph{Canonical Skill Selection:} The lexicon's canonical skill labels are grounded in the ESCO Skills and Competences pillar, ensuring interoperability with the broader European labor market taxonomy framework. From the full ESCO skill hierarchy, we selected approximately 800 skills relevant to the internship domain, spanning technical competencies (programming languages, frameworks, tools), methodological competencies (agile, design thinking), and transferable skills (communication, teamwork).

\paragraph{Synonym Expansion:} For each canonical skill, a set of recognized synonyms and aliases is curated through analysis of our 17,500-listing corpus. Common variations include abbreviations (JavaScript $\rightarrow$ JS, ECMAScript), version-specific references (Python $\rightarrow$ Python 3, Py), vendor-specific terminology (SQL $\rightarrow$ MySQL, PostgreSQL, T-SQL), and colloquial forms (Machine Learning $\rightarrow$ ML, Deep Learning, Statistical Learning). This synonym expansion is critical for bridging the ``vocabulary gap'' between employer terminology and canonical skill labels \cite{giabelli2021skills}.

\paragraph{Lexicon Maintenance:} The technology landscape evolves rapidly, with new frameworks and tools emerging continuously. The lexicon is designed for periodic maintenance through a semi-automated pipeline: frequency analysis of unextracted $n$-grams in recent listings surfaces candidate new skills, which are then reviewed by a domain expert for inclusion. This approach balances the need for currency with the quality assurance of expert curation.

\subsection{Matching Algorithm}

The \texttt{extractSkills} function implements a case-insensitive, whole-word matching algorithm against the curated lexicon. The algorithm processes the job description text through the following stages:

\begin{enumerate}
    \item \textbf{Tokenization and Normalization:} The description is tokenized using a whitespace-aware tokenizer that preserves multi-word skill phrases (e.g., ``Machine Learning'' is treated as a single candidate). Tokens are lowercased and stripped of trailing punctuation.
    \item \textbf{Phrase Matching:} For each lexicon entry (both canonical labels and synonyms), the algorithm scans the normalized token sequence for exact matches. To handle multi-word skills, the algorithm employs a greedy longest-match strategy: it first attempts to match the longest possible phrase at each position before falling back to shorter sub-phrases. This prevents, for example, the word ``learning'' from being extracted when ``Machine Learning'' is present.
    \item \textbf{Contextual Filtering:} A post-processing filter removes matches that appear in negated contexts (e.g., ``no experience with Python required'') or within section headings that are unlikely to represent actual requirements (e.g., boilerplate ``About Us'' sections). The filter uses a set of negation cues (``no,'' ``not,'' ``don't,'' ``doesn't'') within a configurable window of tokens before the matched skill.
    \item \textbf{Canonical Mapping:} Each matched synonym is mapped to its canonical ESCO-aligned label, ensuring that downstream processing (filtering, search, analytics) operates on a consistent vocabulary.
\end{enumerate}

Dictionary-based methods provide a high-precision baseline for entity recognition in specialized domains, where the vocabulary of relevant entities is relatively stable and well-documented \cite{nadeau2007survey}. The primary limitation—inability to detect novel or unlisted skills—is addressed through the periodic lexicon maintenance process and, in future work, through the integration of contextual embedding-based extraction as a secondary tier for low-confidence cases.

\subsection{Ranking and Density Control}

A raw list of matched skills, while informative, does not distinguish between a job's core requirements and incidental mentions. A listing that mentions ``Python'' once in a list of 20 other technologies has a different skill profile than one that mentions ``Python'' extensively. To surface the most salient skills while avoiding ``keyword stuffing'' amplification, the system employs a density control mechanism inspired by TF-IDF principles but adapted for the skill extraction domain \cite{giabelli2021skills, bhola2020retrieving}.

The ranking algorithm assigns each extracted skill a composite score based on three factors:

\begin{enumerate}
    \item \textbf{Normalized Frequency:} The raw count of the skill's occurrences in the description, divided by the total token count, preventing longer descriptions from dominating.
    \item \textbf{Diversity Bonus:} A multiplicative factor that rewards descriptions mentioning a broader range of distinct skills. This directly counteracts keyword stuffing: a description that mentions ``Java'' 50 times but no other technologies receives a lower diversity bonus than one mentioning 10 distinct tools.
    \item \textbf{Position Weighting:} Skills appearing earlier in the description (which typically corresponds to the ``Requirements'' or ``Qualifications'' section) receive a higher weight than those appearing in boilerplate footer text.
\end{enumerate}

The final skill list presented to users is truncated to a configurable maximum (default: 10 skills), with skills ranked by this composite score. This ensures that the displayed skills represent the core requirements of the role, facilitating both accurate search matching and quick comprehension by browsing users.

\section{Heuristic Role Categorization}
%===========================================

The final enrichment step maps each internship to a high-level domain category, enabling the faceted filtering that is a core functional requirement of the system. The \texttt{categorizeJob} function evaluates the (now normalized) job title against a hierarchy of professional ``anchors'' \cite{baeza2011modern, croft2010search}. This categorization serves dual purposes: it provides immediate value for UI navigation even before more sophisticated semantic mapping is applied, and it serves as a fallback classification for cases where embedding-based mapping (Layer~B) has low confidence.

\subsection{Category Taxonomy Design}

The category taxonomy, detailed in Section~7.3, defines five mutually exclusive, collectively exhaustive top-level domains: \textit{Software}, \textit{Data/AI}, \textit{Design}, \textit{Healthcare}, and \textit{Business}. This design reflects the empirical distribution of internships in our corpus and is intentionally flat—a shallow taxonomy optimized for user navigation rather than an exhaustive ontological hierarchy. Each category is associated with a set of anchor terms that serve as high-precision signals for membership.

\subsection{Priority-Ordered Classification}

The classification algorithm, formalized in Algorithm~\ref{alg:categorize_job}, evaluates the job title (and, with lower priority, the extracted skills list) against a priority-ordered cascade of anchor terms. The priority ordering is crucial: it ensures that more specific, semantically dense categories are evaluated before broader ones. For example, ``Machine Learning Engineer'' is evaluated against Data/AI anchors before Software anchors, preventing misclassification into the broader Software category.

\begin{algorithm}[H]
\caption{Heuristic Role Categorization}
\label{alg:categorize_job}
\begin{algorithmic}[1]
\Procedure{CategorizeJob}{title, skills}
    \State $titleLower \gets \text{normalize}(title)$
    \State $skillsLower \gets \text{normalize}(skills)$

    \If {$\text{containsAny}(titleLower, [\text{"data sci"}, \text{"machine learn"}, \text{"deep learn"}, \text{"ai eng"}, \text{"data analy"}, \text{"business intell"}])$}
        \State \Return $\text{"Data/AI"}$
    \EndIf
    \If {$\text{containsAny}(titleLower, [\text{"frontend"}, \text{"backend"}, \text{"full stack"}, \text{"software"}, \text{"devops"}, \text{"mobile dev"}, \text{"web dev"}, \text{"qa"}, \text{"quality assur"}, \text{"cloud eng"}])$}
        \State \Return $\text{"Software"}$
    \EndIf
    \If {$\text{containsAny}(titleLower, [\text{"ux"}, \text{"ui"}, \text{"designer"}, \text{"graphic"}, \text{"product design"}, \text{"visual"}, \text{"interaction"}])$}
        \State \Return $\text{"Design"}$
    \EndIf
    \If {$\text{containsAny}(titleLower, [\text{"nurse"}, \text{"pharma"}, \text{"clinical"}, \text{"medical"}, \text{"healthcare"}, \text{"biomed"}, \text{"public health"}])$}
        \State \Return $\text{"Healthcare"}$
    \EndIf
    \If {$\text{containsAny}(titleLower, [\text{"market"}, \text{"finance"}, \text{"hr"}, \text{"human res"}, \text{"consult"}, \text{"sales"}, \text{"account"}, \text{"operat"}])$}
        \State \Return $\text{"Business"}$
    \EndIf

    \State \Return $\text{"Business"}$ \Comment{Default fallback}
\EndProcedure
\end{algorithmic}
\end{algorithm}

The algorithm includes several design features that enhance its robustness. Anchor terms are defined as substrings rather than requiring exact token matches, capturing morphological variations (e.g., ``designer'' matches both ``Designer'' and ``Designing''). The normalization step applies the same sanitization pipeline described in Section~8.2.1, ensuring consistent matching regardless of source formatting. And the default fallback to ``Business'' reflects the empirical observation that most unclassifiable listings in our corpus fall within professional services domains. This categorization facilitates the efficient discovery mechanisms discussed in retrieval theory, providing a stable and predictable taxonomy browser that performs with perfect consistency and zero latency \cite{baeza2011modern, croft2010search}.

\section{Caching and Performance Considerations}
%===========================================

To translate the theoretical efficiency of individual enrichment modules into practical, low-latency system performance, the results of the enrichment pipeline are stored in a server-side in-memory cache. This caching strategy is the single most impactful performance optimization in the system, fundamentally shaping its operational profile and cost characteristics.

\subsection{Cache Architecture}

The cache is implemented as a server-side \texttt{Map<string, Internship>} structure, keyed by the stable identifier generated in Section~8.2.2. The \texttt{data.ts} module serves as the sole access interface, implementing a read-through caching pattern: on a cache miss, the module reads the raw data from the static JSON catalog, executes the full enrichment pipeline, stores the result in the cache, and returns the enriched object. Subsequent requests for the same identifier are served directly from memory.

\subsection{Amortized Cost Model}

This architecture embodies an amortized cost model that is central to the system's lightweight operational philosophy. The entire computational cost of the enrichment pipeline—including file I/O, text sanitization, regex processing, skill extraction, and categorization—is paid once per data refresh cycle. This one-time cost is then amortized over potentially hundreds of thousands of read requests from the API layer. The cost model stands in stark contrast to architectures that perform semantic analysis at query time, where each user request incurs the full computational burden \cite{buttcher2016information, menghani2023efficient}.

\subsection{Cache Invalidation Strategy}

Cache invalidation is tied directly to the data refresh cycle. When new scrape data is ingested or the enrichment logic is updated, the cache is cleared and repopulated lazily on subsequent requests. This strategy eliminates the complexity of partial invalidation while ensuring that users always receive data processed by the most recent pipeline version. For production deployments with continuous ingestion, a time-to-live (TTL) mechanism can be layered on top, automatically refreshing cached entries after a configurable interval to accommodate incremental data updates.

\subsection{Performance Targets}

With the caching layer in place, the system consistently achieves sub-50ms response times for read requests, a critical threshold for modern interactive search systems \cite{buttcher2016information}. This performance profile is achieved on commodity hardware without specialized infrastructure, directly addressing the ``lightweight'' design goal articulated in the problem statement. The contrast with LLM-dependent architectures is instructive: a single LLM API call for semantic enrichment typically requires 500--2,000ms and incurs per-request financial costs, making caching-amortized local processing not merely an optimization but a fundamental architectural necessity for sustainable operation at scale.

\section{Summary}
%===========================================

This chapter has presented a comprehensive account of the lightweight semantic enrichment pipeline, detailing the architecture, algorithms, and design principles that transform raw, heterogeneous internship listings into structured, semantically rich entities. The pipeline's tiered, deterministic design achieves high extraction accuracy across salary, skill, and category dimensions while maintaining the sub-50ms latency and zero external API costs that define the system's lightweight operational profile. The caching strategy ensures that these computational investments are amortized across many user requests, enabling responsive, cost-effective search at scale. Together with the semantic schema defined in Chapter~7 and the retrieval infrastructure described in Chapter~9, this enrichment pipeline forms the foundation for a sustainable, production-grade internship discovery platform.
