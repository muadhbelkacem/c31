\section{Chapter Introduction}
This chapter presents the research methodology used to design, structure, and evaluate the proposed internship aggregation and semantic enrichment system. It translates the theoretical principles established in Chapter 2 and the implementation environment described in Chapter 3 into a coherent methodological framework covering system requirements, architectural design, data processing workflow, semantic classification, heuristic normalization, and evaluation strategy.

The purpose of this chapter is to define how the proposed lightweight system was conceptually structured and how its effectiveness will be assessed relative to the research questions introduced in Chapter 1. Particular emphasis is placed on balancing semantic processing quality with computational efficiency, reflecting the thesis objective of practical operation on commodity hardware.

\section{System Overview and Functional Methodology}
This chapter establishes the architectural blueprint and methodological framework for the proposed internship aggregation and semantic enrichment system, which constitutes the central technical contribution of this thesis. As established in the problem statement, the primary challenge is transforming noisy, heterogeneous internship and job listing data into structured, usable internship records while maintaining computational efficiency and avoiding reliance on heavyweight cloud-hosted language model infrastructure [11, 15, 21].

To address this challenge, the thesis proposes a hybrid lightweight processing architecture that combines deterministic heuristic normalization with transformer-based semantic classification. This modular design prioritizes maintainability, transparency, and practical deployment on commodity hardware while preserving sufficient semantic expressiveness for internship relevance assessment and enrichment [38, 45, 60].

This chapter defines the system’s functional requirements, architectural structure, formal data representation model, and the operational workflow governing data ingestion, semantic enrichment, filtering, and frontend delivery. The proposed methodology is grounded in established principles of information extraction, structured data integration, semantic classification, and practical lightweight machine learning system design [15, 21, 27, 49].

\subsection{Three-Layer Processing Architecture}
To balance semantic processing quality with computational efficiency, the proposed methodology adopts a lightweight three-layer processing architecture for internship data transformation, classification, and enrichment.

The first stage, Layer A (Deterministic Heuristic Processing), handles computationally inexpensive preprocessing tasks through explicit rule-based logic. This includes structural validation, malformed record filtering, field normalization, duplicate detection support, internship-specific keyword heuristics, and rejection of clearly irrelevant professional job postings. Because these operations rely on deterministic rules rather than learned inference, they are transparent, reproducible, and computationally efficient.

The second stage, Layer B (Lightweight Semantic Classification), processes records that require contextual semantic interpretation beyond explicit heuristic matching. This layer uses a lightweight sentence-transformer model (all-MiniLM-L6-v2) to support internship relevance assessment and semantic enrichment for noisy or ambiguous postings whose meaning cannot be reliably resolved through deterministic rules alone.

The third stage, Layer C (Manual Review Flagging and Exception Handling), handles records that remain uncertain after automated processing. Rather than forcing a potentially incorrect automated classification, ambiguous records are flagged using structured review indicators (e.g., needs_manual_review) for later inspection during dataset maintenance or evaluation. This layer improves system reliability by separating high-confidence automated decisions from uncertain edge cases.

This layered methodology allows straightforward cases to be handled efficiently while reserving semantic inference for ambiguous records and preserving a controlled exception path for uncertain outcomes. The result is a hybrid architecture that maintains interpretability, computational practicality, and robustness when processing heterogeneous recruitment data.

\subsection{System Architecture and Component Mapping}

The proposed system is organized into four logical architectural tiers to separate presentation concerns, application communication, semantic processing responsibilities, and persistence mechanisms. This decomposition improves maintainability, modularity, and implementation clarity by reducing coupling between independently evolving system components [15, 60].

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Presentation Layer (Frontend Application)} -- The presentation layer provides the user-facing internship discovery platform implemented using Next.js and React. This layer is responsible for rendering internship data, supporting interactive user functionality, and exposing authenticated application features.

    Core responsibilities include:
    \begin{itemize}
        \item internship browsing and pagination
        \item keyword-based search and structured filtering
        \item detailed internship viewing
        \item saved internship management for authenticated users
        \item account preference interaction
        \item UI personalization features
    \end{itemize}
    The presentation layer remains isolated from backend processing logic and consumes structured internship data exclusively through the application communication layer.

    \item \textbf{Application Communication Layer (Next.js Route Handlers)} -- The communication layer acts as the controlled interface between the frontend application and backend data services. Implemented using Next.js server-side route handlers, this layer manages request handling, internship data access coordination, response serialization, and caching behavior.

    Its responsibilities include:
    \begin{itemize}
        \item handling frontend internship data requests
        \item delegating access to processed internship records
        \item serving structured JSON responses
        \item managing response caching behavior
        \item isolating frontend components from storage implementation details
    \end{itemize}
    This architectural separation improves maintainability by preventing frontend logic from depending directly on persistence or enrichment implementation details.

    \item \textbf{Semantic Processing Layer (Python Enrichment Pipeline)} -- The semantic processing layer constitutes the computational core of the proposed system and implements the three-layer methodology defined in Section 4.2.1. This layer transforms heterogeneous raw internship and job listing data into structured records suitable for deployment.

    Its responsibilities include:
    \begin{itemize}
        \item \textbf{Layer A (Deterministic Heuristic Processing):} structural validation, malformed record filtering, normalization, duplicate handling support, internship-specific rule matching, and explicit rejection of clearly irrelevant non-internship postings.
        \item \textbf{Layer B (Lightweight Semantic Classification):} context-sensitive internship relevance assessment and semantic enrichment using the lightweight sentence-transformer model (all-MiniLM-L6-v2) for ambiguous records requiring semantic interpretation.
        \item \textbf{Layer C (Manual Review Flagging and Exception Handling):} identification and structured flagging of uncertain records requiring later inspection through manual review indicators such as \texttt{needs\_manual\_review}.
    \end{itemize}
    This layer executes independently from the frontend application runtime and supports automated recurring enrichment workflows.

    \item \textbf{Data Persistence Layer} -- The persistence layer manages both public internship catalog delivery and authenticated user application state.

    The architecture uses a hybrid persistence strategy:
    \begin{itemize}
        \item \textbf{Static internship catalog:} processed internship records exported as structured JSON for efficient frontend consumption
        \item \textbf{Dynamic application persistence:} Supabase-managed PostgreSQL storage for authentication, saved internships, preferences, and account-linked user functionality
    \end{itemize}
    This separation balances efficient public internship delivery with transactional support for authenticated user interactions.
\end{itemize}

This architectural decomposition ensures that changes to frontend behavior, enrichment methodology, persistence mechanisms, or user-facing functionality can be introduced with minimal disruption to unrelated system components.

\subsection{Core Data Model}

The proposed system relies on a structured core data model that defines how internship information moves through acquisition, transformation, storage, and user interaction workflows. This model acts as a formal semantic contract between the ingestion pipeline, persistence layer, and frontend application, ensuring that structured data remains consistent throughout the system lifecycle.

Figure 4.2 presents the conceptual UML representation of the system’s principal entities and their relationships.

The architecture distinguishes between raw acquisition entities and normalized operational entities to reflect the staged transformation of heterogeneous recruitment data.

The \texttt{RawInternship} entity represents unprocessed records obtained from scraping sources. These records preserve original source fields such as raw title, company name, location, description, source URL, and scraping metadata prior to transformation.

The \texttt{DataCleaningService} represents the transformation component responsible for converting raw recruitment records into structured internship entities. This stage performs validation, normalization, heuristic filtering, semantic classification, skill extraction, and manual-review exception handling consistent with the three-layer methodology described previously.

The normalized \texttt{Internship} entity serves as the central operational data structure used throughout the application. It contains structured attributes including stable identifiers, normalized titles, company metadata, salary information, descriptions, extracted skills, categorical labels, duration metadata, platform provenance, and application links.

The design of this schema is motivated by three methodological objectives:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Identity and provenance:} Stable identifiers support consistent referencing across ingestion cycles while preserving traceability to original recruitment sources [10].
    \item \textbf{Structured discovery support:} Explicit metadata such as category labels, extracted skills, salary normalization, and location fields support efficient filtering, browsing, and frontend presentation [3].
    \item \textbf{Cross-layer consistency:} Shared structured entities ensure compatibility between ingestion logic, semantic enrichment, API delivery, and frontend rendering components [15].
\end{itemize}

The conceptual model additionally includes user-oriented entities such as \texttt{User} and \texttt{SavedInternship}, representing authenticated platform functionality including saved internship persistence and account-linked interaction behavior.

\subsection{Application Interaction Flow}

Figure 4.3 illustrates the high-level interaction sequence between the user, frontend application, and backend persistence services during normal platform operation. The interaction model follows an asynchronous request-response architecture typical of modern web applications.

The sequence begins when a user visits the internship platform, triggering the frontend application to load the available internship catalog for browsing. Structured internship data is retrieved through backend application services and rendered to the user interface.

When a user selects a specific internship, the frontend requests the corresponding structured internship record and presents the normalized internship details, including metadata such as title, company, description, skills, salary information, and application links.

Authenticated interaction is additionally supported through the user account workflow. During login, authentication credentials are submitted through the frontend and validated through the Supabase authentication infrastructure, which returns a session token upon successful verification.

Registered users may also persist saved internship interactions. When a user bookmarks an internship, the frontend communicates with the persistence layer to store the user–internship association, after which confirmation is returned to the interface.

This interaction architecture separates frontend presentation behavior from backend persistence responsibilities while supporting responsive user interaction and authenticated account-linked functionality.


\subsection{Ingestion and Semantic Enrichment Workflow}
The data ingestion and enrichment pipeline constitutes the methodological core of the proposed system and directly supports the research objective of balancing semantic processing effectiveness with computational efficiency. The pipeline follows a staged transformation methodology in which raw heterogeneous recruitment data is progressively refined into structured internship records using the most appropriate processing mechanism for each task [11, 15].

The workflow is implemented through the previously defined three-layer processing architecture.

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Layer A: Deterministic Heuristic Processing} -- The first stage performs high-confidence preprocessing using explicit rule-based operations that incur negligible inference cost. This layer prioritizes speed, transparency, and reproducibility. Primary operations include:
    \begin{itemize}
        \item \textbf{Structural validation:} Raw records are checked for required field integrity before transformation begins. Malformed or incomplete records are excluded from further processing to preserve downstream consistency.
        \item \textbf{Text cleaning and normalization:} Raw recruitment text is normalized through whitespace cleanup, formatting correction, and removal of residual markup artifacts to reduce surface-level variability [11].
        \item \textbf{Deterministic attribute extraction:} Structured attributes such as salary information and normalized metadata are extracted using explicit parsing logic where pattern-based extraction is reliable.
        \item \textbf{Stable identifier generation:} A deterministic identifier is generated from normalized record metadata to support consistent record referencing and duplicate management across ingestion cycles [10, 16].
        \item \textbf{Initial heuristic filtering:} Clearly irrelevant non-internship postings are excluded through explicit internship-oriented keyword and structural heuristics.
    \end{itemize}
    \item \textbf{Layer B: Lightweight Semantic Classification} -- The second stage handles semantically ambiguous records that cannot be reliably resolved through deterministic heuristics alone. This layer applies lightweight sentence-transformer semantic inference using the all-MiniLM-L6-v2 model [45]. The model supports contextual internship relevance assessment and semantic enrichment tasks where explicit rule matching is insufficient. Unlike heavyweight cloud-hosted language model pipelines, this approach executes locally and avoids per-request inference cost, preserving the lightweight design objectives of the system [38, 53].
    \item \textbf{Layer C: Manual Review Flagging and Exception Handling} -- The final stage handles records whose classification confidence remains uncertain after automated processing. Rather than forcing unreliable automated categorization, ambiguous records are flagged for later human inspection using structured review indicators (e.g., needs\_manual\_review). This provides a controlled exception mechanism that improves dataset reliability while preserving automated pipeline throughput.
\end{itemize}

\subsection{Export and Deployment Preparation}

After processing, accepted internship records are serialized into the structured JSON catalog consumed by the frontend application.

This deployment-oriented export model separates computational enrichment from user-facing application delivery, ensuring that expensive semantic processing occurs during scheduled ingestion rather than during live user interaction.

This staged methodology preserves interpretability, computational practicality, and semantic robustness while maintaining compatibility with recurring automated data refresh workflows.

\section{Semantic Categorization and Structured Labeling}
This chapter defines the semantic categorization strategy used to transform heterogeneous internship and job listing data into a consistent structured representation suitable for automated processing and frontend presentation.

Because recruitment data originates from multiple external platforms with inconsistent naming conventions, ambiguous terminology, and variable formatting, the system requires an internal semantic labeling strategy that supports normalization, classification, and structured filtering.

This chapter first defines the structured labeling model used within the internship dataset, including normalized metadata fields and extracted semantic attributes. It then explains the categorization strategy used to group heterogeneous internship postings into consistent application-facing categories. Finally, it describes how semantic normalization reduces vocabulary inconsistency and improves structured discovery across noisy recruitment data.

These design decisions are grounded in established principles of data integration, semantic normalization, and information extraction, directly addressing the semantic consistency challenges identified in the problem statement [15, 49, 54].

\subsection{Target Schema Definition}
To achieve a unified and structured representation of heterogeneous recruitment data, the system requires a clearly defined target schema. External internship data originates from multiple heterogeneous sources, including semi-structured scraped web content and partner-provided JSON datasets with inconsistent schema definitions. Direct frontend consumption of such raw data is impractical without normalization, validation, and structural transformation. The target schema therefore serves as the formal structured representation into which raw records are transformed during the enrichment pipeline [49].

The schema is not merely a passive storage format; it functions as a formal semantic contract that ensures consistency across ingestion, semantic processing, persistence, and frontend presentation. By enforcing a shared structured representation, the system reduces ambiguity and limits data inconsistency propagation across pipeline stages [15].

\subsection{Structural Requirements}
The schema's design is directly motivated by three primary functional objectives, each of which addresses a key failure mode of ad-hoc data processing:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Identity and Provenance: Aggregated recruitment data frequently contains duplicate or near-duplicate records across scraping cycles. To support stable identification and dataset consistency, the schema requires a deterministic primary identifier generated from normalized record metadata. Source traceability is additionally preserved through direct reference to the original internship listing URL, supporting auditing, freshness management, and provenance tracking [10].

\item Structured Discovery Support: The frontend application requires structured metadata that enables users to efficiently browse and filter internship listings. The schema therefore includes standardized attributes such as category labels, extracted skills, location metadata, salary normalization, and company information. These fields support practical faceted interaction and consistent frontend presentation [3].

\item Cross-Layer Semantic Consistency: The schema must support interoperability between preprocessing logic, semantic enrichment mechanisms, persistence layers, API delivery, and frontend rendering. A consistent structured entity reduces ambiguity between independently evolving application components and improves maintainability.

\end{itemize}

\subsection{The Internship Interface: A Formal Semantic Contract}
These structural requirements are implemented through the TypeScript Internship interface, which serves as the canonical representation of processed internship records throughout the application.

By defining a shared strongly typed structure, the system ensures that all processing stages—from normalization logic and semantic enrichment through API serialization and frontend rendering—operate on a consistent data entity definition. This improves implementation reliability and reduces the risk of malformed data propagation [49].

\subsection{Taxonomy Selection: The ESCO Framework}
The European Skills, Competences, Qualifications and Occupations (ESCO) framework provides a standardized multilingual classification system designed to describe occupations, skills, competences, and qualifications within the European labor market [17]. ESCO is widely used in recruitment informatics and labor-market analytics because it provides a structured vocabulary for reducing ambiguity in professional terminology and improving interoperability between heterogeneous employment datasets [20, 31].

ESCO separates labor-market knowledge into interrelated conceptual pillars, most notably occupations and skills. This structured decomposition makes it particularly relevant when processing internship and job listing data, where employers frequently describe equivalent competencies using inconsistent terminology. For example, postings may refer to “frontend engineering,” “UI development,” or “React development” while describing closely related professional skill areas.

Although the proposed system does not implement full ontology-level ESCO occupation mapping, the framework serves as an important conceptual reference for the semantic enrichment methodology. Specifically, ESCO informed the design of the internal categorization logic and the construction of curated JSON-based skill reference libraries used during heuristic normalization and semantic enrichment.

This inspiration is particularly relevant for skill normalization. Recruitment data often contains vocabulary inconsistency, abbreviations, overlapping terminology, and informal naming conventions that reduce structured comparability. By adopting the general principle of controlled vocabulary normalization inspired by ESCO, the system improves consistency in extracted skill labeling while avoiding the implementation complexity of full taxonomy alignment.

ESCO is therefore used in this research as a semantic design reference rather than a strict operational dependency. This approach preserves the benefits of standardized recruitment terminology while remaining compatible with the thesis objective of lightweight, practical semantic enrichment on commodity infrastructure.

\subsection{Occupations Pillar}
ESCO organizes occupations into a four-level hierarchical structure. For this system, the Level 4 unit groups are the main focus. Level 3 groups, such as ``Software and Applications Developers and Analysts,'' are too broad for differentiating a front-end intern from a data engineering intern. Level 4 provides greater granularity, with distinct concepts such as ``Web Developer,'' ``Software Developer,'' and ``Systems Analyst.'' This level balances the specificity needed for retrieval with the generalizability required to map many raw titles into a manageable target space. This granularity allows the system to disambiguate roles that a coarser taxonomy would conflate. For instance, a ``Python Developer'' working on web applications, a ``Machine Learning Engineer'' building models, and a ``DevOps Engineer'' managing infrastructure might all be tagged as ``Software Developer'' at Level 2 or 3. At Level 4, however, they can be mapped to distinct unit groups, enabling more precise faceted filtering and improving retrieval precision. This approach is consistent with labor-market analysis frameworks such as O*NET's Standard Occupational Classification (SOC) coding, making the research comparable and interoperable with a wider body of work~\cite{peterson2001occupational}. The \texttt{category} field in the schema is designed to hold a broad professional label.

\subsection{Skills and Competences Pillar}
The skill lexicon used in the extraction phase (detailed in the corresponding chapter) is grounded in the ESCO Skills pillar and is expanded with a curated set of common industry synonyms. ESCO's skill model is inherently linked to its occupations model, defining the essential and optional knowledge, skills, and competences for each job profile. By using ESCO as a reference, the system actively combats the ``vocabulary gap'' where different employers use divergent terms for the same competency. This ground-truth linking is a foundational step for a recommendation system that can accurately connect student skills to job requirements, a known challenge in recruitment informatics~\cite{giabelli2021skills, lacic2020recommender}. The lexicon is not static; it is designed to be periodically updated to incorporate emerging technologies (e.g., new JavaScript frameworks, AI/ML libraries) as they gain traction in the labor market. This maintenance process is essential for building and sustaining a reliable, long-term knowledge base.

\subsection{Internal Categorization and Mapping}
While ESCO provides the granular canonical depth required for semantic precision, it is not directly suitable for the top-level user interface. A student browsing for an internship is unlikely to search for ``ESCO Occupation 2512,'' and a hierarchical tree of hundreds of four-level occupations is unsuitable for exploratory browsing. Therefore, the system introduces a supplementary internal categorization layer: a flatter set of high-level categories designed to facilitate initial browsing and provide a stable foundation for faceted filtering~\cite{faliagka2012online}.

\subsection{Internal Categorization and Mapping}

While ESCO provides a useful conceptual reference for standardized occupational terminology, the proposed system relies on an internally defined categorization framework better aligned with the practical requirements of lightweight semantic enrichment and frontend usability.

A full ontology-driven occupation hierarchy would introduce unnecessary implementation complexity for the scope of this system, particularly given the variability and ambiguity of internship data originating from heterogeneous external sources. Instead, the enrichment pipeline uses curated internal JSON-based semantic reference libraries that support practical classification, skill normalization, and structured filtering.

This internal categorization strategy is informed by ESCO’s principle of controlled vocabulary normalization but is intentionally simplified to support lightweight deployment and maintainable domain adaptation.

The categorization framework is implemented through curated semantic reference resources including domain keyword mappings, internship classification rules, negative role exclusion patterns, and structured skill libraries.

The internal domain space includes categories spanning multiple professional areas, including software engineering, data science, cybersecurity, cloud and DevOps, engineering, healthcare, finance, marketing, operations, sales, human resources, research, education, legal, manufacturing, and related professional domains.

This broader categorization approach provides several methodological advantages:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Practical semantic normalization:
Equivalent or closely related employer terminology can be mapped into consistent internal categories despite vocabulary inconsistency.

\item Frontend filtering compatibility:
Structured categories support user-facing filtering and browsing functionality without exposing complex external taxonomy structures.

\item Lightweight maintainability:
JSON-based semantic reference libraries can be updated incrementally as terminology evolves without requiring heavyweight ontology maintenance.

\item Flexible domain extensibility:
New industries, skill clusters, and internship categories can be introduced through controlled vocabulary updates rather than architectural redesign.

\end{itemize}

This internal semantic mapping strategy therefore balances conceptual standardization with implementation practicality, directly supporting the lightweight design objectives of the proposed system.


\subsection{Addressing the Semantic Gap}
A central challenge in heterogeneous recruitment data processing is the semantic gap between inconsistent employer terminology and the structured representations required for reliable internship discovery. Employers frequently describe equivalent roles, competencies, and technologies using highly variable language, abbreviations, informal naming conventions, or domain-specific jargon. Without normalization, this variability reduces dataset consistency, complicates filtering, and weakens structured comparability across listings [18, 49].

The proposed system addresses this semantic gap through a layered semantic normalization strategy informed by both standardized recruitment terminology principles and practical lightweight enrichment methods.

The first level of this strategy is controlled semantic normalization. Inspired by frameworks such as ESCO, the system reduces vocabulary inconsistency by aligning heterogeneous employer terminology with internally curated semantic reference libraries [17, 54]. This improves consistency in extracted skills, domain categorization, and structured metadata generation without requiring full ontology-level taxonomy enforcement.

The second level is internal categorization and enrichment abstraction. Raw internship and job descriptions often contain highly specific or inconsistent terminology unsuitable for direct frontend presentation or structured filtering. The enrichment pipeline therefore transforms noisy source language into stable internal categories and normalized skill labels better suited for application-level discovery and user-facing browsing [15, 21].

The third level is context-aware semantic classification through lightweight transformer inference. Deterministic heuristics alone cannot reliably interpret ambiguous terminology or context-dependent internship descriptions. The semantic classification layer therefore provides contextual interpretation where rule-based normalization is insufficient, improving classification robustness for noisy or semantically unclear postings [45, 38].

Rather than addressing the semantic gap through expensive live query-time semantic retrieval, the proposed methodology resolves semantic inconsistency during scheduled enrichment and dataset transformation. This shifts computational complexity away from user interaction and supports the thesis objective of lightweight, practical semantic processing on commodity hardware [38, 53].


\section{Evaluation Methodology}
This section defines the framework for empirically evaluating the proposed internship aggregation and semantic enrichment system. The evaluation methodology examines extraction reliability, semantic normalization effectiveness, computational efficiency, and practical operational performance under commodity hardware constraints.

The evaluation design is grounded in established principles of Natural Language Processing (NLP), information extraction, and software systems evaluation [27, 49, 59]. Particular emphasis is placed on evaluation validity, ensuring that the chosen measurements accurately reflect the semantic processing quality and practical system behavior being investigated [59].

The methodology formalizes the evaluation objectives, links them to the research questions, defines the reference dataset and benchmarking conditions, introduces both quantitative and qualitative assessment criteria, and establishes the experimental configurations necessary to examine the trade-off between semantic effectiveness and computational cost.

Because the thesis explicitly targets lightweight practical deployment rather than large-scale cloud inference, the evaluation additionally considers computational efficiency and resource practicality in alignment with Green AI principles [53].

\subsection{Evaluation Objectives}
The evaluation is designed to assess both the semantic output quality and the practical operational characteristics of the proposed internship aggregation and enrichment system. The primary objective is to determine whether the proposed lightweight three-layer architecture can achieve meaningful semantic enrichment and internship classification while remaining computationally practical for deployment on commodity hardware.

The evaluation is explicitly structured around the four research questions defined in Chapter 1, with each question mapped to measurable experimental objectives grounded in prior literature on information extraction, semantic processing, and efficient machine learning systems [33, 38, 49, 59].

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{RQ1 (Architecture Efficiency–Quality Balance):} How can a lightweight semantic enrichment pipeline balance internship classification quality with computational efficiency on commodity hardware? This objective evaluates the overall effectiveness of the proposed three-layer architecture by examining the trade-off between semantic processing quality and practical computational cost. Measurements include enrichment consistency, runtime practicality, memory behavior, and frontend responsiveness under realistic operating conditions. This directly tests the thesis claim that meaningful semantic enrichment can be achieved without heavyweight infrastructure or cloud-dependent inference [38, 53].
    \item \textbf{RQ2 (Sentence-Transformer Classification Effectiveness):} How effectively can lightweight sentence-transformer models support internship relevance classification for noisy internship and job postings? This objective evaluates the contribution of the transformer-based semantic classification layer when handling ambiguous or noisy recruitment data that cannot be reliably resolved through deterministic heuristics alone. The evaluation focuses on internship relevance classification quality, semantic ambiguity resolution, and practical inference behavior using lightweight sentence-transformer models [45, 38].
    \item \textbf{RQ3 (Semantic Enrichment Usability Improvement):} How effectively can semantic enrichment techniques improve the usability of internship records collected from heterogeneous online sources? This objective evaluates whether semantic enrichment improves the practical usability of aggregated internship data by reducing vocabulary inconsistency, improving structured categorization, supporting skill extraction, and producing cleaner frontend-consumable internship records. The focus is on semantic consistency, dataset usability, and structured enrichment effectiveness rather than live retrieval benchmarking [15, 21, 49].
    \item \textbf{RQ4 (Heuristic Normalization Automation):} Which heuristic-based normalization strategies can automate the ingestion of inconsistently structured internship data into a unified schema? This objective evaluates the effectiveness of deterministic preprocessing and heuristic normalization for transforming heterogeneous raw recruitment data into a structured canonical schema. Particular emphasis is placed on structural validation, malformed record filtering, metadata normalization, duplicate handling support, and deterministic attribute extraction [11, 40, 49].
\end{itemize}

\subsection{Ground Truth Construction}
A reliable evaluation reference is necessary to assess the semantic processing quality and practical behavior of the proposed system. Because the thesis focuses on lightweight applied system development rather than large-scale benchmark creation, the evaluation uses a manually inspected representative reference subset rather than a formal externally annotated benchmark corpus.

The reference evaluation process was designed to support qualitative correctness assessment, structured output verification, comparative pipeline analysis, and practical performance observation [10, 49, 59].

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Evaluation Dataset and Reference Construction} -- The evaluation is based on internship and job listing data processed through the implemented enrichment pipeline. The underlying dataset consists of heterogeneous recruitment records collected from multiple online sources, including scraped internship listings and structured JSON-based partner data with varying schema quality.

    A representative evaluation subset was manually inspected to assess semantic correctness and structured output quality. The sampling process intentionally included diverse posting types, ambiguous internship descriptions, clearly irrelevant professional roles, and heterogeneous metadata quality to ensure meaningful evaluation coverage.

    This manually reviewed subset served as the practical reference point for evaluating:
    \begin{itemize}
        \item heuristic normalization correctness
        \item internship relevance classification behavior
        \item semantic enrichment consistency
        \item structured schema completeness
        \item ambiguity handling and manual-review flagging behavior
    \end{itemize}

    \item \textbf{Manual Semantic Verification} -- Because the thesis evaluates a practical applied enrichment system rather than a formal benchmark competition model, semantic correctness assessment was performed through structured manual inspection of processed outputs.

    This review focused on comparing raw recruitment records against enriched outputs to determine whether:
    \begin{itemize}
        \item irrelevant non-internship postings were correctly excluded
        \item ambiguous internship listings were semantically interpreted appropriately
        \item extracted skills aligned with visible listing content
        \item domain categorization remained semantically coherent
        \item normalized metadata fields preserved meaningful information
    \end{itemize}

    This manual verification process supports qualitative evaluation of semantic enrichment effectiveness and classification robustness [21, 49].

    \item \textbf{Comparative Pipeline Assessment} -- To isolate the contribution of semantic classification, comparative observation was conducted between deterministic heuristic preprocessing alone and the combined heuristic + transformer-assisted enrichment pipeline.

    This comparison supports evaluation of:
    \begin{itemize}
        \item classification improvement for ambiguous listings
        \item reduction in false positive internship acceptance
        \item improved semantic interpretation beyond keyword heuristics
        \item practical trade-offs between inference cost and enrichment quality
    \end{itemize}

    This comparative design directly supports the evaluation of RQ1 and RQ2.

    \item \textbf{Operational Performance Reference Measurements} -- Practical performance evaluation was conducted through direct runtime observation during local execution.

    Measured characteristics include:
    \begin{itemize}
        \item end-to-end enrichment runtime
        \item approximate processing throughput
        \item semantic pipeline execution practicality
        \item frontend interaction responsiveness measured through Chromium DevTools
        \item cache-assisted browsing responsiveness after initial frontend data loading
    \end{itemize}
\end{itemize}

Because the thesis emphasizes lightweight deployment practicality, these operational observations serve as an important complement to semantic correctness evaluation [38, 53].

\subsection{Metrics}
The evaluation employs a multi-dimensional set of quantitative and qualitative metrics to assess both semantic output quality and operational practicality. Because the proposed system combines deterministic heuristics, lightweight semantic classification, and applied frontend deployment, no single metric is sufficient to capture overall system effectiveness [27, 33, 59].

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Extraction and Classification Quality} -- For evaluating structured normalization and semantic classification behavior (RQ2 and RQ4), the study applies standard correctness-oriented assessment criteria.
    \begin{itemize}
        \item \textbf{Precision and Recall:} Precision and recall are used where applicable to assess the trade-off between false positive and false negative classification behavior, particularly when comparing heuristic filtering against transformer-assisted semantic classification [37].
        \item \textbf{F1-Score:} The harmonic mean of precision and recall is used as a balanced summary metric when evaluating internship relevance classification performance, particularly in scenarios where both false acceptance and false rejection are important.
        \item \textbf{Manual Semantic Correctness Assessment:} Because portions of the evaluation rely on structured manual inspection rather than formal benchmark datasets, qualitative semantic correctness is also assessed through expert review of processed internship outputs. This includes correctness of domain categorization, internship relevance interpretation, and skill extraction consistency.
    \end{itemize}
    \item \textbf{Semantic Enrichment and Dataset Quality} -- For evaluating the usability improvements introduced by semantic enrichment (RQ3), the study assesses structured dataset quality through practical semantic consistency criteria.
    \begin{itemize}
        \item \textbf{Categorization Consistency:} Evaluation of whether semantically similar internship listings are consistently assigned to coherent internal domain categories.
        \item \textbf{Skill Extraction Quality:} Assessment of whether extracted skill labels accurately reflect visible internship content and remain semantically normalized across heterogeneous source terminology [4, 21].
        \item \textbf{Schema Completeness:} Assessment of the proportion of processed records successfully transformed into complete structured internship entities suitable for frontend deployment.
        \item \textbf{Ambiguity Handling Behavior:} Evaluation of whether uncertain or semantically ambiguous listings are appropriately flagged for manual review rather than incorrectly forced into confident automated classifications.
    \end{itemize}
    \item \textbf{Operational Performance Metrics} -- For evaluating practical deployment feasibility (RQ1), the study includes lightweight operational performance measurements aligned with efficient NLP and Green AI evaluation principles [38, 53].
    \begin{itemize}
        \item \textbf{Pipeline Runtime Observation:} Total end-to-end semantic enrichment execution time observed during local pipeline runs.
        \item \textbf{Approximate Processing Throughput:} Estimated number of internship listings processed per unit time during enrichment execution.
        \item \textbf{Frontend Responsiveness:} Observed page loading, filtering, and interaction responsiveness measured through Chromium DevTools under realistic local browsing conditions.
        \item \textbf{Memory Practicality:} Approximate memory behavior observed during enrichment execution to assess compatibility with commodity hardware constraints.
    \end{itemize}
    \item \textbf{Comparative Evaluation} -- To isolate the contribution of semantic classification, comparative evaluation is performed between:
    \begin{itemize}
        \item deterministic heuristic preprocessing alone
        \item heuristic preprocessing combined with transformer-assisted semantic classification
    \end{itemize}
\end{itemize}

This comparison supports direct analysis of the trade-off between semantic effectiveness and computational cost central to the thesis research objectives.

\subsection{Experimental Configuration}

To attribute observed performance differences to specific architectural components, the evaluation adopts a comparative experimental methodology based on controlled system configurations. Comparative evaluation is a standard approach in software systems and machine learning experimentation for isolating the contribution of individual processing components within a larger pipeline [38, 59].

\subsubsection{Baselines and Comparative Configurations}

The evaluation compares multiple configurations representing increasing semantic capability and computational complexity.

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Baseline 1: Deterministic Heuristic Processing (Layer A Only)} -- This configuration evaluates the deterministic preprocessing layer in isolation. It applies only explicit heuristic and rule-based processing mechanisms, including structural validation, malformed record filtering, metadata normalization, internship keyword heuristics, rule-based categorization, duplicate handling support, and deterministic skill extraction. This baseline establishes the performance floor for the proposed architecture and evaluates how effectively heuristic normalization alone can process heterogeneous recruitment data without contextual semantic inference [11, 40, 49].

    \item \textbf{Baseline 2: Full Lightweight Semantic Pipeline (Layer A + Layer B + Layer C)} -- This configuration represents the complete proposed methodology. It combines:
    \begin{itemize}
        \item Layer A: deterministic heuristic preprocessing and normalization
        \item Layer B: lightweight sentence-transformer-based semantic internship relevance classification
        \item Layer C: controlled manual-review exception handling for semantically ambiguous cases
    \end{itemize}
    This configuration serves as the primary experimental system and evaluates whether lightweight semantic classification improves internship relevance assessment, enrichment consistency, and overall dataset usability beyond deterministic preprocessing alone [45, 38]. The comparative difference between this configuration and the heuristic baseline isolates the practical contribution of transformer-assisted semantic enrichment.

    \item \textbf{Comparative Reference: General-Purpose LLM Assessment} -- A limited exploratory comparative assessment was conducted using general-purpose large language models, including ChatGPT and DeepSeek, to provide contextual comparison against contemporary cloud-based semantic reasoning systems. This comparison was exploratory rather than a formal benchmark and was not intended as a statistically controlled production evaluation. Instead, it served as supplementary qualitative reference for examining differences in:
    \begin{itemize}
        \item internship relevance classification behavior
        \item semantic interpretation plausibility
        \item enrichment consistency
        \item explainability characteristics
        \item practical computational and infrastructure implications
    \end{itemize}
    Because the thesis explicitly targets lightweight local deployment, this comparative reference helps contextualize whether useful semantic enrichment can be achieved without dependence on heavyweight cloud-hosted LLM inference [24, 38, 53].
\end{itemize}

The experimental design explicitly examines the trade-off between semantic effectiveness and computational practicality.
