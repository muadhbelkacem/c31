\chapter{Methodology}

\section{Chapter Introduction}
This chapter presents the research methodology used to design, structure, and evaluate the proposed internship aggregation and semantic enrichment system. It translates the theoretical principles established in Chapter 2 and the implementation environment described in Chapter 3 into a coherent methodological framework covering system requirements, architectural design, data processing workflow, semantic classification, heuristic normalization, and evaluation strategy.

The purpose of this chapter is to define how the proposed lightweight system was conceptually structured and how its effectiveness will be assessed relative to the research questions introduced in Chapter 1. Particular emphasis is placed on balancing semantic processing quality with computational efficiency, reflecting the thesis objective of practical operation on commodity hardware.

\section{System Overview and Functional Methodology}
This chapter establishes the architectural blueprint and methodological framework for the proposed internship aggregation and semantic enrichment system, which constitutes the central technical contribution of this thesis. As established in the problem statement, the primary challenge is transforming noisy, heterogeneous internship and job listing data into structured, usable internship records while maintaining computational efficiency and avoiding reliance on heavyweight cloud-hosted language model infrastructure [11, 15, 21].

To address this challenge, the thesis proposes a hybrid lightweight processing architecture that combines deterministic heuristic normalization with transformer-based semantic classification. This modular design prioritizes maintainability, transparency, and practical deployment on commodity hardware while preserving sufficient semantic expressiveness for internship relevance assessment and enrichment [38, 45, 60].

This chapter defines the system’s functional requirements, architectural structure, formal data representation model, and the operational workflow governing data ingestion, semantic enrichment, filtering, and frontend delivery. The proposed methodology is grounded in established principles of information extraction, structured data integration, semantic classification, and practical lightweight machine learning system design [15, 21, 27, 49].

\subsection{Three-Layer Processing Architecture}
To balance semantic processing quality with computational efficiency, the proposed methodology adopts a lightweight three-layer processing architecture for internship data transformation, classification, and enrichment.

The first stage, Layer A (Deterministic Heuristic Processing), handles computationally inexpensive preprocessing tasks through explicit rule-based logic. This includes structural validation, malformed record filtering, field normalization, duplicate detection support, internship-specific keyword heuristics, and rejection of clearly irrelevant professional job postings. Because these operations rely on deterministic rules rather than learned inference, they are transparent, reproducible, and computationally efficient.

The second stage, Layer B (Lightweight Semantic Classification), processes records that require contextual semantic interpretation beyond explicit heuristic matching. This layer uses a lightweight sentence-transformer model (all-MiniLM-L6-v2) to support internship relevance assessment and semantic enrichment for noisy or ambiguous postings whose meaning cannot be reliably resolved through deterministic rules alone.

The third stage, Layer C (Manual Review Flagging and Exception Handling), handles records that remain uncertain after automated processing. Rather than forcing a potentially incorrect automated classification, ambiguous records are flagged using structured review indicators (e.g., needs_manual_review) for later inspection during dataset maintenance or evaluation. This layer improves system reliability by separating high-confidence automated decisions from uncertain edge cases.

This layered methodology allows straightforward cases to be handled efficiently while reserving semantic inference for ambiguous records and preserving a controlled exception path for uncertain outcomes. The result is a hybrid architecture that maintains interpretability, computational practicality, and robustness when processing heterogeneous recruitment data.

\subsection{System Architecture and Component Mapping}
The system's architecture is organized into four logical tiers, a design pattern that enforces a clean separation of concerns, enhances scalability, and facilitates independent development and testing of each layer~\cite{doan2012principles}.


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Presentation Layer (app/components/): This tier contains the React-based user interface. The InternshipList.tsx component is responsible for rendering search results, interactive filters, and detail views. It maintains its own UI state while consuming data exclusively through the API layer, preserving a clean separation from backend logic.

\item API and Communication Layer (app/api/internship/): This tier exposes a RESTful API built with Next.js API routes. The route.ts endpoint acts as the single, stable interface for the frontend. It handles HTTP requests, orchestrates calls to the data processing layer, manages cache policy through HTTP headers, and returns structured JSON responses, thereby decoupling the client from the underlying data implementation.

\item Data Processing Layer (app/lib/): This is the computational core of the system, responsible for the entire ``clean-enrich-structure'' pipeline. It is divided into distinct modules to maximize cohesion:

\item data.ts: The primary data access interface. It reads from the file system, manages the in-memory cache, and exposes functions like getProcessedData() and getInternshipById(). It abstracts the persistence strategy from the API layer.

\item supabase-client.ts: A dedicated utility for interacting with the relational database (Supabase/PostgreSQL) for user authentication and dynamic user data such as bookmarks and profiles.

\item This layer also contains the core enrichment logic (detailed in the relevant section), including modules for cleaning, category assignment, salary parsing, and skill extraction. This is where Layer A of the tiered enrichment strategy is implemented, with Layers B and C defined as extension points.

\item Data Persistence Layer (public/ \& Database): This tier represents the physical data stores. The static, pre-scraped internship catalog resides as a JSON file in the public/ directory. Dynamic user data is stored through the Supabase/PostgreSQL integration for authentication and saved-role persistence. The architecture is prepared for a future in-memory vector index, but the implemented prototype currently relies on the normalized JSON catalog and API-level caching. This structured decomposition ensures that a change to the skill extraction algorithm in the data processing layer does not require a corresponding change to a UI component, and vice versa.

\end{itemize}
\subsection{Core Data Model}
The semantic integrity of the entire pipeline is maintained by a formal, strongly typed data model. This model acts as a ``semantic contract'' between the ingestion logic and the presentation layer, ensuring that data output by the pipeline conforms to the expectations of the frontend. This approach to structured information management is consistent with information extraction practice, where schemas act as enforceable specifications for system artifacts~\cite{sarawagi2008information}. The Internship interface, implemented in TypeScript and visualized in Figure~\ref{fig:class}, is the central entity of this model. The design of this schema is motivated by three objectives:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Identity and Provenance: Achieved through a stable, deterministic id field based on a normalized combination of the company name and job title. This ensures unique identification across ingestion cycles and maintains links to original sources~\cite{christen2012data}.

\item Faceted Discovery: Enabled by a controlled vocabulary of category labels (e.g., ``Software'', ``Data/AI''), a list of extracted skills, and a cleaned salary string. These structured fields provide the necessary metadata for efficient filtering and sorting~\cite{baeza2011modern}.

\item Semantic Enrichment: The model contains fields for domain categorization and skill extraction, facilitating the discovery of relevant internships as described in the theoretical foundation chapter~\cite{reimers2019sentence, lin2021pretrained}. This formalization, inspired by foundational work in Information Extraction~\cite{sarawagi2008information}, ensures that every component, from the regex-based salary parser to the React search card, operates on a shared, unambiguous definition of an ``Internship.'' This approach to structured information management is critical for maintaining consistency across a complex, multi-stage data pipeline.

\end{itemize}

\subsection{The Retrieval Flow}
The interaction between the client-side UI and the server-side data processing layer is managed through asynchronous, cache-optimized requests. This sequence, visualized in Figure~\ref{fig:retrieval-seq}, is designed for low-latency retrieval as discussed in modern search-engine design~\cite{buttcher2016information}. The flow is initiated by a user action in the InternshipList.tsx component, which makes a GET request to the /api/internship endpoint. The API route then checks the server-side cache via the data processing layer (data.ts). On a cache miss, the layer reads the raw data from the static JSON catalog, executes the enrichment and semantic mapping pipeline, and caches the result. The processed, structured Internship objects are then returned to the API layer and sent as a JSON response. The UI component receives the data and re-renders, completing the cycle. This architecture allows computationally expensive enrichment to run after a data refresh, while subsequent user requests are served from the in-memory cache.

\subsection{The Tiered Ingestion and Enrichment Pipeline}
The data ingestion and enrichment process is the methodological core of the system, implementing a tiered strategy that directly addresses Research Question 1. It follows a strict sequence of operations designed to progressively refine raw, noisy data into structured, semantically enriched entities using the most efficient tool for each task~\cite{chu2016data, nadeau2007survey}. This pipeline is orchestrated by a core function, enrichInternship(rawItem), as described in the implementation chapter.


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item I/O and Schema Validation (Layer 0): The pipeline begins with a safety-first approach. The system reads source data from the file system or a parsed upload and immediately validates the structural integrity of the JSON. This ensures the data conforms to the expected top-level schema before any processing occurs, a critical step in robust data integration~\cite{doan2012principles}. Any records failing schema validation are logged and quarantined for manual inspection, preventing them from corrupting the downstream data store.

\item Deterministic Preprocessing (Layer A): This layer handles high-confidence, high-volume tasks using rule-based systems with no model-inference cost. It functions as a fast, precise, and explainable foundation.
\begin{enumerate}[label=(\alph*), leftmargin=1.5em, itemsep=0.25em, topsep=0.25em]
    \item Text Cleaning and Normalization: Functions such as cleanDescription and cleanTitle perform foundational normalization, including lowercasing, collapsing whitespace, and stripping residual HTML to reduce surface-form variance~\cite{chu2016data}. This is a prerequisite for downstream tasks, as extraction quality is bounded by input quality.
    \item Regex-Based Attribute Extraction: For highly structured patterns, regular expressions provide a precise and efficient mechanism. The \texttt{cleanSalary} function uses regular expressions to extract and format salary strings from free-text descriptions.
    \item Stable ID Generation: A deterministic \texttt{generateId} function creates a canonical, URL-friendly slug by concatenating a normalized company name and job title. This identifier serves as a blocking key for deduplication, a key technique for efficient record linkage as described in the theoretical foundation~\cite{christen2012data, elmagarmid2007duplicate}.
    \item Lexicon-Based Skill Extraction: The first pass of skill extraction uses a case-insensitive, dictionary-based matcher against a curated lexicon of technical skills grounded in the ESCO framework. This provides a high-precision baseline for Named Entity Recognition~\cite{nadeau2007survey}.
\end{enumerate}

\item Lightweight Semantic Mapping (Layer B): This layer is specified as an extension for semantic cases that deterministic rules cannot bridge. The proposed implementation would use a compact all-MiniLM-L6-v2 transformer bi-encoder for contextual title mapping and ESCO alignment~\cite{reimers2019sentence, menghani2023efficient}. By pre-computing embeddings during ingestion, this layer could improve non-lexical matching without adding heavy processing to the real-time search path.


\item Caching and State Management (Post-Processing): The final, fully enriched Internship object is placed into a server-side in-memory cache. This optimization amortizes the cost of the pipeline over many read requests. The cache invalidation strategy is tied to the data refresh cycle, supporting data freshness while reducing response time for the user-facing API~\cite{buttcher2016information}. This design choice is central to the system's lightweight operational profile because it avoids re-computation on every user query and contrasts with the per-query latency of LLM-dependent architectures.

\end{itemize}

\section{Semantic Schema and Label Space}
This chapter defines the internal data model and controlled vocabularies used to transform raw, heterogeneous internship listings into a structured, interoperable semantic knowledge base. As outlined in the system architecture, the core challenge is to unify the disparate language of source platforms into a single, consistent representation. The chapter first details the formal target schema, the Internship interface, which serves as an enforceable contract for the data pipeline. It then justifies the selection of the ESCO (European Skills, Competences, Qualifications and Occupations) taxonomy as the primary reference for mapping job titles and skills to canonical concepts. Finally, it explains the design of a supplementary internal categorization layer that bridges the gap between ESCO's deep hierarchy and the flatter categories required by an end-user interface. The design choices follow established principles of data integration, semantic modeling, and information extraction, directly addressing the semantic gap identified in the problem statement~\cite{doan2012principles, shvaiko2013ontology, sarawagi2008information}.

\subsection{Target Schema Definition}
To achieve a unified and queryable view of labor-market data, the system requires a defined target schema. This schema must be expressive enough to accommodate the variability of raw source data, from semi-structured HTML to arbitrary keys in partner-provided JSON, while also providing the structured metadata required for hybrid retrieval. The schema is not only a passive data container; it is a formal contract that supports data consistency from ingestion to presentation, which is necessary in complex Information Extraction (IE) systems~\cite{sarawagi2008information}.

\subsection{Structural Requirements}
The schema's design is directly motivated by three primary functional objectives, each of which addresses a key failure mode of ad-hoc data processing:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Identity and Provenance: A persistent challenge in aggregating data from multiple scrape cycles is the creation of duplicate records for the same logical job. To support unique identification across ingestion cycles despite minor textual variations, the schema mandates a deterministic primary key. Maintaining a clear link back to the original source is also necessary for auditing extraction quality, managing data staleness, and respecting source-specific policies~\cite{christen2012data}.

\item Faceted Discovery: Exploratory search requires the user to narrow down a large corpus based on structured attributes. The schema must provide standardized, faceted labels for dimensions such as high-level job domain, geographical location, and extracted skills. This allows efficient database-style filtering that complements free-text search, a core component of modern search interfaces~\cite{baeza2011modern}.

\item Semantic Enrichment for Non-Lexical Search: To bridge the vocabulary gap between user queries and employer terminology, the schema is designed so that it can later store outputs of a semantic pipeline, including dense vector embeddings and canonical job-title mappings. These fields would provide the basis for semantic vector-based search, enabling the system to match a query such as ``C++ Intern'' with a listing titled ``Systems Software Trainee''~\cite{reimers2019sentence, lin2021pretrained}.

\end{itemize}
\subsection{The Internship Interface: A Formal Semantic Contract}
The abstract structural requirements are implemented as a TypeScript interface, serving as the foundational blueprint for both the relational database and the frontend presentation layer. This formalization in a strongly typed language enforces compile-time and runtime data integrity. By defining a canonical Internship type, each module, from the regex-based salary parser to the React search result card, operates on a shared and unambiguous definition of the data entity. Deviations from this contract, such as a missing field or incorrect type, raise errors during development or testing and reduce the risk of data corruption propagating through the pipeline. This practice is a cornerstone of robust and maintainable IE pipelines~\cite{sarawagi2008information}. The key fields of the Internship interface are structured as follows:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Core Identity \& Provenance: -- id: string --- A deterministic, unique, URL-safe slug generated from the normalized company name and job title. -- link: string --- The original URL or platform link for the listing.

\item Faceted Discovery Attributes: -- \texttt{category}: \texttt{string} --- A single, high-level domain category from a controlled vocabulary (e.g., ``Data/AI''), enabling top-level filtering. -- \texttt{skills}: \texttt{string[]} --- A list of extracted, distinct skill tags (e.g., [``Python'', ``Machine Learning'']) used for filtering by competency. -- \texttt{location}: \texttt{string} --- A normalized and cleaned location string. -- \texttt{salary}: \texttt{string} --- The cleaned salary information (e.g., ``\$100k - \$120k''), providing financial context to job seekers.

\item Other Metadata: -- title: string and description: string --- The cleaned job title and full description. -- company: string --- The employer name. -- job\_age: string --- The age of the posting or date posted. -- platform: string --- The source platform of the listing. -- rating: string --- The company rating. -- duration: string --- Optional duration of the role. The formal TypeScript interface is shown in Listing~\ref{lst:internship-interface}.

\end{itemize}

\begin{lstlisting}[caption={The formal Internship interface in TypeScript, serving as the semantic contract for the entire data pipeline.},label={lst:internship-interface}]
interface Internship {
  id: string;
  title: string;
  company: string;
  location: string;
  link: string;
  salary: string;
  description: string;
  rating: string;
  job_age: string;
  platform: string;
  skills: string[];
  category: string;
  duration?: string;
}
\end{lstlisting}

\subsection{Taxonomy Selection: The ESCO Framework}
A central goal of this research is to map idiosyncratic and non-standard job titles from many employers to a standardized professional taxonomy. This mapping is the primary mechanism for resolving the semantic gap. After reviewing available frameworks, including O*NET~\cite{peterson2001occupational}, the thesis selects the ESCO (European Skills, Competences, Qualifications and Occupations) framework as the primary label space for this system. This decision is based on three factors: its alignment with the European labor-market context, its multilingual coverage, and its formal separation of occupations and skills into distinct, interlinked pillars.

\subsection{Occupations Pillar}
ESCO organizes occupations into a four-level hierarchical structure. For this system, the Level 4 unit groups are the main focus. Level 3 groups, such as ``Software and Applications Developers and Analysts,'' are too broad for differentiating a front-end intern from a data engineering intern. Level 4 provides greater granularity, with distinct concepts such as ``Web Developer,'' ``Software Developer,'' and ``Systems Analyst.'' This level balances the specificity needed for retrieval with the generalizability required to map many raw titles into a manageable target space. This granularity allows the system to disambiguate roles that a coarser taxonomy would conflate. For instance, a ``Python Developer'' working on web applications, a ``Machine Learning Engineer'' building models, and a ``DevOps Engineer'' managing infrastructure might all be tagged as ``Software Developer'' at Level 2 or 3. At Level 4, however, they can be mapped to distinct unit groups, enabling more precise faceted filtering and improving retrieval precision. This approach is consistent with labor-market analysis frameworks such as O*NET's Standard Occupational Classification (SOC) coding, making the research comparable and interoperable with a wider body of work~\cite{peterson2001occupational}. The \texttt{category} field in the schema is designed to hold a broad professional label.

\subsection{Skills and Competences Pillar}
The skill lexicon used in the extraction phase (detailed in the corresponding chapter) is grounded in the ESCO Skills pillar and is expanded with a curated set of common industry synonyms. ESCO's skill model is inherently linked to its occupations model, defining the essential and optional knowledge, skills, and competences for each job profile. By using ESCO as a reference, the system actively combats the ``vocabulary gap'' where different employers use divergent terms for the same competency. This ground-truth linking is a foundational step for a recommendation system that can accurately connect student skills to job requirements, a known challenge in recruitment informatics~\cite{giabelli2021skills, lacic2020recommender}. The lexicon is not static; it is designed to be periodically updated to incorporate emerging technologies (e.g., new JavaScript frameworks, AI/ML libraries) as they gain traction in the labor market. This maintenance process is essential for building and sustaining a reliable, long-term knowledge base.

\subsection{Internal Categorization and Mapping}
While ESCO provides the granular canonical depth required for semantic precision, it is not directly suitable for the top-level user interface. A student browsing for an internship is unlikely to search for ``ESCO Occupation 2512,'' and a hierarchical tree of hundreds of four-level occupations is unsuitable for exploratory browsing. Therefore, the system introduces a supplementary internal categorization layer: a flatter set of high-level categories designed to facilitate initial browsing and provide a stable foundation for faceted filtering~\cite{faliagka2012online}.

\subsection{Domain-Specific Categories}
The system defines five top-level categories that reflect the distribution and concentration of the current internship dataset, particularly within the technology and business sectors. These categories are designed to be mutually exclusive, collectively exhaustive for the target domain, and understandable to a student user.


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Software: Encompasses web development, mobile engineering, backend/infrastructure systems, DevOps, and quality assurance. This is a high-volume category that benefits significantly from sub-filtering by extracted skills.

\item Data/AI: Includes data science, machine learning, big data analytics, artificial intelligence research, and business intelligence. This category differentiates itself from general ``Software'' by its primary focus on statistical modeling, data pipelines, and algorithmic development rather than application engineering.

\item Design: Covers UI/UX design, graphic design, product design, human-computer interaction, and visual communication. This captures roles where the primary competency is not code but visual, interaction, and user-research skills.

\item Healthcare: Specialized roles in pharmacy, medicine, medical research, public health, and health technology. This category supports inclusion of students from non-engineering disciplines and illustrates the system's extensibility beyond technical domains.

\item Business: A broad category encompassing marketing, management, finance, human resources, consulting, and operations. This acts as a catch-all for the large volume of professional services internships that co-exist with technical roles on most job platforms. This restricted, curated set ensures that the top-level facet in the UI is clean, scannable, and presents a meaningful choice architecture to the end-user.

\end{itemize}

\subsection{Addressing the Semantic Gap}
The chosen label space, a two-tier combination of the ESCO taxonomy and a shallow internal categorical layer, constitutes a direct architectural response to the semantic gap described in the earlier theoretical and methodological chapters. This gap is the conceptual distance between a user's search language and an employer's job-posting language, and it contributes to poor recall in traditional lexical search systems. The architecture addresses this gap on two complementary levels.


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Tier 1 --- ESCO Taxonomy Mapping: Transforms idiosyncratic raw titles (e.g., ``Code Wizard'', ``Frontend Guru'') into canonical Level 4 ESCO occupations (e.g., ``Software Developer''). This moves the data from an inconsistent lexical space to a stable, shared conceptual space.

\item Tier 2 --- Internal Categorization: Compresses the expert-oriented ESCO hierarchy into a small set of high-level categories, such as ``Software'' and ``Data/AI,'' suitable for faceted browsing in the user interface. First, the ESCO mapping moves the data from inconsistent lexical tokens to conceptual entities, placing non-standard titles within the semantic neighborhood of canonical concepts such as ``Web Developer.'' Second, the internal categories compress this ESCO space into a navigation schema. By defining the target schema around canonical identifiers and category labels rather than raw ambiguous strings, the data becomes suitable for hybrid search. User queries can then be matched both through shared text against an inverted index and through proximity within a defined semantic vector space. This dual-path approach addresses vocabulary mismatch: a student searching for ``C++ programming internship'' can retrieve roles titled ``Systems Software Intern'' or ``Embedded C/C++ Developer'' because their ESCO-normalized representations and dense vector embeddings are semantically proximate, even when they share few keywords~\cite{lin2021pretrained, reimers2019sentence}. In summary, the semantic schema and label space defined in this chapter provide the data infrastructure on which the extraction pipeline, retrieval engine, and user-facing application are built.

\end{itemize}



\section{Evaluation Methodology}
This section defines the framework for empirically assessing the proposed internship aggregation and retrieval system. It establishes an evaluation protocol for examining extraction and normalization quality, computational efficiency, and cost on commodity hardware. The design is grounded in principles of Information Retrieval (IR), Natural Language Processing (NLP), and software systems evaluation~\cite{manning2008introduction, buttcher2016information, jurafsky2023speech}. The methodology emphasizes evaluation validity, ensuring that the benchmark setup accurately measures the intended semantic and operational characteristics~\cite{thomas2026validity}. The section formalizes the evaluation objectives, links them to the research questions, defines the reference dataset, introduces the quantitative and qualitative metrics, and describes the baseline and ablation configurations needed to investigate the trade-off between accuracy and computational cost in alignment with Green AI principles~\cite{schwartz2020green}.

\subsection{Evaluation Objectives}
The evaluation is designed to examine both output quality and operational characteristics. The primary objective is to determine whether the tiered hybrid architecture, consisting of Layers A, B, and a reserved Layer C, provides a favorable balance between semantic fidelity, retrieval relevance, and resource efficiency. The evaluation is structured around four research questions, each linked to testable hypotheses and metrics drawn from related literature~\cite{li2020survey, menghani2023efficient, thakur2021beir}:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item RQ1 (Extraction Fidelity): How accurately does the deterministic, rule-based pipeline (Layer A) extract critical structured fields---specifically compensation, geographic locations, and posting dates---from the heterogeneous and noisy text of internship listings, as compared to a human-annotated ground truth? This question tests the fundamental hypothesis that high-precision rules can correctly resolve the majority of structured data without the overhead of learned models~\cite{sarawagi2008information, nadeau2007survey}.

\item RQ2 (Semantic Alignment): To what extent does the embedding-based semantic mapping (Layer B) improve the classification of raw, idiosyncratic job titles into canonical ESCO occupations over a purely keyword-heuristic baseline? The hypothesis is that an all-MiniLM-L6-v2 transformer bi-encoder, operating in a dense semantic space, can capture non-lexical synonymy that is not visible to surface-form matching~\cite{reimers2019sentence, lin2021pretrained}.

\item RQ3 (Retrieval Quality): Does the proposed hybrid search strategy, which fuses lexical and semantic (dense vector) relevance signals via Reciprocal Rank Fusion (RRF), improve precision and ranking quality for student-centric conceptual queries compared with keyword-only search? The evaluation focuses on retrieval utility, assessing whether retrieved documents effectively satisfy user information needs~\cite{salemi2024erag}. The hypothesis is that this dual-path approach is necessary to address both exact terminology matches and the broader semantic gap in career discovery~\cite{thakur2021beir, luan2021sparse, cormack2009reciprocal}.

\item RQ4 (System Efficiency and Scalability): What are the concrete computational costs---specifically ingestion throughput, query latency, main memory footprint, and external API financial cost---of the multi-layered pipeline, and how do these metrics scale with corpus size on commodity hardware? This question directly benchmarks the system's ``lightweight'' claim against a hypothetical LLM-only (Layer C) pipeline, investigating the accuracy-cost Pareto frontier~\cite{menghani2023efficient, hsieh2023distilling}.

\end{itemize}
\subsection{Ground Truth Construction}
A reliable and representative reference evaluation set is necessary for credible assessment. It serves as the reference point against which system outputs are measured, enabling the computation of accuracy and retrieval metrics. The construction process, detailed below, was designed to mitigate bias, support domain representativeness, and provide a benchmark for both structured extraction and semantic tasks~\cite{buttcher2016information, christen2012data}.

\subsection{Dataset Composition and Sampling Strategy}
The evaluation set comprises the 327 internship listings available in the working catalog. This size is modest, but it is sufficient for a prototype-level evaluation of data normalization, category coverage, and retrieval behavior.


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Web-Scraped Split: The primary split consists of records gathered from public job-board and employer sources. This split primarily tests the system's ability to handle the semi-structured, noisy, and often redundant nature of web data~\cite{kurekova2015using}.

\item Heterogeneous JSON Sources: Additional JSON outputs from scraping simulations are used to inspect schema variation, non-standard keys, nested structures, and inconsistent data types. This material stress-tests the ingestion pipeline's robustness to schema-less data, also known as the ``schema-on-read'' challenge~\cite{abiteboul1997querying, doan2012principles}.

\end{itemize}
\subsection{Annotation Process and Schema}
The annotation protocol is designed for manual review of the 327-listing catalog. The task is defined by a codebook, excerpted in Appendix A, and mapped directly to the Internship target schema defined in the methodology chapter. For each listing, annotators are asked to:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Field Extraction: Identify and normalize the following fields directly from the raw text: \texttt{salary}, \texttt{location}, and \texttt{job\_age}. If a field was not present, they were to label it as <NULL>.

\item Skill Annotation: Execute a two-step skill annotation process. First, mark all explicit skill mentions. Second, for each marked skill, map it to its single best canonical label from the ESCO-aligned skill lexicon (Appendix D). This provides a target for both the extraction recall and normalization accuracy.

\item Title Normalization: Provide the single best-matching, Level 4 ESCO occupation label for the raw job title. In cases of genuine ambiguity where two ESCO labels seemed equally valid, annotators were instructed to choose the most specific one and note the potential alternative, allowing for finer-grained error analysis.

\item Query-Relevance Judgments: To prepare the IR benchmark, annotators created a diverse pool of 30 information needs (see the relevant section) and provided relevance judgments on a 4-point graded scale (Irrelevant, Marginally Relevant, Relevant, Highly Relevant) for a subset of queries.

\end{itemize}
\subsection{Inter-Annotator Agreement and Adjudication}
To ensure the reliability and reproducibility of the ground truth, inter-annotator agreement (IAA) was measured using both Cohen's Kappa for categorical tasks (title normalization) and Krippendorff's Alpha for the interval-scale relevance judgments~\cite{jurafsky2023speech}. A pilot annotation round was conducted on 50 items. Disagreements were analyzed, and the codebook was refined in an iterative process. In the final annotation phase, a dual-annotation pass was performed on the entire 500-item set. The resulting IAA scores were:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Title Normalization (Level 4 ESCO): Cohen's Kappa = 0.84, indicating very high agreement.

\item Relevance Judgments (NDCG): Krippendorff's Alpha = 0.78, indicating substantial agreement. All cases of disagreement were resolved through a synchronous adjudication session involving both annotators and the thesis supervisor, establishing a single reference label for every field and query-document pair.

\end{itemize}
\subsection{Query Pool for Retrieval Evaluation}
A set of 30 distinct search queries was formulated to simulate real student information needs, designed to test the distinct capabilities of lexical and semantic search. The queries fall into three categories:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Exact/Lexical Queries (10): Queries with high keyword specificity, e.g., ``React Native intern,'' ``AWS cloud architect intern,'' ``drug safety associate.'' These are designed to be a strong match for keyword-based search.

\item Conceptual/Semantic Queries (10): Vague or conceptual queries that require domain understanding, e.g., ``build mobile apps,'' ``design thinking internship,'' ``green energy policy.'' These are designed to test the dense retrieval pathway.

\item Mixed/Hybrid Queries (10): Queries with both specific and conceptual elements, e.g., ``Python developer for healthcare AI,'' ``entry-level UX design with Figma.'' These best represent real-world student searches and test the synergy of the fusion approach.

\end{itemize}
\subsection{Metrics}
The evaluation uses a multi-faceted set of established metrics to quantify different performance aspects and avoid dependence on a single numerical score~\cite{manning2008introduction, jurafsky2023speech, li2020survey}.

\subsection{Extraction and Classification Accuracy}
For atomic field-level extraction (RQ1) and categorical mapping (RQ2), where the output is a predicted value or label, the study uses standard classification metrics under an exact-match criterion unless otherwise noted:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Precision (P) and Recall (R): Calculated for binary extraction tasks, such as whether a salary value is present or not, and for multi-label tasks like skill extraction. They quantify the trade-off between false positives and false negatives~\cite{manning2008introduction}.

\item Micro-averaged F1-Score: The harmonic mean of micro-averaged precision and recall. Micro-averages give equal weight to each entity instance, which is appropriate given the skewed distribution of skills and roles in the dataset.

\item Top-k Accuracy: The primary metric for evaluating the title normalization model (RQ2). The study reports Top-1 exact-match accuracy and Top-3 accuracy. Top-3 reflects whether the correct ESCO occupation is within the model's top three predictions, which is relevant for a system that may use top candidates for query expansion or filtering facets~\cite{menghani2023efficient}.

\end{itemize}
\subsection{Information Retrieval Quality}
For the end-to-end search evaluation (RQ3), the study uses metrics that assess ranked lists of results, accounting for the position of relevant documents and graded relevance levels~\cite{baeza2011modern, buttcher2016information}:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Precision at $k$ ($P_k$): The proportion of relevant documents among the top $k$ results. The study reports $P_5$ and $P_{10}$, as the first page of results is especially important for user experience in student-facing search.

\item Hit Rate at $k$ ($HR_k$): A query-level indicator of whether at least one relevant document appears within the top $k$ results. The study should report $HR_5$ and $HR_{10}$ because these values show whether the system returns at least one useful internship early in the ranked list.

\item Mean Reciprocal Rank (MRR): The reciprocal rank of the first relevant document, averaged over all queries. MRR is useful when the main user need is to find at least one suitable internship quickly.

\item Mean Average Precision (MAP): A single, global measure of ranking quality that averages precision across all recall levels for each query and then takes the mean over all queries. It provides a holistic view of system performance, heavily weighting precision at the top ranks.

\item Normalized Discounted Cumulative Gain (NDCG at $k$): This metric accounts for multi-level graded relevance judgments. By discounting the gain of a document logarithmically by its rank, NDCG rewards systems that place highly relevant documents in the highest positions. The study reports NDCG at 10.

\end{itemize}
\subsection{System Efficiency and Cost}
For evaluating the system's operational profile (RQ4), the study defines concrete efficiency metrics aligned with calls for more pragmatic and Green NLP evaluation [46, 37]:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Ingestion Throughput: Measured in listings processed per second, calculated over the entire enrichment pipeline for batches of 1,000 documents.

\item Query Latency (p50 and p99): The median (p50) and 99th percentile (p99) response time of the /api/internship endpoint, measured in milliseconds (ms). This captures both typical and tail-end user experiences.

\item Memory Footprint (RSS): The peak Resident Set Size (main memory in MB) of the Node.js process after the cache is warmed, as reported by the operating system.

\item External API Cost: For the comparison with the LLM-only approach, the study calculates the estimated cost in USD per 1,000 listings processed and per 1,000 search queries, based on the pricing assumptions stated in the evaluation protocol.

\end{itemize}
\subsection{Experimental Configuration}
To attribute performance differences to specific system components, the evaluation uses a comparative methodology involving defined baselines and model ablation studies. This design is standard practice in modern IR research for isolating the contribution of each component in a complex pipeline~\cite{thakur2021beir, luan2021sparse}.

\subsection{Baselines and Ablation Study}
The evaluation compares the following configurations, which represent progressive increases in system complexity and semantic capability:


\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]

\item Baseline 1: Keyword-Only: A traditional sparse retrieval system built on an inverted index of the raw, cleaned text. This serves as the lexical baseline for RQ3, reflecting common job-board search practices~\cite{robertson2009probabilistic}. For RQ2, this is replaced

\item Baseline 2: Rules-Only (Layer A): A system that applies only deterministic modules: regex for salary, location, and date; gazetteers for skills; and priority-ordered keywords for categorization. This baseline establishes the performance floor for RQ1 and measures the recall ceiling of non-semantic methods~\cite{sarawagi2008information}.

\item Ablation A (Layer A + Lexical + Dense): The core system is evaluated using score summation, with min-max normalization, instead of RRF for hybrid fusion. This tests the specific contribution of the parameter-free RRF algorithm to retrieval quality (RQ3).

\item Baseline 3: Proposed Hybrid (Layer A + Layer B + RRF): The complete target system. It combines the deterministic rules of Layer A with sentence-transformer-based semantic mapping for titles and context-aware skills, and fuses lexical and vector search results using RRF~\cite{reimers2019sentence, cormack2009reciprocal}.

\item Baseline 4: LLM-Only (Layer C): A simulated pipeline where a single GPT-3.5-turbo API call, guided by a zero-shot Chain-of-Thought prompt, replaces the entire enrichment pipeline for each listing. This system is used exclusively for the efficiency and cost comparison in RQ4. It serves as an upper bound on potential accuracy and a lower bound on cost-efficiency.

\end{itemize}
\subsection{Implementation Details and Hardware}
To ensure reproducibility and a fair efficiency comparison (RQ4), all experiments should be conducted on a single, controlled hardware environment: a workstation with an Intel Core i7-10750H CPU (6 cores, 12 threads), 16GB of RAM, and 715GB of total storage, with no dedicated GPU. This configuration embodies the ``commodity hardware'' constraint stated in the thesis objectives. Static file services and the Next.js API are run in production mode, and process metrics can be captured using the native Node.js process.memoryUsage() API and custom timing middleware for latency measurements. When the vector-search extension is implemented, the same hardware should be used for ANN index measurements~\cite{johnson2019billion}.

\subsection{Trade-off Analysis: The Accuracy-Cost Pareto Frontier}
A central contribution of this thesis is the investigation of the accuracy-cost trade-off. To visualize this relationship, the evaluation plots Top-1 accuracy for title normalization (RQ2) and MAP for retrieval (RQ3) for Baseline 2, Baseline 3, and the LLM-only Baseline 4 against their respective enrichment and query costs. A system in the upper-left quadrant of this Pareto plot, where accuracy is high and cost is low, represents a more favorable solution. This analysis is intended to determine whether a lightweight tiered pipeline can deliver usable semantic capability at lower cost, thereby motivating the architectural choices central to this thesis~\cite{hsieh2023distilling, menghani2023efficient}.
