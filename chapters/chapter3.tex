\chapter{Technological Environment and Development Tools}

\section{Chapter Introduction}
This chapter identifies the technological environment that supports the proposed system. Its purpose is not to repeat the theoretical discussion from Chapter 2, but to clarify the practical tools, platforms, and development components used to implement the semantic internship-search pipeline. The chapter is organized around the application layer, backend and persistence layer, data representation layer, natural-language-processing tools, retrieval infrastructure, and evaluation environment.

\section{Application Development Environment}
The application environment provides the interaction point between the student user, the internship catalog, and the semantic retrieval pipeline. The available implementation evidence identifies a React-based presentation layer and a Next.js API layer; accordingly, this chapter describes that verified stack rather than an alternative mobile-client stack.

\subsection{Presentation-Layer Technologies}
The presentation layer is responsible for displaying searchable internship records, filters, and detail views. Its academic role in the thesis is to make the structured output of the enrichment pipeline accessible to users through a controlled interface.

\subsubsection{React-Based User Interface}
The current implementation text identifies a React-based user interface located under the application components. This layer renders internship cards, search results, and interactive filtering controls while remaining separated from the data-processing modules.

\subsubsection{Client-Side Interaction Flow}
The client-side interaction flow begins when a student submits a query or applies a filter. The interface sends the request to the API layer and updates the displayed internship list after receiving structured JSON data. This separation supports maintainability because user-interface changes can be made without altering the extraction and ranking logic.

\subsection{API and Communication Layer}
The communication layer provides the interface between the client application and the processed internship data. It is implemented through Next.js API routes in the current source material.

\subsubsection{Next.js API Routes}
The route endpoint acts as a stable access point for internship search and retrieval. It receives requests, delegates data access to the processing layer, applies cache policy when relevant, and returns structured JSON responses.

\subsubsection{JSON-Based Data Exchange}
JSON is used as the exchange format between the API layer and the client application. This choice is consistent with the internship catalog format and with the TypeScript interface used to define the Internship entity.

\section{Database and Persistence Technologies}
The persistence environment combines static catalog storage with relational database support. This hybrid organization reflects the distinction between relatively stable internship listings and dynamic user-specific data.

\subsection{Hybrid Persistence Architecture}
The system uses local JSON storage for the main catalog and Supabase/PostgreSQL for dynamic data. This organization keeps the read-heavy catalog simple while retaining transactional database support for user-related features.

\subsubsection{Static Catalog Storage}
The static catalog stores the pre-scraped internship listings in a JSON file. This file-based layer supports reproducible ingestion, straightforward version control, and rapid loading during the preprocessing stage.

\subsubsection{Supabase and PostgreSQL}
Supabase provides a managed PostgreSQL backend for relational persistence. In the thesis architecture, this layer supports dynamic user state, metadata, and database-backed functionality that requires stronger transactional guarantees than a static file can provide.

\subsubsection{pgvector Extension}
The pgvector extension is relevant to the semantic-search component because it enables dense vector storage and similarity operations inside PostgreSQL. It therefore provides a database-level foundation for combining structured metadata with embedding-based retrieval.

\section{Data Representation and Type-Safety Tools}
The system requires a stable representation of internship records so that extraction, storage, retrieval, and display operate on the same semantic contract.

\subsection{TypeScript Data Interfaces}
The Internship interface defines the expected fields of an internship record, including title, company, location, salary information, skills, category labels, canonical title, and embedding-related fields. This interface reduces ambiguity between modules and supports development-time validation.

\subsection{Structured Internship Records}
The structured record format transforms heterogeneous scraped data into a consistent representation. This format is essential because retrieval metrics, filtering behavior, and result presentation all depend on stable field names and normalized values.

\section{Natural-Language Processing and Semantic Tools}
The semantic layer uses lightweight NLP tools to bridge the vocabulary gap between employer descriptions and student queries.

\subsection{Transformer-Based Semantic Components}
Transformer-based models are used as lightweight semantic components rather than as uncontrolled end-to-end generators. The manuscript refers to compact transformer models such as DistilBERT and Sentence-BERT as tools for contextual mapping and embedding generation.

\subsubsection{DistilBERT and Lightweight Transformer Models}
DistilBERT represents the class of compact transformer models used to reduce computational cost while preserving useful contextual representations. In this thesis, such models motivate Layer B, which is reserved for semantic cases that deterministic rules cannot resolve.

\subsubsection{Sentence-BERT Embeddings}
Sentence-BERT supports efficient sentence-level embeddings through a bi-encoder architecture. This makes it suitable for comparing internship titles, descriptions, and canonical labels without running a full cross-encoder over every query-document pair.

\section{Indexing and Retrieval Technologies}
The retrieval environment combines lexical and semantic access mechanisms. This reflects the thesis argument that internship discovery requires both exact technical-term matching and semantic similarity.

\subsection{Lexical Retrieval Tools}
BM25 provides the lexical retrieval baseline. It is used to represent exact keyword matching and remains important for precise skill names, company names, and technical acronyms.

\subsection{Vector-Based Search Tools}
Vector search supports semantic matching by comparing dense embeddings. In the thesis architecture, dense retrieval is connected to embedding generation, HNSW indexing, and similarity search over pre-computed vectors.

\subsubsection{HNSW Approximate Nearest-Neighbor Search}
HNSW provides an approximate nearest-neighbor indexing strategy for efficient vector retrieval. Its role is to make dense semantic search practical at catalog scale.

\subsubsection{Hybrid Fusion with Reciprocal Rank Fusion}
Reciprocal Rank Fusion combines lexical and dense retrieval outputs using rank positions rather than raw scores. This makes it useful for integrating BM25 results with vector-search results without requiring fragile score normalization.

\section{Development, Testing, and Evaluation Environment}
The development environment must support repeatable ingestion, retrieval, and measurement. For this reason, the implementation chapter later records the controlled hardware assumptions and the logging or timing mechanisms used to measure throughput, latency, and memory behavior.

\subsection{Runtime and Hardware Environment}
The evaluation protocol uses a controlled workstation configuration and records process-level measurements. This supports reproducibility and prevents the empirical comparison from depending on unspecified infrastructure conditions.

\subsection{Measurement and Logging Tools}
The system requires logs for ingestion status, cache behavior, query latency, and error cases. These logs provide the evidence that students must use when completing the results chapter, especially for throughput, latency, HR@k, NDCG@k, and cost-comparison tables.

\section{Chapter Conclusion}
This chapter has separated the technological environment from the theoretical foundation. Chapter 2 explains the concepts behind the system, while Chapter 3 identifies the concrete tools and platforms that make implementation possible. The distinction is important for academic organization: theoretical material justifies the approach, whereas the technological environment documents the software stack, database layer, NLP tools, retrieval infrastructure, and evaluation support used by the project.
