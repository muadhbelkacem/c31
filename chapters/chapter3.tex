\chapter{Technological Environment and Development Tools}
\section{Chapter Introduction}
This chapter documents the concrete technological environment and development tools used to implement the proposed internship aggregation and semantic enrichment system. Its purpose is twofold. First, it provides a reproducible account of the software stack, libraries, infrastructure components, and development practices that support the implementation. Second, it establishes a clear separation from the theoretical foundations presented in Chapter 2: whereas Chapter 2 explains the concepts behind information extraction, semantic classification, and data normalization, this chapter identifies the specific tools used to realize those concepts in working software.
The chapter is organized into six main areas:
(1) frontend application technologies,
(2) data representation and storage mechanisms,
(3) the local semantic processing and enrichment environment,
(4) text processing and heuristic normalization tools,
(5) development, testing, and evaluation tooling,
(6) deployment considerations for automated data ingestion.
       Each section describes a specific layer of the technology stack, justifies the selection of tools relative to the system's lightweight and cost-aware design goals, and explains how the components interact.
\section{Application Development Environment}
TThe application environment provides the primary user interaction layer for students browsing internship listings, while also supporting authenticated account-specific functionality through the broader application infrastructure. Based on the implementation evidence, the system uses the Next.js framework (version 16.0.7) and React (version 19.2.1) for the presentation and application integration layers.
This architecture reflects modern hybrid web application design, combining efficient frontend rendering with backend integration for user-facing functionality \cite{riva2022realworld}. Next.js was selected because it supports React Server Components (RSC), provides a unified TypeScript development experience, and enables rapid prototyping without sacrificing production-grade reliability.
\subsubsection*{Next.js App Router and Server Components}
The application environment provides the primary user interaction layer for students browsing internship listings, while also supporting authenticated account-specific functionality through the broader application infrastructure. Based on the implementation, the system uses the Next.js framework (version 16.0.7) and React (version 19.2.1) for the presentation and application integration layers. This architecture reflects modern hybrid web application design, combining efficient frontend rendering with backend integration for user-facing functionality.
Next.js was selected for several interconnected reasons \cite{riva2022realworld}. First, its file-based routing and layout system aligns well with the structured internship data model, enabling clean separation between listing views, filtering interfaces, and detailed internship pages. Second, its strong TypeScript integration supports maintainable frontend development and safer component interaction. Third, the framework provides performance-oriented rendering and frontend optimization capabilities suitable for responsive web applications.
In local Chromium-based development testing, initial data-driven page loads typically ranged from approximately 0.6 to 2.5 seconds depending on caching state and data fetch conditions, while subsequent cached interactions exhibited significantly faster response times, often approaching near-instant frontend navigation and filtering behavior.
The main user interface components, organized according to the Next.js component architecture, include:
\begin{itemize}
\item InternshipList.tsx: Displays internship listings as structured cards containing title, company, location, salary information, and extracted skill metadata.
\item SearchBar.tsx: Provides free-text internship search functionality through frontend interaction mechanisms.
\item FilterPanel.tsx: Enables category, skill, and location-based filtering for internship exploration.
\item InternshipDetail.tsx: Presents the complete structured internship record, including cleaned metadata, description, extracted skills, and classification outputs intended for frontend consumption.
\end{itemize}
The frontend architecture follows a clear separation-of-concerns design in which presentation logic remains independent from the semantic enrichment pipeline. This separation improves maintainability, allowing user interface evolution without affecting the underlying internship classification, normalization, or enrichment processes.

\subsubsection*{Client-Side Interaction Flow}
The client-side interaction flow begins when a student enters a search query, applies filtering criteria, or changes the current listing page. The frontend operates over the production internship dataset generated by the offline enrichment pipeline. In this workflow, raw postings are collected by the scraper, processed through the local semantic enrichment pipeline, and exported as a production-ready JSON file consumed by the Next.js application.
After the dataset is loaded, the interface applies client-side search, filtering, and pagination logic over the enriched internship records. Filters such as category, skills, and location operate over structured metadata produced during enrichment, while pagination is handled within the frontend state and URL-based navigation mechanisms.
For interactive filtering operations, the frontend employs asynchronous request-management patterns where appropriate, including request cancellation mechanisms to prevent stale filtering results during rapid user interaction. This improves responsiveness when users rapidly modify filtering selections.
This architecture deliberately separates computationally expensive offline semantic processing from lightweight frontend interaction. Internship classification, normalization, skill extraction, deduplication, and domain enrichment are completed prior to deployment, while the frontend focuses exclusively on browsing, filtering, and presenting already-processed internship records. This separation improves maintainability and preserves responsive user interaction.

\subsection{API and Communication Layer}
The application communication layer supports authenticated frontend functionality and structured interaction between the user interface and backend application services. It is implemented using Next.js route handlers and integrated backend functionality within the same application environment.
This approach was selected over a separate backend framework (e.g., Express.js or Fastify) because it reduces deployment complexity, avoids maintaining an independent application server, and enables a unified development environment in which frontend and backend application logic can share common TypeScript definitions and data models.
Within the current architecture, this communication layer primarily supports account-related functionality, authenticated user interactions, and structured application data exchange, while the computationally intensive semantic enrichment pipeline remains an offline preprocessing stage external to the frontend application runtime.
This architectural separation supports the system's lightweight design goals by minimizing infrastructure complexity while preserving maintainability between the semantic processing pipeline and the user-facing web application.
\subsubsection*{Next.js API Routes}
The primary internship data endpoint, /api/internship/route.ts, provides structured access to processed internship records for the frontend application. Implemented using Next.js route handlers, this approach allows backend-integrated application functionality without requiring a separately deployed backend server, reducing infrastructure complexity and simplifying deployment.
Incoming frontend requests are handled through standard HTTP GET operations, with query parameters supporting search, filtering, and pagination interactions within the internship browsing workflow. Request handling is delegated through the application's data access layer (data.ts), which abstracts the underlying data source and allows the frontend application logic to remain decoupled from storage implementation details.
The internship discovery workflow operates over production-ready data generated by the offline semantic enrichment pipeline. Raw scraped postings are first processed externally through classification, normalization, deduplication, skill extraction, and domain enrichment before being exported as structured production data for application consumption.
To improve responsiveness during repeated access, the application employs lightweight caching mechanisms where appropriate, reducing unnecessary repeated data loading during frontend interaction.
This design preserves a clear separation between offline semantic processing and runtime application delivery, ensuring that computationally intensive enrichment remains outside the live web application request path.

\subsubsection*{JSON-Based Data Exchange}
JSON is used as the primary exchange format between the semantic enrichment pipeline, the application data layer, and the client-facing frontend. This choice is consistent with the native format of the processed internship catalog (intern\_data.json) and aligns naturally with the TypeScript data models used by the frontend application.
Using a uniform serialization format across storage, processing, and presentation simplifies the overall architecture and reduces the risk of schema drift between system components. The frontend application relies on structured TypeScript interfaces to ensure consistency in the handling of internship records, helping detect mismatches between expected and received data structures during development.
This approach supports lightweight interoperability between the offline Python enrichment pipeline and the web application layer without requiring more complex inter-process communication or dedicated database serialization layers.
\section{Database and Persistence Technologies}
The system employs a hybrid persistence architecture that balances efficient read-heavy access to the internship catalog with the transactional requirements of user-specific application data. This design reflects a deliberate architectural trade-off: the internship catalog is relatively static between scheduled enrichment updates and primarily optimized for browsing and filtering operations, whereas user-specific data such as authentication state, saved preferences, and account-linked interactions require persistent transactional storage.
This separation allows the system to maintain lightweight delivery of processed internship records while preserving robust persistence guarantees for authenticated user functionality.
\subsubsection*{Static Catalog Storage}
The primary internship catalog resides in public/intern\_data.json. This file is generated by the semantic enrichment pipeline (described in Chapter 5) and contains cleaned, normalized, deduplicated, and semantically enriched internship records intended for frontend consumption \cite{doan2012principles, chu2016data}.
Using a single JSON file for the read-heavy internship catalog offers several advantages:
\begin{itemize}
\item Version control: The file can be tracked in Git, allowing rollback to previous catalog states and enabling reproducible experimentation across development iterations.
\item Rapid loading: During local Chromium DevTools testing, the production JSON catalog was commonly observed to load in approximately 250 ms under cached or local development conditions. This supports responsive internship browsing, although actual load times may vary depending on dataset size, cache state, and deployment environment.
\item Simplified deployment: The system can serve internship catalog data without requiring a database dependency for public internship browsing operations, reducing infrastructure complexity and deployment overhead.
\item Efficient caching: Because the internship catalog remains relatively compact compared with large-scale enterprise datasets, lightweight application-level caching can improve repeated access performance during normal frontend usage.
\end{itemize}
The JSON catalog functions as a portable serialized representation of the processed internship dataset, while user-specific dynamic application state remains delegated to the relational persistence layer.
\subsubsection*{Supabase and PostgreSQL}
Supabase (version 2.x) provides the managed PostgreSQL backend with built-in REST and realtime APIs for dynamic user-specific application functionality. In this architecture, Supabase stores application data that does not belong in the static internship catalog, including:
\begin{itemize}
\item User accounts and authentication credentials, managed through Supabase Auth with secure session management and access control
\item Saved internships (bookmarks), represented through relational mappings between authenticated users and internship records
\item Search history and recently viewed interaction metadata, supported through persistent user-linked storage for future scalability
\item User preferences and configurable account-linked settings, including extensible support for notification-oriented integrations
\end{itemize}
PostgreSQL (via Supabase) provides a structured relational persistence layer for user-centric application state. It was selected because it offers strong transactional guarantees (ACID compliance) suitable for authenticated operations and user-state consistency.
Supabase specifically reduces operational complexity by providing integrated authentication services, managed database infrastructure, REST/realtime communication support, and security controls, allowing the implementation to focus on the internship semantic enrichment pipeline rather than backend infrastructure administration.
This hybrid persistence architecture complements the lightweight JSON-based internship catalog by separating read-heavy public internship discovery data from dynamic authenticated user application state.
\section{Data Representation and Type-Safety Tools}
Reliable data representation is essential for a system that transforms noisy, heterogeneous internship data into structured, queryable records. The web application layer uses TypeScript (version 5.3.0) to enforce structured data contracts across frontend and application-facing modules \cite{riva2022realworld}.
TypeScript was selected over plain JavaScript because its static type system helps detect field mismatches, missing properties, and incompatible data structures during development, reducing runtime errors and improving maintainability. This is particularly valuable in an application that consumes semantically enriched structured internship records, where consistency between API responses, frontend rendering logic, and user-facing data models is critical.
Within the broader architecture, TypeScript complements the Python-based enrichment pipeline by providing type safety at the application layer, while the semantic preprocessing pipeline remains responsible for upstream data cleaning, normalization, and schema preparation.
\subsection{TypeScript Data Interfaces}
The Internship interface, defined in TypeScript, specifies the exact shape of every internship
record in the system. The complete interface is shown in Listing 3.1.
\begin{verbatim}
interface Internship {
  id: string;                       // Stable unique internship identifier
  title: string;                    // Internship or job title
  company: string;                  // Employer or organization name
  location: string;                 // Geographic location of the opportunity
  link: string;                     // Original application or posting URL
  salary: string;                   // Cleaned salary representation if available
  description: string;              // Full normalized internship description
  platform: string;                 // Source platform (e.g., LinkedIn, Indeed)
  skills: string[];                 // Extracted structured skill tags
  category: string;                 // Assigned internship domain/category
  duration?: string;                // Internship duration if explicitly detected
  internship_probability?: number;  // Semantic internship relevance confidence
  is_real_internship?: boolean;     // Final internship classification decision
}
\end{verbatim}
This interface serves as a structured contract within the web application layer, helping ensure consistency between API responses, frontend rendering logic, and user-facing data consumption. TypeScript's static type checking allows mismatches in expected frontend data structures to be identified during development rather than at runtime.
Because the semantic enrichment pipeline operates in Python, schema consistency between the enrichment layer and the frontend is maintained through disciplined JSON serialization and structured application-side validation rather than shared compile-time type enforcement.
\subsection{Structured Internship Records}
Beyond static type safety, the application enforces structural consistency through validation checks applied before internship records are consumed by the frontend interface. After parsing structured JSON data, validation logic ensures that essential identifying fields are present before a record is accepted for application use.
\subsubsection*{The validation process performs the following checks}
\begin{itemize}
\item Required field presence: Confirms that critical identifying attributes such as title and company exist and contain non-empty string values.
\item Malformed record filtering: Records missing essential identifying information are excluded from downstream application use to prevent incomplete or unusable internship entries from reaching the user interface.
\end{itemize}

\section{Semantic Enrichment and Transformer-Based Tools}
The semantic enrichment pipeline relies on lightweight transformer-based tools selected to balance semantic expressiveness with computational efficiency. Rather than depending on large general-purpose cloud-hosted language models for internship classification and enrichment, the system uses compact transformer architectures capable of efficient local inference on commodity CPU hardware without GPU acceleration.
This design decision directly supports the thesis's lightweight and resource-conscious architectural goals by eliminating per-inference API costs, reducing infrastructure complexity, and maintaining reproducible local processing for semantic internship enrichment.
\subsection{Transformer-Based Semantic Components}
Transformer-based models are used as lightweight semantic processing components rather than as general-purpose generative systems \cite{vaswani2017attention}. The implementation relies primarily on the SentenceTransformers framework \cite{reimers2019sentence} with the all-MiniLM-L6-v2 model, which provides compact sentence embeddings suitable for semantic similarity analysis, internship relevance classification support, and enrichment-related matching tasks.
The selected model is loaded from the Hugging Face ecosystem and executed locally within the Python-based semantic enrichment pipeline. This approach enables reproducible offline inference on commodity CPU hardware without requiring GPU acceleration or external cloud inference services.
The all-MiniLM-L6-v2 model was selected because it offers a favorable trade-off between semantic representation quality, inference speed, and computational efficiency \cite{menghani2023efficient, schwartz2020green}, making it appropriate for lightweight internship enrichment workflows operating over heterogeneous recruitment datasets.

\subsection{Semantic Classification Workflow}
The transformer model is integrated into the semantic enrichment pipeline as a lightweight semantic similarity component rather than as a standalone generative classifier. After internship records are collected and normalized, relevant textual fields--primarily job titles and descriptive content--are passed through the all-MiniLM-L6-v2 sentence-transformer model to generate compact semantic embeddings.
These embeddings are used to support internship relevance assessment by comparing noisy or ambiguous internship postings against curated semantic reference patterns representing valid internship characteristics. This enables the system to distinguish genuine internship opportunities from unrelated full-time professional job postings, even when lexical terminology varies significantly across sources.
The transformer-based classification stage operates alongside deterministic heuristic filtering rather than replacing rule-based validation entirely. This hybrid design improves robustness by combining semantic similarity analysis with explicit structural filtering, allowing lightweight classification behavior without requiring large-scale generative inference.
Because inference is performed locally within the Python enrichment pipeline, no external API calls or cloud-hosted model services are required. This preserves reproducibility, minimizes operational cost, and aligns with the thesis objective of efficient semantic enrichment on commodity hardware.
\section{Text Processing and Heuristic Normalization Tools}
Beyond transformer-based semantic processing, the system relies extensively on deterministic text-processing and heuristic normalization mechanisms to improve the consistency and usability of heterogeneous internship data \cite{sarawagi2008information, chu2016data}. Because recruitment listings frequently contain noisy formatting, inconsistent field naming, multilingual terminology, and platform-specific irregularities, purely semantic approaches alone are insufficient for robust preprocessing.
The proposed architecture therefore combines lightweight semantic enrichment with rule-based normalization techniques that perform structural cleaning, field harmonization, internship-specific filtering, and metadata standardization prior to frontend deployment. This hybrid processing strategy improves robustness while preserving the computational efficiency objectives of the overall lightweight system architecture.
\subsection{Rule-Based Text Normalization}
The semantic enrichment pipeline complements transformer-based processing with deterministic rule-based text normalization mechanisms designed to improve consistency across heterogeneous internship data sources. Recruitment records collected from different platforms frequently contain inconsistent formatting, non-standard field naming, multilingual terminology, and noisy textual artifacts that reduce downstream classification quality.
To address these issues, the system applies heuristic normalization procedures that standardize textual fields prior to semantic enrichment. These operations include whitespace normalization, field harmonization, malformed record filtering, internship-specific keyword normalization, and removal of structurally invalid or incomplete entries.
Rule-based normalization was deliberately selected as a lightweight preprocessing layer because deterministic transformations are computationally inexpensive, transparent, and highly effective for repetitive structural cleaning tasks that do not require semantic inference.
\subsection{JSON-Based Rule Configuration}
To preserve maintainability and reduce hardcoded logic, the system externalizes domain-specific processing rules into structured JSON configuration resources. These configuration files support deterministic internship filtering, semantic enrichment assistance, and domain normalization without requiring direct modification of the application logic.
\subsubsection*{Key configuration resources include}
\begin{itemize}
\item skills\_library.json: Structured internship skill definitions and synonym mappings used to support skill extraction and normalization.
\item domain\_keywords.json: Domain classification reference keywords used to assist internship categorization and semantic enrichment.
\item internship\_rules.json: Positive internship indicators, multilingual internship terminology, exclusion phrases, and heuristic internship detection rules.
\item negative\_role\_patterns.json: Structured rejection patterns used to identify senior professional roles, licensed occupations, permanent employment, and non-internship job postings.
\end{itemize}
This configuration-driven architecture improves flexibility, maintainability, and reproducibility while keeping the semantic enrichment pipeline computationally lightweight.
\subsection{Heuristic Filtering and Classification Support}
Deterministic heuristic filtering operates alongside transformer-based semantic classification to improve robustness when processing noisy recruitment data. Explicit rule patterns are used to identify structurally invalid postings, obvious non-internship professional roles, and domain-specific exclusion cases that do not require transformer inference.
This hybrid design reduces unnecessary semantic processing while improving classification consistency. Clear deterministic cases can be handled through inexpensive rule evaluation, allowing transformer-based semantic similarity analysis to focus on ambiguous internship records where contextual interpretation provides greater value.
The combination of deterministic filtering and lightweight semantic enrichment supports the thesis objective of balancing classification quality with computational efficiency on commodity hardware


\section{Development, Testing, and Evaluation Environment}
The development and evaluation environment supports reproducible implementation, semantic pipeline execution, and performance observation under controlled hardware conditions. All experimental observations discussed in Chapter 6 are conducted on a consistent local hardware configuration to support reproducibility and fair evaluation of the proposed lightweight architecture.
\subsection{Hardware Configuration}
All development and experimental evaluation were conducted on a single workstation with the following specifications:
\begin{itemize}
\item CPU: Intel Core i7-10750H (6 cores, 12 threads, 2.60 GHz)
\item RAM: 16 GB
\item Storage: 715 GB total storage
\item GPU: None (CPU-only execution)
\item Operating System: windows 11
\item Node.js version: 20.11.0 (LTS)
\end{itemize}
This configuration reflects the commodity hardware constraint central to the thesis objectives. The proposed system is specifically designed to operate without GPU acceleration, demonstrating that practical internship semantic enrichment and classification can be achieved using widely accessible general-purpose computing hardware.
\subsection{Development Instrumentation and Evaluation Support}
To support reproducible evaluation, the implementation includes lightweight logging and measurement mechanisms that monitor semantic pipeline execution, dataset transformation behavior, and frontend responsiveness.
The evaluation environment focuses on practical performance observation rather than production-scale distributed monitoring, consistent with the lightweight architecture objectives of the thesis.
\subsubsection*{Key measurements include}
\begin{itemize}
\item Pipeline execution monitoring: The semantic enrichment pipeline records dataset processing behavior, including total processed records, accepted internship classifications, rejected non-internship records, manual review candidates, and enrichment completeness indicators such as missing skill extraction outcomes.
\item Classification behavior analysis: Internship relevance classification outputs are logged to support later quantitative evaluation of semantic filtering effectiveness and heuristic classification consistency.
\item Runtime observation: End-to-end processing duration is observed during local execution to assess the practical computational cost of semantic enrichment on commodity hardware.
\item Frontend responsiveness observation: Local Chromium DevTools measurements are used to assess practical frontend responsiveness during internship browsing, filtering, and cached interaction scenarios.
\end{itemize}
This instrumentation provides sufficient evaluation support for analyzing classification quality, enrichment consistency, filtering effectiveness, and computational practicality within the scope of the proposed lightweight internship enrichment system.
