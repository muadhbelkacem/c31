\chapter{Background: Text Representation and Retrieval}
Search and retrieval are the core mechanisms for accessing internship listings once they have been ingested and enriched. The effectiveness of a search system directly determines whether a student can bridge the "semantic gap" described in Chapter~2---transforming a vague career aspiration like ``I want to build apps'' into a concrete set of relevant postings. In this chapter, we explore the evolution from traditional lexical matching to modern semantic search techniques, highlighting the fundamental trade-offs in accuracy, performance, and interpretability as established in retrieval theory \cite{manning2008introduction, baeza2011modern, croft2010search}. We build a conceptual framework that directly motivates the hybrid retrieval design at the heart of this thesis.

\section{Keyword Retrieval}
Keyword-based retrieval, also known as lexical or sparse retrieval, relies on the presence of exact words or tokens in both the query and the document. This approach has been the foundation of information retrieval for decades, prized for its efficiency, interpretability, and predictable behavior \cite{manning2008introduction, zobel2006inverted}. In the context of internship listings, a search for ``Python Developer'' will return any job posting containing the exact tokens ``Python'' and ``Developer,'' irrespective of the broader meaning.

\subsection{Inverted Indexing}
The fundamental data structure enabling high-speed keyword search is the \textit{inverted index}. Conceptually, it is a simple but powerful mapping: each unique term (token) in the corpus points to a list of document identifiers (postings) containing that term, often along with the term's frequency and position within each document \cite{manning2008introduction, zobel2006inverted}. This structure allows for sub-linear search time; instead of scanning every document for a query term, the system only retrieves the pre-computed postings list. For a catalog of internship postings exceeding 17,500 items, an inverted index ensures that a search for a rare technical skill like ``Kubernetes'' remains fast and precise. The construction and compression of these indices is a well-understood engineering problem, making inverted indexing a robust, sustainable, and low-resource foundation for any production retrieval system \cite{buttcher2016information}.

\subsection{BM25 (Best Matching 25)}
While boolean retrieval---simply checking for the presence of a term---provides a binary true/false result, modern ranking models assign a continuous relevance score, enabling a sorted list of results. BM25 (Best Matching 25) is the de facto standard for this task, providing a sophisticated scoring mechanism grounded in the probabilistic relevance framework \cite{robertson2009probabilistic, jurafsky2023speech, buttcher2016information}. BM25 is an evolution of the classic TF-IDF (Term Frequency-Inverse Document Frequency) model, introducing two essential parameters that directly address the idiosyncrasies of internship listings:

\begin{itemize}
    \item \textbf{Term Frequency Saturation ($k_1$):} The raw term frequency (TF) in TF-IDF assumes that a document containing a term ten times is ten times as relevant as one containing it once. In practice, this is rarely true and makes the system vulnerable to ``keyword stuffing''---an employer repeating ``Java'' dozens of times to artificially boost their posting. BM25 applies a nonlinear saturation function controlled by $k_1$, which bounds the contribution of term frequency. The relevance gain from a term’s first few occurrences is steep, but additional mentions contribute diminishing returns, making the system robust against manipulation and verbose postings \cite{robertson2009probabilistic}.
    \item \textbf{Document Length Normalization ($b$):} Job descriptions vary dramatically in length. A detailed ``Senior Research Intern'' posting might naturally contain more words than a brief ``QA Tester'' entry, including incidental mentions of a query term. BM25's length normalization parameter $b$ penalizes excessively long documents. By tuning $b$, we ensure that a concise, perfectly matched internship posting is not outranked by a longer, more generic one simply because the longer text has more chances to mention a key skill \cite{robertson2009probabilistic}.
\end{itemize}

BM25 remains an exceptionally strong and difficult-to-beat baseline, particularly for queries centered on domain-specific technical terms, acronyms (e.g., ``AWS,'' ``RCT''), and specific degree requirements, where exact lexical matching defines precision \cite{robertson2009probabilistic, thakur2021beir}. Its primary failure mode is its inability to handle the vocabulary mismatch problem: a student searching for ``C++ Intern'' will miss a perfectly suitable role titled ``Systems Software Intern'' that lists C++ as a key requirement but never uses the exact phrase.

\section{Vector Representations}
To address the inherent limitations of lexical matching, modern retrieval systems have moved toward vector-based, or ``dense,'' representations. Instead of representing text as a sparse bag of words, this paradigm embeds it into a continuous, high-dimensional vector space. The core hypothesis is that the geometric distance between two vectors---often measured with cosine similarity---correlates with the semantic similarity of the underlying text \cite{jurafsky2023speech, luan2021sparse, lin2021pretrained}. In this space, ``Junior Java Developer'' and ``Software Engineering Intern'' are mapped to nearby points, even if they share no words.

\subsection{Dense Embeddings}
Unlike the high-dimensional and sparse lexical vectors (where each dimension corresponds to a unique word from the vocabulary), dense embeddings are compressed representations, typically 384 to 1536 dimensions long. Each dimension encodes a latent feature of the text's meaning, learned from data. These vectors are generated by pre-trained neural networks, most notably those based on the Transformer architecture, which has revolutionized the field of NLP by enabling models to weigh the dynamic contextual importance of each word in a sentence \cite{vaswani2017attention, devlin2019bert}. A model like BERT (Bidirectional Encoder Representations from Transformers) can produce context-aware embeddings, meaning the vector for ``Java'' in the sentence ``Experience with Java'' is different from its embedding in ``Located on the island of Java,'' allowing for the disambiguation described in Chapter~2.

\subsection{Sentence-BERT (SBERT) and Bi-Encoders}
Despite their power, standard BERT models are architecturally ill-suited for large-scale similarity search. They are designed as \textit{cross-encoders}, meaning a query and a document must be fed into the model simultaneously, requiring a full neural network pass for every single query-document pair. For a corpus of 17,500 postings, executing a single search could take minutes, rendering real-time interaction impossible.

Sentence-BERT (SBERT) introduced a paradigm-shifting \textit{bi-encoder} architecture \cite{reimers2019sentence}. In a bi-encoder, both the query and the document are processed by separate, identical BERT networks to produce a single, independent, fixed-sized embedding for each. This decoupling has two revolutionary consequences for our use case:
\begin{enumerate}
    \item \textbf{Offline Indexing:} We can pre-compute a semantic embedding for every internship in our catalog. This one-time, offline process converts the entire corpus into a matrix of vectors.
    \item \textbf{Real-Time Search:} At search time, we only need to generate a single embedding for the user's query and then find the closest document vectors in our pre-computed index.
\end{enumerate}
This architecture is the standard for efficient dense retrieval, alongside frameworks like Dense Passage Retrieval (DPR) \cite{karpukhin2020dense}, and forms the conceptual backbone of the semantic search component of this thesis. Fine-tuning SBERT on domain-specific data, such as pairs of similar job titles, can further collapse the semantic gap between, for example, ``ML Engineer'' and ``Machine Learning Intern'' \cite{reimers2019sentence, johnson2019billion}.

\section{Hybrid Retrieval}
In the high-stakes, precise domain of internship discovery, neither keyword nor vector search is a panacea. Each modality has a distinct failure mode. Lexical search fails on synonyms and concepts (semantic gap), while dense search can be poor at handling exact, rare matches like specific course codes (``ENGR301''), company names, or niche acronyms (``RTL Design'') where semantic similarity is diffuse. Hybrid retrieval is a framework for combining their complementary strengths, consistently outperforming single-modality systems, especially in zero-shot scenarios where models face data unlike their training set \cite{thakur2021beir, luan2021sparse}:
\begin{enumerate}
    \item \textbf{Sparse Retrieval (BM25):} Acts as a precision anchor for exact matches on unambiguous terms, ensuring a search for ``React Native Intern at Acme Corp'' returns the specific Acme Corp posting if it exists. Recent advances like SPLADE further blur the lines by using neural networks to learn sparse lexical expansions, potentially adding ``React'' to a query for ``React Native'' \cite{formal2021splade}.
    \item \textbf{Dense Retrieval (SBERT):} Handles the conceptual ``fuzzy'' layer, ensuring a student searching for ``Frontend Web Programming'' sees relevant ``UI/UX Development'' and ``JavaScript Engineering'' roles, capturing the semantic neighborhood of their query \cite{reimers2019sentence}.
\end{enumerate}

\subsection{Reciprocal Rank Fusion (RRF)}
A central practical challenge in hybrid retrieval is score fusion: BM25 outputs a theoretically unbounded lexical score, while SBERT returns a cosine similarity bounded between $[-1, 1]$. Naively normalizing or summing these incommensurable scores is brittle and requires heavy parameter tuning. Reciprocal Rank Fusion (RRF) elegantly circumvents this issue. It operates not on score magnitudes, but on the rank positions of documents in each respective result list \cite{cormack2009reciprocal}. A document that is 2nd in the BM25 list and 5th in the SBERT list receives a higher fused score than one that is 150th and 1st. This method is robust, parameter-free, and inherently penalizes documents that perform poorly in one retrieval paradigm, using only the ordinal information common to any ranked list. This makes it an ideal, low-maintenance fusion algorithm for a diverse, evolving corpus of job postings \cite{cormack2009reciprocal}.

\section{Efficiency Considerations}
The theoretical elegance of semantic search must translate into a practical, low-latency system. Scaling to thousands of job postings requires specialized infrastructure to manage high-dimensional vector operations without sacrificing the ``lightweight'' design goal of this thesis \cite{johnson2019billion, wang2021milvus}.

\subsection{Vector Databases and Approximate Nearest Neighbor (ANN) Search}
Traditional SQL databases are optimized for exact matching and one-dimensional B-tree indexing, and performing exact nearest neighbor (k-NN) search in a 384-dimensional space is computationally wasteful. At the scale of 17,500 records, an exact linear scan might be acceptable, but for true scalability and sub-50ms latency, a better approach is required. Vector databases are purpose-built for this task, utilizing \textit{Approximate Nearest Neighbor (ANN)} algorithms. ANN algorithms trade a small, tunable amount of recall (e.g., 99\% of the true nearest neighbors) for orders-of-magnitude improvements in query speed and memory efficiency \cite{malkov2018efficient, wang2021milvus}. This trade-off is perfectly acceptable in a recruitment search context, where missing the 51st-most-similar posting in a list of 50 results is a nondestructive event.

\subsection{HNSW (Hierarchical Navigable Small World)}
HNSW is one of the most performant and widely-adopted ANN algorithms, serving as the foundation for our vector indexing strategy \cite{malkov2018efficient}. It constructs a multi-layered, proximity graph structure:
\begin{itemize}
    \item The \textbf{top layers} contain only a few nodes with long-range edges, establishing a highway network that allows the search to rapidly traverse the entire vector space.
    \item The \textbf{bottom layer} contains all data points connected by short-range edges, enabling a fine-grained local search for the most precise neighbors.
\end{itemize}
A search starts by greedily navigating the sparse top layer to get to the general region of the query vector quickly, and then descends to the dense bottom layers for final refinement. This navigable small-world structure empowers a logarithmic search complexity, $O(\log N)$, making it perfectly suited for a low-latency production environment where a student expects real-time feedback during search \cite{malkov2018efficient}.

\subsection{Quantization}
For deep efficiency, the memory footprint of the vector index can become a limiting factor. Storing even a 384-dimensional vector of 32-bit floats for each of 17,500 (and counting) postings incurs significant RAM overhead. Quantization techniques compress these vectors into a lower-precision representation, dramatically reducing the required RAM while mostly preserving the relative distances between points \cite{jegou2010product, guo2020accelerating}. \textit{Scalar Quantization} maps 32-bit floats to 8-bit integers, a simple approach providing a 4$\times$ memory reduction. \textit{Product Quantization (PQ)} is a more advanced method that splits the vector into sub-vectors and quantizes them independently, achieving even higher compression ratios. This is a critical technique for maintaining the ``lightweight'' character of our system, allowing a semantic brain to run on commodity hardware without resorting to expensive, large-scale cloud resources, aligning perfectly with the principles of ``Green AI'' \cite{menghani2023efficient, schwartz2020green}.
