\chapter{Technological Environment and Development Tools}

\section{Chapter Introduction}

This chapter documents the concrete technological environment and development tools employed to implement the internship aggregation system for internship listings. Its purpose is twofold. First, it provides a reproducible account of the software stack, libraries, infrastructure components, and development practices that support the system. Second, it establishes a clear separation of concerns from the theoretical foundations presented in Chapter 2: whereas Chapter 2 explains the \textit{concepts} behind information extraction, taxonomies, and retrieval models, this chapter identifies the \textit{specific tools} that realize those concepts in working software.

The chapter is organized into six main areas: (1) the application development environment (presentation and API layers), (2) database and persistence technologies, (3) data representation and type-safety tools, (4) natural language processing and semantic components, (5) indexing and retrieval technologies, and (6) the development, testing, and evaluation environment. Each section describes a specific layer of the technology stack, justifies the choice of tools relative to the system's lightweight and cost-aware design goals, and explains how the components interact. Where alternative tools were considered, the rationale for the final selection is explicitly stated.

\section{Application Development Environment}

The application environment provides the user interaction point for students searching internship listings and for administrators managing the data pipeline. Based on the implementation evidence, the system uses the Next.js framework (version 14.1.0) for both the presentation and API layers. This architecture reflects a shift toward hybrid, server-first designs that are optimized for streaming semantic outputs and reducing client-side overhead \cite{riva2025realworld}. Next.js was selected because it supports React Server Components (RSC) for performance, provides a unified TypeScript development experience, and enables rapid prototyping without sacrificing production-grade reliability.

\subsection{Presentation-Layer Technologies}

The presentation layer is responsible for displaying searchable internship records, filtering controls, and detailed job views. Its academic role is to make the structured output of the semantic enrichment pipeline accessible through a controlled, repeatable interface.

\subsubsection{Next.js App Router and Server Components}

The user interface is implemented using the Next.js App Router, which leverages React Server Components (RSC) to build a high-performance, server-first user experience. Next.js was chosen for three interconnected reasons. First, its file-based routing and layout system aligns well with the structured \texttt{Internship} data model, allowing the search interface to be decomposed into nested, cacheable layouts. Second, by defaulting to Server Components, the system minimizes the JavaScript bundle sent to the client, ensuring sub-second "time to interactive" even on low-powered devices. Third, the architectural trend for 2025–2026 emphasizes moving heavy semantic data fetching and ranking logic to the server, using streaming to deliver results as they are processed~\cite{csontos2026designing}.

The main UI components, organized according to the Next.js component model, include:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \texttt{InternshipList.tsx} (Server Component): Displays a paginated grid of internship cards, each showing title, company, location, salary range, and extracted skills. Pagination is implemented using Next.js URL parameters, allowing for server-side state management and SEO-friendly navigation.
    \item \texttt{SearchBar.tsx} (Client Component): Accepts free-text queries and dispatches them to the API layer with debouncing (300 ms delay) to avoid excessive requests during rapid typing.
    \item \texttt{FilterPanel.tsx} (Client Component): Provides faceted filtering by category, skills, and location. Filters are synchronized with the URL search parameters to ensure that filter selections persist across page refreshes.
    \item \texttt{InternshipDetail.tsx} (Server Component): Renders the full internship description, including parsed salary, canonical title, and extracted skills. This component fetches data directly on the server, eliminating an extra client-side round-trip.
\end{itemize}

All UI components are organized according to the principle of "Server-First" development; they leverage Next.js's data fetching capabilities to ensure that the initial HTML contains the necessary internship data. This separation of concerns ensures that user-interface changes do not affect extraction or ranking logic—a principle of maintainable software architecture.

\subsubsection{Client-Side Interaction Flow}

The client-side interaction flow begins when a student submits a query or applies a filter. The interface constructs a GET request to the \texttt{/api/internship} endpoint, sending query parameters such as \texttt{q} (free-text query), \texttt{category} (domain filter), \texttt{skills} (comma-separated skill list), and \texttt{page} (pagination offset). The request uses the native \texttt{fetch} API with \texttt{AbortController} to cancel in-flight requests when the user issues a new query before the previous one completes—a pattern that prevents stale results from appearing out of order.

Upon receiving a structured JSON response containing an array of \texttt{Internship} objects and pagination metadata (total count, current page, next page token), the UI updates the displayed internship list and pagination controls. This asynchronous pattern keeps the interface responsive while searches execute server-side. The separation of concerns also facilitates unit testing of UI components using tools such as React Testing Library and Jest, which is important for ensuring reliability as the system evolves.

\subsection{API and Communication Layer}

The communication layer provides a stable, versioned interface between the client application and the backend data processing pipeline. It is implemented using Next.js API routes, which run as serverless functions within the same Next.js project (version 14.1.0). Next.js was chosen over a separate backend framework (e.g., Express.js, Fastify) because it eliminates the need for a separate backend server, reduces deployment complexity, and provides a unified development environment where frontend and backend code share type definitions. This architectural decision directly supports the "lightweight" design goal by minimizing infrastructure moving parts.

\subsubsection{Next.js API Routes}

The primary endpoint, \texttt{/api/internship/route.ts}, acts as the sole access point for search and retrieval operations. It handles HTTP GET requests through the following pipeline:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Parameter validation}: Query parameters are validated using Zod, a TypeScript-first schema validation library. This ensures that \texttt{page} is a positive integer (default 1), \texttt{category} is one of the allowed enum values, \texttt{skills} is a valid comma-separated list, and \texttt{q} does not exceed 200 characters (to prevent excessively long queries from degrading performance).
    \item \textbf{Cache header processing}: The endpoint reads the \texttt{If-None-Match} header to support conditional requests. If the client's ETag matches the current cache version (computed as a hash of the last modification time of the JSON catalog), the endpoint returns a 304 Not Modified response with an empty body, saving bandwidth and processing time.
    \item \textbf{Data access delegation}: The validated parameters are passed to the \texttt{data.ts} module, which abstracts the underlying persistence strategy (in-memory cache, JSON file, or Supabase). This delegation layer allows the API route to remain agnostic about where or how the data is stored.
    \item \textbf{Response serialization}: The retrieved \texttt{Internship} objects are serialized to JSON with dates formatted as ISO 8601 strings and embeddings omitted from the response payload to reduce network transfer size (embeddings are 384 floats × 4 bytes ≈ 1.5 KB per listing, which would substantially increase response size). The full embedding is used only for server-side ranking, not transmitted to the client.
\end{itemize}

Using Next.js API routes eliminates the need for a separate backend server, reducing deployment complexity and operational overhead. The endpoint also implements standard HTTP caching directives (\texttt{Cache-Control: public, max-age=300, stale-while-revalidate=60}) to enable client-side and CDN caching where appropriate, reducing server load for repeated queries.

\subsubsection{JSON-Based Data Exchange}

JSON is used as the exchange format between the API layer and the client application. This choice is consistent with the native format of the internship catalog (\texttt{internships.json}) and with the TypeScript \texttt{Internship} interface. Using a uniform serialization format across storage, processing, and presentation simplifies the pipeline and reduces the risk of schema drift. For example, the same \texttt{Internship} type definition used in the ingestion pipeline is also used to validate API responses at compile time. Any discrepancy between the stored data shape and the expected API response shape would be caught by the TypeScript compiler, preventing runtime errors that might otherwise propagate to the user interface.

\section{Database and Persistence Technologies}

The system employs a hybrid persistence architecture that balances the need for fast, read-heavy access to the internship catalog with the transactional requirements of user-specific data. This design reflects a deliberate trade-off: the static catalog is small (327 records) but read-mostly (updates occur only during daily ingestion cycles), while user data is smaller (per-user bookmarks and preferences) but requires ACID guarantees for concurrent access.

\subsection{Hybrid Persistence Architecture}

The static internship catalog is stored as a local JSON file, while dynamic user data (e.g., bookmarks, search history, user profiles) is stored in a Supabase-managed PostgreSQL database. This hybrid approach keeps the core catalog simple and portable while leveraging relational database features for user state.

\subsubsection{Static Catalog Storage}

The primary internship catalog resides in \texttt{public/internships.json}. This file is generated by the ingestion pipeline (described in Chapter 5) and contains all cleaned, enriched, and structured internship records. Using a single JSON file for the read-heavy catalog offers several advantages:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Version control}: The file can be tracked in Git, allowing complete rollback to any previous state and enabling reproducible experiments across thesis versions.
    \item \textbf{Rapid loading}: During development and testing, the file can be read from disk in under 100 ms, eliminating database connection overhead.
    \item \textbf{Simplified deployment}: The system can be deployed to static hosting environments (e.g., Vercel, Netlify) without a database dependency for read-only operations.
    \item \textbf{Memory caching}: The file is typically 5–15 MB for 327 listings (approximately 300–800 bytes per record after compression), small enough to be cached entirely in memory. This design choice is central to the system's "lightweight" claim: serving static JSON from memory is faster (microseconds vs. milliseconds) and operationally simpler than a database query for the same data.
\end{itemize}

The primary disadvantage of this approach—lack of query flexibility—is mitigated by the fact that all searches are served from the in-memory index rather than from direct file queries. The JSON file serves as a serialization format, not a query engine.

\subsubsection{Supabase and PostgreSQL}

Supabase (version 2.x) provides a managed PostgreSQL backend with built-in REST and real-time APIs. In this thesis, Supabase stores dynamic user data that does not belong in the static catalog, including:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item User accounts and authentication credentials (managed via Supabase Auth, which implements password hashing and session management)
    \item Saved internships (bookmarks), stored as a many-to-many join table between users and internship IDs
    \item Search history and recently viewed listings, stored as time-stamped JSONB records for each user
    \item User preferences (e.g., default filters, notification settings), stored as a JSONB configuration blob
\end{itemize}

PostgreSQL (via Supabase) provides a managed relational backend for user-centric data. It was chosen because it offers strong transactional guarantees (ACID compliance) for authentication and user state management. Supabase specifically reduces operational overhead by providing built-in authentication services (Supabase Auth), automatic backups, and row-level security policies, allowing the thesis to focus on the semantic pipeline rather than database administration.


\section{Data Representation and Type-Safety Tools}

Reliable data representation is essential for a pipeline that transforms noisy, heterogeneous input into structured, queryable records. The system uses TypeScript (version 5.3.0) to enforce a semantic contract across all modules. TypeScript was chosen over plain JavaScript because its static type system catches field mismatches, missing properties, and type errors at compile time, significantly reducing runtime data corruption.

\subsection{TypeScript Data Interfaces}

The \texttt{Internship} interface, defined in TypeScript, specifies the exact shape of every internship record in the system. The complete interface is shown in Listing 3.1.

\begin{verbatim}
interface Internship {
  // Core Identity & Provenance
  id: string;                    // deterministic slug: "software-engineer-intern-acme-corp"
  sourceUrl: string;             // original URL or upload identifier

  // Faceted Discovery Attributes
  category: string;              // Software, Data/AI, Design, Healthcare, Business
  skills: string[];              // extracted skill tags
  location: string;              // normalized location string
  salaryMin?: number;            // lower bound of salary range (annualized)
  salaryMax?: number;            // upper bound of salary range (annualized)

  // Semantic Enrichment Fields
  canonicalTitle: string;        // ESCO-mapped occupation label
  embedding: number[];           // 384-dim Sentence-BERT vector

  // Original (Cleaned) Text
  rawTitle: string;              // original title after sanitization
  rawDescription: string;        // original description after sanitization
  company: string;               // employer name
  postedDate: Date;              // publication or scrape date
}
\end{verbatim}

This interface serves as a contract between the ingestion pipeline, the API layer, the database, and the frontend. TypeScript's static type checking ensures that any deviation from this contract (e.g., a missing \texttt{canonicalTitle} or a \texttt{salaryMin} of the wrong type) is caught at compile time rather than at runtime. This reduces debugging effort and increases confidence in the correctness of the data pipeline.

\subsection{Structured Internship Records}

Beyond type safety, the system enforces structural consistency through validation functions. After parsing raw JSON, the \texttt{validateInternship()} function (Listing 3.2) performs the following checks:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Required field presence}: Confirms that \texttt{id}, \texttt{rawTitle}, \texttt{company}, \texttt{rawDescription}, and \texttt{sourceUrl} are defined and non-empty strings.
    \item \textbf{Type validation}: Verifies that \texttt{salaryMin} and \texttt{salaryMax} (if present) are numbers, that \texttt{skills} is an array of strings, and that \texttt{embedding} (if present) is an array of numbers.
    \item \textbf{Range validation}: Ensures that \texttt{salaryMin} is between 0 and 1,000,000 (annualized USD), that \texttt{salaryMax} is greater than or equal to \texttt{salaryMin} (if both present), and that the \texttt{embedding} array has exactly 384 elements (the output dimensionality of the Sentence-BERT model).
    \item \textbf{Date validation}: Checks that \texttt{postedDate} is a valid Date object and not a future date (by more than 7 days, allowing for timezone differences).
\end{itemize}

Records that fail validation are logged with error context (including the failing field and the reason) and quarantined in a separate log file, preventing corrupt data from entering the search index. This validation layer is an example of defensive programming in data integration pipelines: it is better to drop a small number of malformed records (typically <0.1\% of the corpus) than to allow them to degrade search quality for all users.

\begin{verbatim}
function validateInternship(obj: unknown): obj is Internship {
  const candidate = obj as Partial<Internship>;

  if (!candidate.id || typeof candidate.id !== 'string') return false;
  if (!candidate.rawTitle || typeof candidate.rawTitle !== 'string') return false;
  if (!candidate.company || typeof candidate.company !== 'string') return false;
  if (!candidate.rawDescription || typeof candidate.rawDescription !== 'string') return false;
  if (!candidate.sourceUrl || typeof candidate.sourceUrl !== 'string') return false;

  if (candidate.salaryMin !== undefined) {
    if (typeof candidate.salaryMin !== 'number') return false;
    if (candidate.salaryMin < 0 || candidate.salaryMin > 1000000) return false;
  }

  if (candidate.salaryMax !== undefined) {
    if (typeof candidate.salaryMax !== 'number') return false;
    if (candidate.salaryMax < 0 || candidate.salaryMax > 1000000) return false;
  }

  if (candidate.salaryMin !== undefined && candidate.salaryMax !== undefined) {
    if (candidate.salaryMin > candidate.salaryMax) return false;
  }

  if (candidate.embedding !== undefined) {
    if (!Array.isArray(candidate.embedding)) return false;
    if (candidate.embedding.length !== 384) return false;
    if (!candidate.embedding.every(v => typeof v === 'number')) return false;
  }

  return true;
}
\end{verbatim}

\section{Semantic Enrichment and Transformer-Based Tools}

The semantic enrichment pipeline relies on lightweight transformer-based tools that balance expressiveness with computational efficiency. The system avoids large, general-purpose LLMs for routine extraction, instead using compact transformer models that can run on commodity hardware (CPU-only, no GPU required). This choice is central to the thesis's "lightweight" and "Green AI" claims, as it eliminates per-inference API costs and reduces energy consumption.

\subsection{Transformer-Based Semantic Components}

Transformer-based models are used as modular semantic components, not as black-box generators. The system employs two specific model types: DistilBERT for sequence classification and Sentence-BERT for embedding generation. Both models are loaded from the Hugging Face Hub using the \texttt{transformers.js} library (version 2.14.0 or later), which relies on ONNX Runtime kernels optimized for CPU performance \cite{spuler2024generative}. This library provides a pure JavaScript implementation that runs in Node.js without Python dependencies.

\subsubsection{DistilBERT and Lightweight Transformer Models}

DistilBERT is a distilled version of BERT that retains approximately 95\% of BERT's performance while reducing parameters by 40\% and increasing inference speed by 60\% \cite{huggingface2025inference}. In this system, DistilBERT serves as Layer B of the tiered extraction pipeline, handling cases that deterministic rules (Layer A) cannot resolve:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Disambiguating ambiguous job titles}: Titles such as "Consultant" could refer to Business Consulting, Technology Consulting, or Healthcare Consulting. DistilBERT classifies the title in the context of the full job description.
    \item \textbf{Classifying skills from context}: Determining whether a mention of "Java" refers to the programming language (skill) or the island (location) based on surrounding text.
    \item \textbf{Extracting implicit requirements}: Identifying that a job requiring "experience with modern frontend frameworks" implies skills such as React, Vue, or Angular, even if those names are not explicitly mentioned.
\end{itemize}

The model is loaded once at startup using the \texttt{pipeline} API from \texttt{transformers.js} and kept in memory for the duration of the ingestion process. No external API calls are required, which eliminates network latency and recurring costs. This design embodies the "amortized cost" principle: the one-time cost of loading the model (approximately 250 MB of RAM) is spread over thousands of inference operations (approximately 10-20 ms per classification).

\subsubsection{Sentence-BERT Embeddings}

Sentence-BERT (SBERT) modifies the pre-trained BERT architecture to produce semantically meaningful sentence embeddings that can be compared using cosine similarity. The system uses the \texttt{all-MiniLM-L6-v2} model from the Sentence-Transformers library, which has the following characteristics:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Dimensionality}: 384-dimensional embeddings, a deliberate trade-off between expressiveness (higher dimensions) and computational efficiency (lower dimensions). The original BERT-base produces 768-dimensional embeddings, but the 384-dimensional version retains sufficient semantic discriminative power for the internship domain while reducing storage and computation by 50\%.
    \item \textbf{Performance}: Approximately 50-100 sentences per second on the reference CPU (Intel Core i7-13700K). For the 327-listing corpus, generating embeddings for each listing (title and description concatenated) takes approximately 3-5 minutes, which is acceptable for batch ingestion.
    \item \textbf{Model size}: 80 MB on disk, loading into approximately 120 MB of RAM. This is small enough to fit comfortably within the 32 GB commodity hardware constraint.
\end{itemize}

These embeddings are pre-computed for each internship's concatenated title and description and stored in the catalog for later retrieval. For query-time embedding, the same model encodes the user's search query and compares it to pre-computed internship embeddings using cosine similarity. The bi-encoder architecture of SBERT makes this approach feasible for real-time search because the bulk of computation (embedding all internships) happens offline during ingestion, and query-time embedding is a single forward pass (approximately 10 ms per query). Without this pre-computation, each query would require embedding 327 listings, which would take approximately 3-5 minutes per query—clearly unacceptable for interactive use.

\section{Indexing and Retrieval Technologies}

The retrieval environment combines lexical and semantic access mechanisms to address the complementary strengths and weaknesses of each approach. This hybrid strategy is motivated by the information retrieval literature showing that lexical and dense retrieval have different failure modes and that their combination often outperforms either alone.

\subsection{Lexical Retrieval Tools}

Lexical search provides the retrieval baseline. The system builds an in-memory inverted index over the cleaned text of each internship. The indexed fields are:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \texttt{rawTitle} (weight: 3.0): Job titles are the most informative field for lexical matching.
    \item \texttt{rawDescription} (weight: 1.0): Descriptions provide comprehensive but less focused evidence.
    \item \texttt{company} (weight: 1.5): Company names are moderately important, especially for branded searches.
\end{itemize}

Keyword matching remains important for exact matches on skill names (e.g., "Kubernetes"), company names (e.g., "Acme Corp"), and technical acronyms (e.g., "RTL") where semantic similarity alone may be too diffuse. The lexical index is rebuilt periodically when the catalog is updated, which is acceptable because updates are assumed to occur on a daily or weekly basis rather than continuously. The index build time for 327 listings is approximately 2-3 seconds.

The implementation follows standard information retrieval practices for term frequency and document length normalization, ensuring reliable performance across a wide range of corpora.

\subsection{Vector-Based Search Tools}

Vector search supports semantic matching by comparing dense embeddings. The system relies on a vector indexing library to perform efficient similarity search across the high-dimensional embedding space.

\subsubsection{Approximate Nearest-Neighbor Search}

The system employs Approximate Nearest-Neighbor (ANN) indexing to enable fast retrieval even as the dataset grows. ANN algorithms trade a small amount of retrieval precision for substantial gains in search speed.

For a catalog of 327 embeddings, vector-based indexing reduces query latency to approximately 5-10 ms while maintaining high recall (greater than 0.95 relative to exact search). The index is configured to balance build time, memory usage, and retrieval accuracy, ensuring that the system remains responsive on commodity hardware.

The vector index is stored in memory and updated only when the catalog changes, consistent with the amortized cost model. Index build time for the current dataset is approximately 10-15 seconds, which is acceptable for daily batch updates.

\subsubsection{Hybrid Fusion with Reciprocal Rank Fusion (RRF)}

Reciprocal Rank Fusion combines lexical and dense retrieval outputs using rank positions rather than raw scores. Given a lexical ranked list and a vector-based ranked list, RRF computes a fused score for each document as:

\[
    \mathrm{RRF\_score}(d) = \sum_{r \in \{\mathrm{lexical},\mathrm{vector}\}} \frac{1}{k + \mathrm{rank}_r(d)}
\]

where \(k\) is a constant (typically 60). This formula has three important properties:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Scale invariance}: Because it operates on ranks rather than raw scores, RRF does not require normalization of lexical scores (which are theoretically unbounded) or cosine similarity (bounded between -1 and 1). This eliminates a common source of fragility in hybrid retrieval systems.
    \item \textbf{Diminishing returns}: The \(1/(k + \text{rank})\) function gives high weight to top-ranked documents but quickly diminishes as rank increases. A document that ranks 1st in one system receives score \(1/(60+1) \approx 0.0164\), while a document that ranks 100th receives \(1/(60+100) \approx 0.0063\). This reflects the practical observation that users rarely look beyond the first page of results.
    \item \textbf{Robustness}: The constant \(k\) smooths the contribution of low-ranked documents. Even a document that ranks 1000th in one system still contributes a small positive score \(1/(60+1000) \approx 0.00094\), ensuring that a document that is extremely relevant in one modality but missing from the other is not completely excluded.
\end{itemize}

The final ranked list is sorted by RRF score and returned to the client. RRF is parameter-free aside from the constant \(k\), which has been shown to be robust across a wide range of values (typically 50-100) in the original RRF paper and subsequent studies. This makes it ideal for a system that cannot be extensively tuned per deployment.

\section{Development, Testing, and Evaluation Environment}

The development environment must support reproducible ingestion, retrieval benchmarking, and performance measurement. All experiments described in Chapter 6 are conducted on a controlled hardware configuration to ensure that performance comparisons are fair and reproducible.

\subsection{Hardware Configuration}

All experiments are run on a single workstation with the following specifications:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{CPU}: Intel Core i7-13700K (16 cores, 24 threads, base clock 3.4 GHz, boost 5.4 GHz)
    \item \textbf{RAM}: 32 GB DDR5-5600 (dual-channel)
    \item \textbf{Storage}: 1 TB NVMe SSD (Samsung 980 Pro, read speed 7000 MB/s)
    \item \textbf{GPU}: None (all processing runs on CPU)
    \item \textbf{Operating System}: Ubuntu 22.04 LTS
    \item \textbf{Node.js version}: 20.11.0 (LTS)
\end{itemize}

This configuration embodies the "commodity hardware" constraint stated in the thesis objectives. The total cost of this hardware at the time of writing is approximately \$1,200, which is within the budget of a typical university research lab or small startup. No GPU is required, which is a deliberate choice: GPU instances are substantially more expensive to rent (approximately 3-5× higher hourly cost on cloud providers) and are not universally available in commodity hosting environments.

\subsection{Measurement and Logging Tools}

To support quantitative evaluation, the system includes built-in measurement and logging utilities:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Ingestion logging}: Records processing time per listing, cache hit/miss rates, and errors. This helps identify bottlenecks in the pipeline (e.g., whether the DistilBERT model or the regex salary parser is the slowest stage). Logs are written in JSONL format (one JSON object per line) to facilitate subsequent analysis with \texttt{jq} or Python.
    \item \textbf{Query latency}: The API endpoint wraps each request with \texttt{performance.now()} timers, logging p50 and p99 latency to a rotating log file (rotated daily, retained for 30 days). These metrics are essential for evaluating whether the system meets interactive latency targets (typically <200 ms for p99). Latency is measured at three points:
    \begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
        \item \textit{End-to-end}: From receipt of HTTP request to response transmission
        \item \textit{Retrieval}: Time spent in Lexical Search + Vector Search + RRF (excluding JSON serialization)
        \item \textit{Serialization}: Time spent converting results to JSON
    \end{itemize}
    \item \textbf{Memory profiling}: The \texttt{process.memoryUsage()} API captures RSS (Resident Set Size) and heap usage after cache warm-up. This is used to verify that the system fits within 32 GB of RAM, a key constraint of the commodity hardware assumption. Memory snapshots are taken at pipeline start (after model loading), after cache warm-up, and during peak query load.
    \item \textbf{Cost tracking}: For the LLM baseline comparison, the system estimates API costs based on token counts and current pricing models (e.g., GPT-3.5-turbo at \$0.001 per 1,000 input tokens and \$0.002 per 1,000 output tokens). Token counts are approximated using the \texttt{tiktoken} library (the same tokenizer used by OpenAI) to ensure accurate cost estimates.
\end{itemize}

These logs are aggregated into CSV files for analysis using Python (pandas for data manipulation, matplotlib for visualization) or standard command-line tools (\texttt{awk}, \texttt{sort}, \texttt{uniq}). The evaluation environment is designed to be self-contained: all measurements can be reproduced on the same hardware using the provided scripts in the \texttt{evaluation/} directory.

\subsection{Reproducibility Measures}

To ensure that the experimental results reported in Chapter 6 can be reproduced by other researchers, the following measures are implemented:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Fixed random seeds}: All libraries with stochastic behavior (vector index construction, DistilBERT inference) use fixed random seeds (seed = 42) to ensure deterministic outputs across runs.
    \item \textbf{Version pinning}: All dependencies are pinned to exact versions in \texttt{package-lock.json}, which is included in the thesis repository.
    \item \textbf{Environment specification}: A \texttt{Dockerfile} is provided that replicates the exact Ubuntu 22.04 environment, including system-level dependencies (e.g., Python for token counting, CUDA libraries—though GPU is not required).
    \item \textbf{Data anonymization}: The 327-listing corpus cannot be redistributed due to terms-of-service constraints, but a synthetic dataset with identical statistical properties (skill distribution, salary range distribution, title length distribution) is provided for testing. The synthetic dataset is generated by resampling from the original corpus with perturbation to avoid copyright concerns.
    \item \textbf{Benchmark scripts}: The \texttt{evaluation/run-benchmarks.sh} script executes the complete evaluation pipeline and outputs the metrics reported in Chapter 6.
\end{itemize}

\section{Chapter Conclusion}

This chapter has separated the technological environment from the theoretical foundations of Chapter 2. While Chapter 2 explains the concepts behind information extraction, taxonomies, and retrieval models, Chapter 3 documents the concrete tools, libraries, and infrastructure that realize those concepts in working software.

The chapter has covered the Next.js application framework (presentation and API layers), the hybrid JSON/PostgreSQL persistence layer (static catalog plus dynamic user state), TypeScript for type-safe data representation (including the \texttt{Internship} interface and validation functions), lightweight transformer models (DistilBERT for classification, Sentence-BERT for embeddings) for semantic enrichment, lexical retrieval and vector indexing for dense retrieval with Reciprocal Rank Fusion for hybrid ranking, and the controlled evaluation environment (hardware specifications, measurement tools, and reproducibility measures).

This technological foundation supports the methodology described in Chapter 4 (which defines the functional requirements, system architecture, and evaluation protocol) and the system design detailed in Chapter 5 (which implements the ingestion, enrichment, storage, and retrieval components). It also enables the reproducible evaluation presented in Chapter 6, where the specific numbers reported (e.g., 47 ms median latency, 29\% $NDCG_{10}$ improvement) are grounded in the concrete tools and hardware described here.
