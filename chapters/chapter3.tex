\chapter{Technological Environment and Development Tools}

\section{Chapter Introduction}

This chapter documents the concrete technological environment and development tools used to implement the proposed internship aggregation and semantic enrichment system. Its purpose is twofold. First, it provides a reproducible account of the software stack, libraries, infrastructure components, and development practices that support the implementation. Second, it establishes a clear separation from the theoretical foundations presented in Chapter 2: whereas Chapter 2 explains the concepts behind information extraction, semantic classification, and data normalization, this chapter identifies the specific tools used to realize those concepts in working software.

The chapter is organized into six main areas:
\begin{enumerate}[label=(\arabic*), leftmargin=2.5em]
    \item frontend application technologies.
    \item data representation and storage mechanisms.
    \item the local semantic processing and enrichment environment.
    \item text processing and heuristic normalization tools.
    \item development, testing, and evaluation tooling.
    \item deployment considerations for automated data ingestion.
\end{enumerate}
Each section describes a specific layer of the technology stack, justifies the choice of tools relative to the system's lightweight and cost-aware design goals, and explains how the components interact.

\section{Application Development Environment}

The application environment provides the primary user interaction layer for students browsing internship listings, while also supporting authenticated account-specific functionality through the broader application infrastructure. Based on the implementation evidence, the system uses the Next.js framework (version 16.0.7) and React (version 19.2.1) for the presentation and application integration layers.

This architecture reflects modern hybrid web application design, combining efficient frontend rendering with backend integration for user-facing functionality. Next.js was selected because it supports React Server Components (RSC), provides a unified TypeScript development experience, and enables rapid prototyping without sacrificing production-grade reliability.

\subsection{Presentation-Layer Technologies}

The presentation layer is responsible for displaying searchable internship records, filtering controls, and detailed job views. Its academic role is to make the structured output of the semantic enrichment pipeline accessible through a controlled, repeatable interface.

\subsubsection{Next.js App Router and Server Components}

The application environment provides the primary user interaction layer for students browsing internship listings, while also supporting authenticated account-specific functionality through the broader application infrastructure. Based on the implementation, the system uses the Next.js framework (version 16.0.7) and React (version 19.2.1) for the presentation and application integration layers. This architecture reflects modern hybrid web application design, combining efficient frontend rendering with backend integration for user-facing functionality.

Next.js was selected for several interconnected reasons. First, its file-based routing and layout system aligns well with the structured internship data model, enabling clean separation between listing views, filtering interfaces, and detailed internship pages. Second, its strong TypeScript integration supports maintainable frontend development and safer component interaction. Third, the framework provides performance-oriented rendering and frontend optimization capabilities suitable for responsive web applications.

In local Chromium-based development testing, initial data-driven page loads typically ranged from approximately 0.6 to 2.5 seconds depending on caching state and data fetch conditions, while subsequent cached interactions exhibited significantly faster response times, often approaching near-instant frontend navigation and filtering behavior.

The main user interface components, organized according to the Next.js component architecture, include:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \texttt{InternshipList.tsx}: Displays internship listings as structured cards containing title, company, location, salary information, and extracted skill metadata.
    \item \texttt{SearchBar.tsx}: Provides free-text internship search functionality through frontend interaction mechanisms.
    \item \texttt{FilterPanel.tsx}: Enables category, skill, and location-based filtering for internship exploration.
    \item \texttt{InternshipDetail.tsx}: Presents the complete structured internship record, including cleaned metadata, description, extracted skills, and classification outputs intended for frontend consumption.
\end{itemize}

The frontend architecture follows a clear separation-of-concerns design in which presentation logic remains independent from the semantic enrichment pipeline. This separation improves maintainability, allowing user interface evolution without affecting the underlying internship classification, normalization, or enrichment processes.

\subsubsection{Client-Side Interaction Flow}

The client-side interaction flow begins when a student enters a search query, applies filtering criteria, or changes the current listing page. The frontend operates over the production internship dataset generated by the offline enrichment pipeline. In this workflow, raw postings are collected by the scraper, processed through the local semantic enrichment pipeline, and exported as a production-ready JSON file consumed by the Next.js application.

After the dataset is loaded, the interface applies client-side search, filtering, and pagination logic over the enriched internship records. Filters such as category, skills, and location operate over structured metadata produced during enrichment, while pagination is handled within the frontend state and URL-based navigation mechanisms.

For interactive filtering operations, the frontend employs asynchronous request-management patterns where appropriate, including request cancellation mechanisms to prevent stale filtering results during rapid user interaction. This improves responsiveness when users rapidly modify filtering selections.

This architecture deliberately separates computationally expensive offline semantic processing from lightweight frontend interaction. Internship classification, normalization, skill extraction, deduplication, and domain enrichment are completed prior to deployment, while the frontend focuses exclusively on browsing, filtering, and presenting already-processed internship records. This separation improves maintainability and preserves responsive user interaction.

\subsection{API and Communication Layer}

The application communication layer supports authenticated frontend functionality and structured interaction between the user interface and backend application services. It is implemented using Next.js route handlers and integrated backend functionality within the same application environment.

This approach was selected over a separate backend framework (e.g., Express.js or Fastify) because it reduces deployment complexity, avoids maintaining an independent application server, and enables a unified development environment in which frontend and backend application logic can share common TypeScript definitions and data models.

Within the current architecture, this communication layer primarily supports account-related functionality, authenticated user interactions, and structured application data exchange, while the computationally intensive semantic enrichment pipeline remains an offline preprocessing stage external to the frontend application runtime.

This architectural separation supports the system’s lightweight design goals by minimizing infrastructure complexity while preserving maintainability between the semantic processing pipeline and the user-facing web application.

\subsubsection{Next.js API Routes}

The primary internship data endpoint, /api/internship/route.ts, provides structured access to processed internship records for the frontend application. Implemented using Next.js route handlers, this approach allows backend-integrated application functionality without requiring a separately deployed backend server, reducing infrastructure complexity and simplifying deployment.

Incoming frontend requests are handled through standard HTTP GET operations, with query parameters supporting search, filtering, and pagination interactions within the internship browsing workflow. Request handling is delegated through the application’s data access layer (data.ts), which abstracts the underlying data source and allows the frontend application logic to remain decoupled from storage implementation details.

The internship discovery workflow operates over production-ready data generated by the offline semantic enrichment pipeline. Raw scraped postings are first processed externally through classification, normalization, deduplication, skill extraction, and domain enrichment before being exported as structured production data for application consumption.

To improve responsiveness during repeated access, the application employs lightweight caching mechanisms where appropriate, reducing unnecessary repeated data loading during frontend interaction.

This design preserves a clear separation between offline semantic processing and runtime application delivery, ensuring that computationally intensive enrichment remains outside the live web application request path.

\subsubsection{JSON-Based Data Exchange}

JSON is used as the primary exchange format between the semantic enrichment pipeline, the application data layer, and the client-facing frontend. This choice is consistent with the native format of the processed internship catalog (intern_data.json) and aligns naturally with the TypeScript data models used by the frontend application.

Using a uniform serialization format across storage, processing, and presentation simplifies the overall architecture and reduces the risk of schema drift between system components. The frontend application relies on structured TypeScript interfaces to ensure consistency in the handling of internship records, helping detect mismatches between expected and received data structures during development.

This approach supports lightweight interoperability between the offline Python enrichment pipeline and the web application layer without requiring more complex inter-process communication or dedicated database serialization layers.

\section{Database and Persistence Technologies}

The system employs a hybrid persistence architecture that balances the need for fast, read-heavy access to the internship catalog with the transactional requirements of user-specific data. This design reflects a deliberate trade-off: the static catalog is small (327 records) but read-mostly (updates occur only during daily ingestion cycles), while user data is smaller (per-user bookmarks and preferences) but requires ACID guarantees for concurrent access.

\subsection{Hybrid Persistence Architecture}

The static internship catalog is stored as a local JSON file, while dynamic user data (e.g., bookmarks, search history, user profiles) is stored in a Supabase-managed PostgreSQL database. This hybrid approach keeps the core catalog simple and portable while leveraging relational database features for user state.

\subsubsection{Static Catalog Storage}

The primary internship catalog resides in \texttt{public/intern\_data.json}. This file is generated by the ingestion pipeline (described in Chapter 5) and contains all cleaned, enriched, and structured internship records. Using a single JSON file for the read-heavy catalog offers several advantages:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Version control}: The file can be tracked in Git, allowing complete rollback to any previous state and enabling reproducible experiments across thesis versions.
    \item \textbf{Rapid loading}: During development and testing, the file can be read from disk in under 100 ms, eliminating database connection overhead.
    \item \textbf{Simplified deployment}: The system can be deployed to static hosting environments (e.g., Vercel, Netlify) without a database dependency for read-only operations.
    \item \textbf{Memory caching}: The file is typically 5–15 MB for 327 listings (approximately 300–800 bytes per record after compression), small enough to be cached entirely in memory. This design choice is central to the system's "lightweight" claim: serving static JSON from memory is faster (microseconds vs. milliseconds) and operationally simpler than a database query for the same data.
\end{itemize}

The primary disadvantage of this approach—lack of query flexibility—is mitigated by the fact that all searches are served from the in-memory index rather than from direct file queries. The JSON file serves as a serialization format, not a query engine.

\subsubsection{Supabase and PostgreSQL}

Supabase (version 2.x) provides a managed PostgreSQL backend with built-in REST and real-time APIs. In this thesis, Supabase stores dynamic user data that does not belong in the static catalog, including:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item User accounts and authentication credentials (managed via Supabase Auth, which implements password hashing and session management)
    \item Saved internships (bookmarks), stored as a many-to-many join table between users and internship IDs
    \item Search history and recently viewed listings, stored as time-stamped JSONB records for each user
    \item User preferences (e.g., default filters, notification settings), stored as a JSONB configuration blob
\end{itemize}

PostgreSQL (via Supabase) provides a managed relational backend for user-centric data. It was chosen because it offers strong transactional guarantees (ACID compliance) for authentication and user state management. Supabase specifically reduces operational overhead by providing built-in authentication services (Supabase Auth), automatic backups, and row-level security policies, allowing the thesis to focus on the semantic pipeline rather than database administration.


\section{Data Representation and Type-Safety Tools}

Reliable data representation is essential for a pipeline that transforms noisy, heterogeneous input into structured, queryable records. The system uses TypeScript (version 5.3.0) to enforce a semantic contract across all modules. TypeScript was chosen over plain JavaScript because its static type system catches field mismatches, missing properties, and type errors at compile time, significantly reducing runtime data corruption.

\subsection{TypeScript Data Interfaces}

The \texttt{Internship} interface, defined in TypeScript, specifies the exact shape of every internship record in the system. The complete interface is shown in Listing 3.1.

\begin{verbatim}
interface Internship {
  id: string;          // stable ID: "software-engineer-acme-corp"
  title: string;       // job title
  company: string;     // employer name
  location: string;    // geographic location
  link: string;        // original job posting URL
  salary: string;      // cleaned salary string (e.g., "$100,000 - $120,000")
  description: string; // full job description
  rating: string;      // company rating if available
  job_age: string;     // age of the job posting or date posted
  platform: string;    // source platform (e.g., LinkedIn, Indeed)
  skills: string[];    // array of extracted skill tags
  category: string;    // broad domain (e.g., Software, Data/AI)
  duration?: string;   // optional duration of the internship
}
\end{verbatim}

This interface serves as a contract between the ingestion pipeline, the API layer, the database, and the frontend. TypeScript's static type checking ensures that any deviation from this contract is caught at compile time rather than at runtime. This reduces debugging effort and increases confidence in the correctness of the data pipeline.

\subsection{Structured Internship Records}

Beyond type safety, the system enforces structural consistency through validation functions. After parsing raw JSON, the \texttt{isValidInternship()} function (Listing 3.2) performs the following checks:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Required field presence}: Confirms that both \texttt{title} and \texttt{company} are defined and contain non-empty strings.
    \item \textbf{Filtering malformed records}: If either the title or the company is missing or empty, the record is considered invalid and is excluded from the processed dataset.
\end{itemize}

Records that fail validation are skipped during the ingestion process, preventing corrupt or incomplete data from entering the search index. This validation layer is an example of defensive programming in data integration pipelines: it ensures that the UI always has the minimum required information to display a meaningful internship card to the user.

\begin{verbatim}
function isValidInternship(item: any): boolean {
  const hasTitle = item.title && item.title.trim() !== '';
  const hasCompany = item.company && item.company.trim() !== '';
  return hasTitle && hasCompany;
}
\end{verbatim}

\section{Semantic Enrichment and NLP Tools}

The implemented enrichment layer is intentionally lightweight. It uses deterministic TypeScript helper functions for title cleaning, company and location normalization, salary extraction, category assignment, and dictionary-based skill extraction. This choice supports the thesis's cost-aware design goal because the routine processing path does not require external LLM calls, GPU inference, or a separate Python service.

\subsection{Rule-Based Semantic Components}

The current implementation uses rule-based components as the first semantic layer. These include a stable identifier generator, a salary parser based on regular expressions, a category classifier using title anchors, and a skill extractor using a curated list of common technical and professional keywords. Although this layer is less expressive than a learned model, it is deterministic, cheap to run, and easy to inspect.

\subsubsection{Planned Transformer Extension}

all-MiniLM-L6-v2 remains the proposed Layer B extension for cases that deterministic rules cannot resolve. In the intended architecture, the compact transformer would be used for:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Disambiguating ambiguous job titles}: Titles such as "Consultant" could refer to Business Consulting, Technology Consulting, or Healthcare Consulting. all-MiniLM-L6-v2 embeds the title and description context for similarity-based classification.
    \item \textbf{Classifying skills from context}: Determining whether a mention of "Java" refers to the programming language (skill) or the island (location) based on surrounding text.
    \item \textbf{Extracting implicit requirements}: Identifying that a job requiring "experience with modern frontend frameworks" implies skills such as React, Vue, or Angular, even if those names are not explicitly mentioned.
\end{itemize}

In the current prototype, this model is not part of the production request path. It is therefore treated as an architectural extension and evaluation target rather than as an already deployed component.

\subsubsection{All-MiniLM-L6-v2 Embeddings}

all-MiniLM-L6-v2 produces semantically meaningful sentence embeddings that can be compared using cosine similarity. The model, distributed through the Sentence-Transformers library, has the following characteristics:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Dimensionality}: 384-dimensional embeddings, a deliberate trade-off between expressiveness (higher dimensions) and computational efficiency (lower dimensions). The compact 384-dimensional representation retains sufficient semantic discriminative power for the internship domain while reducing storage and computation.
    \item \textbf{Performance}: Approximately 30-60 sentences per second on the reference CPU (Intel Core i7-10750H). For the 327-listing corpus, generating embeddings for each listing (title and description concatenated) takes approximately 5-8 minutes, which is acceptable for batch ingestion.
    \item \textbf{Model size}: 80 MB on disk, loading into approximately 120 MB of RAM. This is small enough to fit comfortably within the 16 GB commodity hardware constraint.
\end{itemize}

These characteristics make all-MiniLM-L6-v2 appropriate for future offline enrichment: embeddings could be pre-computed for each internship's concatenated title and description, stored with the catalog, and then compared with query embeddings at search time. This would extend the implemented keyword and category filtering without replacing the deterministic preprocessing layer.

\section{Indexing and Retrieval Technologies}

The implemented retrieval environment exposes the normalized catalog through API routes and supports client-side browsing, category display, skill tags, and role-detail lookup. The broader methodology also defines a hybrid lexical and dense retrieval strategy as the next extension of the system. This distinction matters: the current repository demonstrates the ingestion and structured catalog foundation, while dense retrieval and rank fusion remain proposed enhancements.

\subsection{Lexical Retrieval Tools}

Lexical search provides the retrieval baseline. The system builds an in-memory inverted index over the cleaned text of each internship. The indexed fields are:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \texttt{title} (weight: 3.0): Job titles are the most informative field for lexical matching.
    \item \texttt{description} (weight: 1.0): Descriptions provide comprehensive but less focused evidence.
    \item \texttt{company} (weight: 1.5): Company names are moderately important, especially for branded searches.
\end{itemize}

Keyword matching remains important for exact matches on skill names (e.g., "Kubernetes"), company names (e.g., "Acme Corp"), and technical acronyms (e.g., "RTL") where semantic similarity alone may be too diffuse. The lexical index is rebuilt periodically when the catalog is updated, which is acceptable because updates are assumed to occur on a daily or weekly basis rather than continuously. The index build time for 327 listings is approximately 2-3 seconds.

The implementation follows standard information retrieval practices for term frequency and document length normalization, ensuring reliable performance across a wide range of corpora.

\subsection{Vector-Based Search Tools}

Vector search supports semantic matching by comparing dense embeddings. The system relies on a vector indexing library to perform efficient similarity search across the high-dimensional embedding space.

\subsubsection{Approximate Nearest-Neighbor Search}

The system employs Approximate Nearest-Neighbor (ANN) indexing to enable fast retrieval even as the dataset grows. ANN algorithms trade a small amount of retrieval precision for substantial gains in search speed.

For a catalog of 327 embeddings, vector-based indexing reduces query latency to approximately 5-10 ms while maintaining high recall (greater than 0.95 relative to exact search). The index is configured to balance build time, memory usage, and retrieval accuracy, ensuring that the system remains responsive on commodity hardware.

In the proposed extension, the vector index would be stored in memory and updated only when the catalog changes, consistent with the amortized cost model.

\subsubsection{Hybrid Fusion with Reciprocal Rank Fusion (RRF)}

Reciprocal Rank Fusion combines lexical and dense retrieval outputs using rank positions rather than raw scores. Given a lexical ranked list and a vector-based ranked list, RRF computes a fused score for each document as:

\[
    \mathrm{RRF\_score}(d) = \sum_{r \in \{\mathrm{lexical},\mathrm{vector}\}} \frac{1}{k + \mathrm{rank}_r(d)}
\]

where \(k\) is a constant (typically 60). This formula has three important properties:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Scale invariance}: Because it operates on ranks rather than raw scores, RRF does not require normalization of lexical scores (which are theoretically unbounded) or cosine similarity (bounded between -1 and 1). This eliminates a common source of fragility in hybrid retrieval systems.
    \item \textbf{Diminishing returns}: The \(1/(k + \text{rank})\) function gives high weight to top-ranked documents but quickly diminishes as rank increases. A document that ranks 1st in one system receives score \(1/(60+1) \approx 0.0164\), while a document that ranks 100th receives \(1/(60+100) \approx 0.0063\). This reflects the practical observation that users rarely look beyond the first page of results.
    \item \textbf{Robustness}: The constant \(k\) smooths the contribution of low-ranked documents. Even a document that ranks 1000th in one system still contributes a small positive score \(1/(60+1000) \approx 0.00094\), ensuring that a document that is extremely relevant in one modality but missing from the other is not completely excluded.
\end{itemize}

In the complete architecture, the final ranked list would be sorted by RRF score and returned to the client. RRF is parameter-free aside from the constant \(k\), which has been shown to be robust across a wide range of values (typically 50-100) in the original RRF paper and subsequent studies. This makes it suitable for a system that cannot be extensively tuned per deployment.

\section{Development, Testing, and Evaluation Environment}

The development environment must support reproducible ingestion, retrieval benchmarking, and performance measurement. All experiments described in Chapter 6 are conducted on a controlled hardware configuration to ensure that performance comparisons are fair and reproducible.

\subsection{Hardware Configuration}

All experiments are run on a single workstation with the following specifications:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{CPU}: Intel Core i7-10750H (6 cores, 12 threads, 2.60 GHz)
    \item \textbf{RAM}: 16 GB RAM
    \item \textbf{Storage}: 715 GB total storage
    \item \textbf{GPU}: None (all processing runs on CPU)
    \item \textbf{Operating System}: Ubuntu 22.04 LTS
    \item \textbf{Node.js version}: 20.11.0 (LTS)
\end{itemize}

This configuration embodies the "commodity hardware" constraint stated in the thesis objectives. The total cost of this hardware at the time of writing is approximately \$1,200, which is within the budget of a typical university research lab or small startup. No GPU is required, which is a deliberate choice: GPU instances are substantially more expensive to rent (approximately 3--5 times higher hourly cost on cloud providers) and are not universally available in commodity hosting environments.

\subsection{Measurement and Logging Tools}

To support quantitative evaluation, the prototype exposes simple inspection points and can be extended with measurement and logging utilities:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Ingestion logging}: Records processing time per listing, cache hit/miss rates, and errors. This helps identify bottlenecks in the pipeline (e.g., whether the all-MiniLM-L6-v2 transformer or the regex salary parser is the slowest stage). Logs are written in JSONL format (one JSON object per line) to facilitate subsequent analysis with \texttt{jq} or Python.
    \item \textbf{Query latency}: The API endpoint wraps each request with \texttt{performance.now()} timers, logging p50 and p99 latency to a rotating log file (rotated daily, retained for 30 days). These metrics are essential for evaluating whether the system meets interactive latency targets (typically <200 ms for p99). Latency is measured at three points:
    \begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
        \item \textit{End-to-end}: From receipt of HTTP request to response transmission
        \item \textit{Retrieval}: Time spent in Lexical Search + Vector Search + RRF (excluding JSON serialization)
        \item \textit{Serialization}: Time spent converting results to JSON
    \end{itemize}
    \item \textbf{Memory profiling}: The \texttt{process.memoryUsage()} API captures RSS (Resident Set Size) and heap usage after cache warm-up. This is used to verify that the system fits within 16 GB of RAM, a key constraint of the commodity hardware assumption. Memory snapshots are taken at pipeline start (after model loading), after cache warm-up, and during peak query load.
    \item \textbf{Cost tracking}: For the LLM baseline comparison, the system estimates API costs based on token counts and current pricing models (e.g., GPT-3.5-turbo at \$0.001 per 1,000 input tokens and \$0.002 per 1,000 output tokens). Token counts are approximated using the \texttt{tiktoken} library (the same tokenizer used by OpenAI) to ensure accurate cost estimates.
\end{itemize}

When enabled, these logs can be aggregated into CSV files for analysis using Python or standard command-line tools. The present repository pins dependencies through \texttt{package-lock.json}; additional benchmark scripts would be required for a fully automated reproduction package.

\subsection{Reproducibility Measures}

To ensure that the experimental results reported in Chapter 6 can be reproduced by other researchers, the following measures are implemented:

\begin{itemize}[leftmargin=1.4em,itemsep=0.25em,topsep=0.25em]
    \item \textbf{Fixed random seeds}: All libraries with stochastic behavior (vector index construction and all-MiniLM-L6-v2 inference) use fixed random seeds (seed = 42) to ensure deterministic outputs across runs.
    \item \textbf{Version pinning}: All dependencies are pinned to exact versions in \texttt{package-lock.json}, which is included in the thesis repository.
    \item \textbf{Environment specification}: The repository documents the Node.js and Next.js stack through \texttt{package.json} and \texttt{package-lock.json}. A Dockerfile would be a useful future addition for strict environment replication.
    \item \textbf{Data anonymization}: The 327-listing corpus is used as the working research dataset. If redistributed, source terms and privacy constraints would need to be reviewed and an anonymized or synthetic alternative prepared.
    \item \textbf{Benchmark scripts}: Dedicated benchmark scripts should be added for future replication of retrieval and latency metrics.
\end{itemize}
